# OryxOS v0.4 分布式底座规划（评审稿）

**日期**: 2026-09-02 | **状态**: 待评审 | **前置**: v0.3 治理面已交付（020~023）

> 本文供协作者评审。每条关键裁决都给出理由与被否掉的备选，欢迎针对性反对；文末列出明确邀请评审的开放问题。

---

## 1. 目标与边界

**双目标**：

- **容错**：挂一个副本不断服务；滚动升级用户无感
- **承载**：用户量上来后加副本就能摊（这是分布式更日常的价值，不只是灾备）

**验收 Demo（版本完成的定义）**：K8s 双副本——① 滚动升级中进行的会话不断线；② 定时任务恰好执行一次；③ 并发多用户/同用户连发消息无丢失、无重复、无报错；④ 副本 A 创建的 Agent 在副本 B 秒级可见可对话。

**不做**（边界）：消息队列、K8s Operator、跨请求 Provider 健康记忆、文件全面入库（留 v1.0 租户模型定型后）、智能路由。

## 2. 现状盘点：有状态且单点的全量清单

按"状态在哪、多副本下会发生什么"盘点全部已有功能，结论三分：

### 2.1 DB 态——基本就绪，换库即好

会话/审计三表/记忆(sqlite 档)/知识 chunk/调度状态/执行历史/providers/notify/策略/api_keys 全在 DB，且两个关键机制 day one 已按跨进程语义设计：

- **会话乐观锁**：`JpaSessionManager.saveIfUnchanged` 条件更新，javadoc 明写"防跨进程旧快照覆盖"
- **向量层库无关**：BLOB(float32[]) + 纯 Java 余弦扫描——**换 PostgreSQL 零向量迁移**（修正了 roadmap 当年"切 pgvector"的假设，pgvector 降为可选优化）

### 2.2 内存态——两处要改，其余是可重建缓存

- `AgentService.sessionLocks` 进程锁：多副本下只防本副本，跨副本语义要重建（→ 025 核心）
- 飞书/企微/钉钉长连接：事件是单连接投递还是广播？**未实证**（→ 025 前置调查 + 幂等去重）
- ChatModel 缓存/知识向量内存加载：各副本自建，无碍

### 2.3 文件态——第三战场（本次盘点新增）

- Agent 工作区（AGENT.md/skills 软连接）：共享卷可解，但 **`WorkspaceWatcher` 的 inotify 在共享存储上不可靠**——热更新感知要换机制
- 知识库源文件：共享卷 + 索引任务需跨副本认领
- 记忆 markdown 档：并发追加写丢数据——裁决为单机档
- 启动期一次性逻辑（SchemaUpgrade/SecretMigration/播种）：多副本并发启动的安全性

### 2.4 瓶颈链（用的人多了，按序炸哪）

```
① SQLite 单写者锁（几百写 TPS 天花板，每轮对话写 3+ 行）   → 024 解决
② 同 session 跨副本并发（单机排队退化为多机报错）           → 025 解决
③ LLM Provider 配额（加副本不增加模型限流；023 fallback 缓冲）→ 运营面，如实声明
④ 计算层（虚拟线程挂 IO 等待，单副本可承数万并发）           → 最不慌
```

## 3. 参考实现调研结论（StaffDeck / AgentScope Java）

对两个项目的分布式实现做了逐文件调研（多实例架构/归属与接管/分布式锁/调度/状态存储/引入组件八个维度），交叉结论：

### 3.1 核心发现：两家殊途同归于「turn 租约互斥」，都没做粘性路由

| | StaffDeck | AgentScope Java |
|---|---|---|
| 形态 | 刻意单实例（文件锁拒绝第二进程），但租约模型完整 | 无状态多副本；官方明确「不 sticky-route，只互斥」，`sessionAffinity` 是死代码 |
| 会话归属 | turn 租约表：唯一约束即互斥，执行期归属、执行完释放 | 同款（TTL 90s、TTL/3 心跳续租），turn 间无归属、每轮从 store 重载 |
| 副本挂了 | 租约过期→终结该轮+保留检查点+告知用户重发，**不自动重放**（标记"副作用结果未知"） | 租约过期→reconciler 释放+置 idle，下一条消息任意副本自然接管 |

**采纳口径**：绑定的是"正在执行的一轮"（租约 + 续租 fencing 硬互斥），不是"会话永久归属副本"（粘性路由）——状态在共享 DB，永久归属换不来正确性收益，却要付路由/转发/再平衡整套复杂度（AgentScope 连转发层都没做）。副本挂 → 租约过期 → 下一条消息落到哪个健康副本哪个接管：零协调者、秒级、零数据丢失。LB 层 IP-hash 粘性可作缓存优化叠加，不承担正确性。

### 3.2 从 StaffDeck 吸收（租约工艺）

1. **统一并发原语**：「唯一约束即互斥 + 插入失败抢过期的 + 条件 UPDATE rowcount==1」——OryxOS 全部认领场景（session turn/定时任务/知识索引/IM 事件）用同一套
2. **续租带 owner fencing、失败即终止执行**——防脑裂核心
3. **双层锁**：进程内快路径 + DB 慢路径（OryxOS 的 sessionLocks 保留为快路径，恰好已有一半）
4. **不自动重放**：崩溃轮次终结为失败、执行历史留痕、告知用户重发、标记副作用结果未知——Agent 执行有外部副作用，重放不诚实
5. 回收多证据交叉验证（避免误杀慢任务）；IM 事件幂等回执表

### 3.3 从 AgentScope Java 吸收

1. **总路线验证**：「无状态副本 + 外置状态 + turn 互斥 + CAS 兜底」——OryxOS 现状与之同构
2. **协调面接口化**：`CoordinationStore` 式接口 + JDBC 默认实现 + Redis 可插拔第二实现——默认零新增件（同库多副本即可跑，企业不一定给 Redis），规模上来换实现即可
3. **误配 fail-fast**：分布式档 + 单机型组件（markdown 记忆档等）→ 启动直接拒绝
4. 「权威落库 + seq 游标」事件流分层——记为 v0.5 多 Agent 事件流的方案储备

### 3.4 两家的坑，明确避开

| 坑 | 出处 | OryxOS 对策 |
|---|---|---|
| 文件锁承担正确性（跨机器静默失效） | StaffDeck | 正确性只依赖 DB 租约 |
| **startup 全量抹除活跃行**（多副本互杀，最危险） | StaffDeck | 回收只认过期租约，永无 startup 分支 |
| lease_owner 随机 ID 不可路由 | StaffDeck | owner 写成 `instanceId@epoch` |
| 租约参数硬编码、零指标 | StaffDeck | 配置化 + `leases_held/reclaimed/fence_conflicts` 指标（挂 023 MetricsRecorder） |
| 锁不可达 30s **静默降级为进程锁**（脑裂后门） | AgentScope | fail-closed，拒绝服务优于错误服务 |
| fencing token 发了但客户端不用 | AgentScope | fencing 贯穿到续租与终止路径 |
| 锁无续期看门狗（长 turn 丢锁） | AgentScope | 租约心跳续租为必选项 |
| 多租户拼字符串 | AgentScope | v0.4 不做租户，但不埋拼接式债务 |

## 4. 四刀分解

```
024 可插拔存储 ──→ 025 session 归属与多副本正确性 ──→ 026 文件面分布式 ──→ 027 容器交付
（物理前提）      （行为正确性）                    （第三战场）        （验收 Demo 闭环）
```

### 024 可插拔存储

- Flyway 接管迁移，**收编五个手工 SchemaUpgrade**（SQLite ALTER 弱的补偿产物退役；Flyway 自带迁移锁顺带解决多副本并发启动）
- PostgreSQL 支持：方言/迁移脚本双轨（14 处 AUTOINCREMENT 等专有面清理）
- **SQLite 保持默认零配置档**——单机五分钟上手是产品资产，PG 是可选档不是升级
- 已知风险：本开发环境的 PG 自动化测试路径（镜像拉取受限）需在 plan 阶段先行验证

### 025 session 归属与多副本正确性（本版本的技术核心）

- **turn 租约表**：唯一约束即互斥、插入失败抢过期的、条件 UPDATE CAS；owner=`instanceId@epoch`；续租 fencing 失败即中止；过期惰性接管 + 不重放
- 双层锁：进程内 sessionLocks 快路径 + DB 租约兜底
- 定时任务/知识索引/IM 事件用**同一套 CAS 认领原语** + 幂等去重
- `instances` 心跳表（落库不落内存）
- 协调面接口化（JDBC 默认 / Redis 可插拔）
- 租约配置化 + 指标；分布式误配 fail-fast；启动并发安全
- 前置调查：IM 长连接多副本投递行为实证

### 026 文件面分布式

- Agent 工作区/知识库源文件走共享卷（NFS/PVC RWX——其 HA 是企业存储设施职责，与"DB 的 HA 交给 DBA"同一边界哲学）
- **watcher 从 inotify 改为 DB 版本号通知**（DB 作变更通知总线、文件作内容载体，仍零新增件）
- 知识索引任务 DB 原子认领（复用 025 原语）
- markdown 记忆档裁决为单机档（分布式强制 DB 记忆后端，误配 fail-fast）

### 027 容器交付

- 官方镜像 + Helm Chart + 探针（actuator 已就位）；主密钥接 K8s Secret（022 环境变量档零改动）；共享卷挂载编排
- OpenTelemetry tracing 导出（021 内生 trace 的导出面）
- 验收 Demo 四条在此闭环

## 5. 与竞品的差异化立足点

- 对 **Dify/RAGFlow**（Postgres+Redis+Celery+向量库多件套）：OryxOS 默认**一个共享 DB 就能多副本**，锁/调度/变更通知全走 DB；Redis 是规模档可选插件而非必答
- 对 **kagent**（CNCF，K8s-native CRD/Operator）：OryxOS 不绑 K8s——裸机/VM/K8s 都是一等部署形态，Helm 是兼容而非归顺
- 对 **AgentScope Java** 自身：其锁语义（可降级/无 fencing 落地/无续期）、消息层（全轮询非原子）停在"能跑"水平——OryxOS 按企业底座标准把这三块做对

## 6. 开放问题（邀请评审重点拍砖）

1. **turn 租约的粒度与 TTL**：参考值 StaffDeck 900s / AgentScope 90s+心跳续租——OryxOS 单轮含多次 LLM 往返（长的分钟级），倾向"短 TTL（60~90s）+ 心跳续租"而非长 TTL，是否认可？
2. **崩溃轮次的用户体验**：不重放 + 告知重发是底线；是否需要在 IM 渠道主动推一条"刚才那轮中断了请重发"（StaffDeck 做了）？
3. **MySQL 支持的优先级**：roadmap 原文 PG/MySQL 并列；建议 v0.4 只做 PG（企业开源部署主流 + advisory lock 等能力更全），MySQL 视需求后补——是否接受？
4. **共享卷的最低要求**：NFS 语义参差（锁/缓存一致性），我们只依赖"读写可见性 + rename 原子性"，不依赖文件锁——文档如何声明支持矩阵？
5. **Redis 插件的启动时机**：接口留缝 v0.4 落，Redis 实现是 v0.4 内做完还是留待真实规模需求触发（我倾向后者，YAGNI）？
6. **024 的 PG 测试策略**：本地/CI 环境镜像受限，候选：宿主机 PG 服务 / 嵌入式 PG 二进制 / 门禁内 SQLite + 发布前 PG 真机清单——需要定一个。
