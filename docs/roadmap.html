OryxOS 演进路线图

从「单机可信的 Agent Harness」演进为「企业级分布式 Agent OS」，五个版本主题依次递进，每一步都以可演示的 Demo 验收。

当前版本 v0.3（治理面已交付） 目标 Apache 孵化 制定于 2026-08 · 更新于 2026-09-02

演进方式：六条原则

决定「怎么走」比「走到哪」更重要，所有排期冲突回到这六条裁决。

01 · 版本主题制

一个版本只讲一个故事

延续 spec-driven 节奏（specs/NNN），每个 minor 版本一个主题、一组 spec、一个验收 Demo。不做没有主题归属的散功能。

02 · 状态外置先行

单机做深，分布式自然展开

不引入 etcd/Nacos。先把 Session、记忆、调度、审计全部外置到可插拔存储，实例无状态化后，分布式只是「多跑几个副本」。

03 · 治理领先半步

每次能力扩张前，先补齐管它的手段

审计 → 可视 → 可查 → 可审批，治理面始终比功能面领先。这是对 96% 已上生产、只有 12% 管得住的市场缺口的直接回答。

04 · 开放标准优先

不自造协议

工具走 MCP，跨 Agent 走 A2A，Skill 兼容 agentskills.io 目录形态。与 OpenClaw / Hermes 生态互通而非对抗。

05 · 接口即承诺

AGENT.md 与 /api/v1 保持稳定

目录格式和 REST 契约是用户资产。破坏性变更必须走版本门禁 + 迁移脚本，SQLite → PostgreSQL 迁移由 Flyway 承载。

06 · 单一事实源

文档先对齐，再对外

以 VisionAndRoadmap.md 为准，修正「做不做编排」「etcd vs DB」两处文档冲突，归档过期的里程碑章节。

主线：五个版本，四次能力跃迁

排序逻辑：先补打单短板 → 再坐实治理差异化 → 分布式垫底座 → 多 Agent 协作 → 生态飞轮。

v0.2

补齐公式 —— 让 Agent 有知识、有入口

已交付 · 2026-08

三块打单短板一次补齐：知识库是公式唯一缺角（Dify/RAGFlow 的核心卖点）；IM 入站是企业 Agent 的实际入口（OpenClaw 最大吸引力）；API 裸奔过不了企业安全评审。

  • 知识库导入/切分/检索 + retrieve_knowledge 工具 + frontmatter knowledge: 引用。向量层定义 VectorStore 接口，先用 sqlite-vec 落地（零新依赖），为 v0.4 换 pgvector 留缝
  • ChannelIM 入站抽象 + 飞书双向接入先行（沙箱域名白名单已含 *.feishu.cn），企微/钉钉随后。复用现有 Notify 凭证体系
  • 流式SSE 流式响应（text/event-stream），保持同步模型不变——虚拟线程内逐 token 写出，不引入 WebFlux
  • 认证/api/v1 API Key 认证（RBAC 留到 v1.0，先把门锁上）；CORS 白名单收紧
已验收：四角全部落地——知识库（014 导入/检索 + 015 语义召回）、飞书长连接双向渠道（017 真机 V1~V7）、REST API Key 门禁（018，无 Key 401）、SSE 流式（019，REST 三端点 + CLI + 管理台打字机）。各特性验收报告见 specs/01x-*/acceptance-report.md；提前预支了 v0.3 的审计看板（016）。
v0.3

治理面 —— 把「可审计」升级为「可治理」

已交付 · 2026-09（较排期提前约一季度）

审计数据已落库一年，只写不查等于没有。这一版把差异化主张坐实：单机就能交付、且被后续分布式放大的治理能力。全部端到端可控，无外部依赖，适合放在分布式之前。

  • 策略Tool Policy（020）：全局 + Agent 级工具 allow/deny，三道保险（事前过滤/事中拒绝/事后 blocked_by='policy' 留痕），热更新即时生效
  • 审计trace ID 串联一次 ReAct 全链路 + 展示层脱敏（021）：一次消息处理=一个 trace，三表同链、日志 MDC 互查、管理台「审计」页时间线回放；查询 API 与聚合看板由 016 预支
  • 看板Prometheus 业务指标（023）：oryxos_* 六类计数（LLM 调用/耗时/token/工具/策略拦截/切换）经 /actuator/prometheus 接企业监控栈
  • 密钥密钥加密存储（022）：落库凭证 AES-256-GCM（enc:v1:），主密钥两档（环境变量优先/master.key 首启自动生成），SecretCipher 接口为 KMS/Vault 留缝——「数据库泄露不再等于凭证泄露」
  • 路由Provider fallback（023）：frontmatter fallback 有序备用，单次调用故障按序切换、主备留痕 trace 可回放；智能路由留到数据积累后（本版指标+审计正是其数据来源）
已验收：Tool Policy 越权拦截留痕（020 E2E）→ 管理台按 trace ID 回放完整链路与成本（021 真机 V1~V8）→ db 直查全密文（022 V1~V7）→ 主败备成 29ms 级切换 + 监控指标对照（023 V1~V6）。各特性验收报告见 specs/02x-*/acceptance-report.md。
v0.4

分布式底座 —— 兑现名字里的 Distributed

进行中 · 2026-09 起（原排期 2027 Q2）

「无状态实例、状态外置」从 day one 就是设计前提，这一版兑现它——目标是双重的：容错（挂一个副本不断服、滚动升级无感）与承载（用户多了加副本就能摊，任意 session 落任意副本、无粘性）。2026-09 全量状态盘点（维护者审议）：DB 态基本就绪（会话乐观锁与向量层库无关形态 day one 已在，换库比预想轻）；内存态两处要改（session 进程锁、IM 长连接投递行为）；文件态是第三战场（Agent 工作区/知识库源文件/watcher 热更新/记忆 markdown 档）。瓶颈链按序：SQLite 单写者锁 → 同 session 跨副本语义 → 模型侧配额（运营面，023 fallback 缓冲）→ 计算层（虚拟线程挂 IO 等待，最不慌）。差异化坚守「零新增件」：无 Redis、无消息队列、不做 Operator——锁/调度/变更通知全走共享 DB，文件面走企业共享存储（NFS/PVC），两者的 HA 都是企业已有设施（对 Dify 多件套与 kagent 绑 K8s 的双向差异化）。按四刀推进：

  • 024 存储可插拔存储：Flyway 收编五个手工 SchemaUpgrade（SQLite ALTER 弱的补偿产物退役，且 Flyway 自带迁移锁解多副本并发启动）、PostgreSQL 方言/迁移脚本双轨（14 处 AUTOINCREMENT 等专有面清理）；SQLite 仍是默认零配置档（单机体验是产品资产）；pgvector 降为可选优化留缝（向量层 BLOB+Java 余弦换库零迁移）
  • 025 计算面计算面多副本正确性与并发承载：定时任务 DB 抢锁（xxl-job 思想自实现）多副本恰好一次；同 session 跨副本串行化（PG advisory lock，行为与单机进程锁等价——排队而非报错）；IM 长连接多副本投递行为实证 + 事件幂等去重；启动期并发安全（播种/SecretMigration）；实例注册 + 心跳表
  • 026 文件面文件面分布式：Agent 工作区/知识库源文件走共享卷 + watcher 从 inotify 改为 DB 版本号通知（共享存储上 inotify 不可靠；DB 作变更通知总线、文件作内容载体，仍零新增件）；知识索引任务 DB 原子认领（与调度抢锁同款语义）；记忆 markdown 档裁决为单机档（分布式强制 DB 记忆后端，并发追加写丢数据的诚实答案）；文件全面入库留 v1.0 租户模型定型后再议（「目录=Agent」接口承诺不动）
  • 027 交付容器交付：官方镜像 + Helm Chart + 探针（actuator 已就位）；主密钥走 K8s Secret（022 环境变量档零改动接线）；共享卷挂载编排；OpenTelemetry tracing 导出（021 内生 trace 的导出面，对齐 kagent 可观测水位）
验收 Demo：K8s 双副本——滚动升级进行中会话不断线；定时任务恰好执行一次；并发多用户/同用户连发消息无丢失无重复无报错；副本 A 创建的 Agent 在副本 B 秒级可见可对话。
v0.5

多 Agent 协作 —— 从单兵到团队

2027 Q3

愿景的核心一跃：一句话任务 → 底座拆解 → Agent 团队分工交付。前四版把「可靠、可治理、可扩容」垫好，这一版才有资格做协作——否则是在不可控的地基上叠不可控。

  • 委托子 Agent 委托：隔离会话、隔离上下文、结果回传（Hermes 模式的企业版）
  • A2A对接 A2A 协议：跨 Agent / 跨节点发现与协同，进程内与跨实例同一套语义
  • FlowFlow 声明式编排：一个目录/一个 md 定义多 Agent 流程，与「目录即 Agent」同构；自然语言生成 Flow 草稿
  • 降本execute_code：多步工具流水线压成一次推理执行
验收 Demo：发布「调研 X 并出报告」一句话任务 → 协调者拆解 → 检索/分析/撰写三个 Agent 协作 → 审批后交付，全程审计可回放。
v1.0

生态与飞轮 —— Apache 就绪

2027 Q4 →

1.0 的定义不是功能多，而是接口稳定 + 质量可证 + 社区可长。评测 harness 与 Skill 自沉淀让审计数据变成成长飞轮；完整 RBAC/多租户补齐企业采购最后一公里。

  • 质量Agent 评测 harness（行为回归），发版门禁挂评测分
  • 飞轮成功执行自动沉淀 Skill；审计轨迹 → 离线评测 → 蒸馏便宜模型
  • 安全容器级沙箱后端（Docker，microVM 留升级位）；三级租户 + RBAC + SSO（OIDC）
  • 生态Skill 市场（agentskills.io 兼容）；Java/Python SDK；OryxOS 自身作为 MCP Server 对外暴露
阶段门禁：API 冻结一个版本无破坏性变更 + 3 家以上真实企业部署案例 + 提交 Apache 孵化提案。

关键取舍备忘

决策点取舍理由
向量库两步走v0.2 sqlite-vec → v0.4 pgvector知识库不等 PostgreSQL；用 VectorStore 接口隔离，迁移成本封在一层
认证两步走v0.2 API Key → v1.0 RBAC/SSO先把门锁上过安全评审，权限模型等租户模型定型再做，避免返工
分布式不用 etcdDB 抢锁 + 心跳企业已有 DB 运维能力，零新增件；与「无状态实例」原则同构（采 VisionAndRoadmap 方向 A，废弃旧文档 Nacos/ETCD 方案）
编排的边界做 Flow 目录编排，不做可视化画布与 Dify/n8n 保持互补而非对撞；md 声明式与「目录即 Agent」同一心智模型
同步模型不动摇SSE/并行工具都在虚拟线程内做宪法七；异步框架带来的复杂度在 Agent 场景无收益
HITL 审批移出主线v0.3 不做危险动作人工审批，治理走「事先定义」的 Tool Policy企业 Agent 多为定时/群聊无人值守场景，发起人 ≠ 审批人、审批人常缺位；无 RBAC 时临时越权责任链断裂，审批疲劳沦为安全剧场。若未来有真实需求，须待 v1.0 RBAC/租户定型后再评估（2026-08-27 维护者裁决）

节奏说明：季度粒度是主题排期，不是承诺交付日；每版本内部仍按 spec → clarify → plan → tasks → implement 的既有流程走，主题内的 spec 可并行。竞品情报（OpenClaw 生态、kagent 进 CNCF incubation、AgentCore Policy 演进）每季度复盘一次，只调整优先级，不推翻主线。
