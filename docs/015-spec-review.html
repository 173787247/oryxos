记忆系统升级：015 对比现有功能的优化点

现状基线 main（014 已合入） 需求文档 specs/015-memory-semantic-recall/spec.md 范围 16 条 FR / 10 条 SC / 4 个用户故事 日期 2026-08-20

一句话：现在的长期记忆「记得住、找不准」——只能按字面关键词翻归档区。015 让 Agent 能按意思、按时间找回记忆；同时把记忆后端升级为与知识库同款的插件契约，并在本期把 mem0 档真实跑通（百炼等其他服务将来照同一契约挂入），并为分布式部署预留设计约束。未配置向量化的部署行为与今天一致，零破坏。

PART 1 / 用户可感知的优化Agent 的记性变好了

01检索：从「字面匹配」到「语义 + 关键词 + 时间」三路融合

现状
recall_memory 只在归档区做纯关键词包含匹配：用户上周记了「发布流程在灰度环节踩雷」，这周问「上次那个部署的坑怎么处理的」——没有共同关键词，找不回来。且 markdown 档区分大小写、sqlite 档不区分，两档行为还不一致。
015 后
三路并行召回再按名次融合：语义路（措辞不同也能命中）＋关键词路（工单号、代号等精确短语保底）＋时间新近路（同等相关时最近的排前，贴合「上次」的直觉）；大小写行为跨档统一。工具名称与参数完全不变。

价值：跨会话记忆真正可用——这是记忆系统从「日志」变成「记性」的分水岭。复用 014 知识库已交付的检索基建，零新依赖、零新服务。

02零配置升级，故障自动降级

现状
无向量化概念。
015 后
已为知识库配了向量化的部署，记忆检索自动同享同一份配置；没配置的部署行为与今天逐项一致（唯一例外是大小写统一修正）；向量化服务中途故障时检索自动退回「关键词＋时间」两路并在结果里标注，对话不中断，恢复后自动回到三路。

价值：存量部署无迁移动作、无学习成本；升级是「白捡的」，不是「要伺候的」。

03记忆写入零丢失，历史记忆自动补索引

现状
save_memory 只落库（没有索引这回事）。
015 后
落库仍然第一优先，向量化在落库后异步进行——向量化失败绝不影响记忆写入（标记待索引，随对账自动补齐）；升级后首次启动，存量历史记忆 30 秒内自动补建索引，旧记忆同样能按语义找回；向量模型更换时索引自动重建，不需要任何手动操作。

价值：记忆是对话的副作用，丢了不可恢复——所以一致性取舍与知识导入相反（知识可以显式失败重试，记忆必须先保住本体）。这条是专门为记忆定制的可靠性设计。

04模型更会「分区」：save_memory 参数指引增强

现状
工具说明只有一句「记住一件值得长期记住的事」，模型不知道核心区/归档区的语义差别，全凭常识猜。
015 后
参数说明讲清取舍依据：core = 少量常驻事实（每轮都在上下文）；archival = 一般值得记的事件（需要时检索找回）；不确定填 archival。纯文案增强，签名不变。

价值：核心区更干净（省每轮 context 预算），归档区职责更明确。

PART 2 / 架构层优化为后续演进把地基打平

05记忆后端升级为插件契约——外部记忆服务可安全接入

现状
三档后端（markdown/sqlite/mem0）共用一个三方法接口，没有能力声明、没有跨档行为测试；mem0 档是未经实测的骨架。接口上人人平等，实际能力参差——干不了的事只能运行时才暴露。
015 后
对齐 014 知识库验证过的插件范式：每个后端声明检索能力三态（仅关键词 / 条目交底座内置检索 / 后端自带语义整体接管）＋分区支持位（外部服务不懂 core/archival 时必须显式声明，防止 scope=core 被静默降维）＋参数化契约测试全档必须绿＋「自带语义」测试桩验三同（同工具/同审计/同分区语义）。

价值：本期直接在自托管 mem0 OSS 上跑通这条路（core=原文模式+元数据分区、archival=交提炼、分区过滤实测、docker compose 可复现，集成测试打 integration 标签）；将来接百炼、ReMe 只需新写一个实现类挂进注册表——不改任何上层代码与需求。知识与记忆从此共用同一套插件哲学。

06修复既有作用域缺口：sqlite 档记忆跨 Agent 共享

现状
memory_entries 表没有 agent_name 列——sqlite 档下所有 Agent 实际共用一份记忆，与「记忆跟 Agent 走」的既定设计不符（代码核查发现的存量缺口）。
015 后
补列修复（手工 DDL），存量无主数据归入全局占位并给可读迁移说明；修复后 sqlite 档与 markdown 档的 per-Agent 语义一致。

价值：修掉隔离性缺口；同时这也是分布式共享 DB 路径的必要前提（见 08）。

07观测与审计：记忆检索埋点对齐知识形态

现状
recall_memory 审计只有一行普通工具记录，结果是裸文本，无命中明细。
015 后
埋点结构化并与知识检索同形态：查询原文＋命中明细＋降级标记＋耗时，随 tool_invocations 落库。

价值：将来做统一检索看板（知识＋记忆）时数据现成，无需二次埋点——与 014 埋点「一次设计到位」同一原则。

08分布式就绪：五条设计约束，将来分布式零返工

现状
无约束声明；markdown 档（本地文件）在多副本下的定位不明。
015 后
写入设计约束：向量索引与记忆本体同库存储／索引是派生数据可全量重建／对账幂等（多副本同时执行收敛一致）／不引入实例内状态／markdown 档显式定位为单机档，分布式推荐 sqlite（共享 DB）或外部服务档。只写约束，本期不做分布式实现。

价值：与路线图方向 A（「记忆全外置共享 DB、实例无状态」）对齐，成本≈0；分布式改造时记忆域不需要回头改需求。

09配置归位：向量化配置升格全局段

现状
向量化配置挂在 knowledge.embedding.* 下——知识专属的名字，记忆要用就名不正言不顺。
015 后
升格为全局 embedding.provider/model 段（知识与记忆共用同一份），旧键作为兼容别名继续生效，存量配置零迁移。

价值：一套凭证一套配置；趁只有一个消费者时改名，越晚成本越高。

PART 3 / 刻意不动的零迁移、零学习成本的保证

不变项说明
核心区语义全量注入每轮 prompt、永不截断、不参与检索——名片夹还是名片夹
归档区注入策略「最近窗口」照旧推入上下文（注入管最近的，检索管相关的，两通道互补）；窗口是否收窄，等埋点数据说话
工具签名save_memory / recall_memory 名称、参数、返回形态完全不变，存量 Agent 零改动
MEMORY.md文件位置与两段结构不变，可读、可 Git、审计天然
写入哲学仍是 Agent 显式写入（不做 mem0 式自动提取/改写——显式写入信噪比高，且改写式记忆与「可审计」主张冲突；要提取式的企业走外部服务档）
审计路径工具调用照旧入 tool_invocations，只是内容更结构化

PART 4 / 评审关注点四处最值得讨论的取舍

R1 · 范围取舍（已扩大，请确认）

本期范围 = 检索升级 + 后端契约对齐 + mem0 真实跑通（维护者已拍板并入）。联调需要 docker 起 mem0 OSS + 一个 OpenAI 兼容 LLM key；契约桩测试保 CI 常绿，真实联调打 integration 标签按需跑。评审确认这个最终范围。

R2 · 已拍板：装配期拒绝，删除降维分支

调研结论：mem0 经「infer:false 原文模式＋metadata 过滤」可完整映射两区（core 原文常驻 / archival 交提炼），百炼有等价维度——「映射不了分区」是假想场景；而降维会静默破坏「核心区每轮在场」契约，比启动报错危险。故分区定为记忆后端必选能力，装配期校验、无法映射即可读拒绝。（依据 research D8；mem0 filter 的版本性 bug 列为 016 联调验证点）

R3 · 三路等权

语义/关键词/时间三路在融合中等权、无调参口。建议先等权＋埋点观察，有数据再议——认可与否？

R4 · 兼容承诺的唯一例外

关键词大小写统一是对「未配置则行为零变化」承诺的唯一例外（修的是两档不一致的存量 bug）——确认各方接受。
