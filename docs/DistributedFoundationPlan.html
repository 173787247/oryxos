验收 Demo（版本完成的定义）——K8s 双副本：
  1. 滚动升级中进行的会话不断线
  2. 定时任务恰好执行一次
  3. 并发多用户 / 同用户连发消息：无丢失、无重复、无报错
  4. 副本 A 创建的 Agent 在副本 B 秒级可见、可对话

01目标与边界

双目标：容错（挂一个副本不断服务、滚动升级用户无感）与承载（用户量上来后加副本就能摊——这是分布式更日常的价值，不只是灾备）。

明确不做：消息队列、K8s Operator、跨请求 Provider 健康记忆、文件全面入库（留 v1.0 租户模型定型后）、智能路由。

02现状盘点：有状态且单点的全量清单

按「状态在哪、多副本下会发生什么」盘点全部已有功能，结论三分：

DB 态——基本就绪，换库即好

会话 / 审计三表 / 记忆(sqlite 档) / 知识 chunk / 调度状态 / 执行历史 / providers / notify / 策略全在 DB。两个关键机制 day one 已按跨进程语义设计：会话乐观锁（saveIfUnchanged 条件更新）与向量层库无关（BLOB + Java 余弦——换 PostgreSQL 零向量迁移，pgvector 从必答降为可选优化）。

内存态——两处要改，其余是可重建缓存

  • sessionLocks 进程锁：跨副本语义要重建（→ 025 核心）
  • IM 长连接（已实证，2026-09-02 官方文档 + SDK 反编译 + 代码核查）：三平台三种语义——飞书集群模式随机投一条（≤50 连接）但有 3s 超时重推且可能落到另一副本；钉钉 Stream 同为随机投一；企微单连接互踢（新连接踢旧连接，多副本不能都建连 → 需租约属主）。存量坑实锤：017 的 MessageDeduplicator 是进程内 Map，多副本下重推去重失效 → 去重下沉 DB 幂等回执表（→ 025）

文件态——第三战场（本次盘点新增）

  • Agent 工作区：共享卷可解，但 WorkspaceWatcher 的 inotify 在共享存储上不可靠——热更新感知要换机制
  • 知识库源文件：共享卷 + 索引任务跨副本认领
  • 记忆 markdown 档：并发追加写丢数据——裁决为单机档
  • 启动期一次性逻辑（迁移/播种）：多副本并发启动安全

瓶颈链（用的人多了，按序炸哪）

① SQLite 单写者锁（几百写 TPS 天花板）　→ 024 解决
② 同 session 跨副本并发（单机排队退化为多机报错）　→ 025 解决
③ LLM Provider 配额（加副本不增配额；023 fallback 缓冲）　→ 运营面，如实声明
④ 计算层（虚拟线程挂 IO 等待，单副本可承数万并发）　→ 最不慌

03参考实现调研：StaffDeck / AgentScope Java

对两个项目做了逐文件调研（八个维度，证据到文件:行号），交叉结论：

核心发现：两家殊途同归于「turn 租约互斥」，都没做粘性路由

StaffDeckAgentScope Java
形态刻意单实例（文件锁拒绝第二进程），但租约模型完整无状态多副本；官方明确「不 sticky-route，只互斥」，sessionAffinity 是死代码
会话归属turn 租约表：唯一约束即互斥，执行期归属、执行完释放同款（TTL 90s、TTL/3 心跳续租），turn 间无归属、每轮从 store 重载
副本挂了租约过期 → 终结该轮 + 保留检查点 + 告知用户重发，不自动重放租约过期 → 释放 + 置 idle，下一条消息任意副本自然接管

采纳口径：绑定的是「正在执行的一轮」（租约 + 续租 fencing 硬互斥），不是「会话永久归属副本」——状态在共享 DB，永久归属换不来正确性收益，却要付路由/转发/再平衡整套复杂度。副本挂 → 租约过期 → 下一条消息落到哪个健康副本哪个接管：零协调者、秒级、零数据丢失。LB 层 IP-hash 粘性可作缓存优化叠加，不承担正确性。

吸收 — StaffDeck 的租约工艺

  • 统一并发原语：「唯一约束即互斥 + 插入失败抢过期的 + 条件 UPDATE rowcount==1」——session turn / 定时任务 / 知识索引 / IM 事件全用同一套
  • 续租带 owner fencing、失败即终止执行——防脑裂核心
  • 双层锁：进程内快路径 + DB 慢路径（OryxOS 的 sessionLocks 恰好已是一半）
  • 不自动重放：崩溃轮次终结为失败、执行历史留痕、告知用户重发、标记「副作用结果未知」
  • 回收多证据交叉验证；IM 事件幂等回执表

吸收 — AgentScope Java 的架构骨架

  • 总路线验证：「无状态副本 + 外置状态 + turn 互斥 + CAS 兜底」——OryxOS 现状与之同构
  • 协调面接口化：JDBC 租约为默认实现（零新增件，同库多副本即可跑），Redis 作为可插拔第二实现（规模档插件）
  • 误配 fail-fast：分布式档 + 单机型组件 → 启动直接拒绝
  • 「权威落库 + seq 游标」事件流分层——记为 v0.5 方案储备

避开 — 两家的已知坑

坑出处OryxOS 对策
文件锁承担正确性（跨机器静默失效）StaffDeck正确性只依赖 DB 租约
startup 全量抹除活跃行（多副本互杀）StaffDeck回收只认过期租约，永无 startup 分支
lease_owner 随机 ID 不可路由StaffDeckowner 写成 instanceId@epoch
租约参数硬编码、零指标StaffDeck配置化 + 租约指标挂 023 MetricsRecorder
锁不可达 30s 静默降级为进程锁（脑裂后门）AgentScopefail-closed：拒绝服务优于错误服务
fencing token 发了但客户端不用 / 锁无续期看门狗AgentScopefencing 贯穿续租与终止；心跳续租必选

024 可插拔存储

  • Flyway 接管迁移，收编五个手工 SchemaUpgrade（Flyway 自带迁移锁顺带解决多副本并发启动）
  • PostgreSQL 支持：方言/迁移脚本双轨（14 处 AUTOINCREMENT 等专有面清理）
  • SQLite 保持默认零配置档——单机五分钟上手是产品资产，PG 是可选档不是升级
  • 已知风险：开发环境 PG 自动化测试路径受限，plan 阶段先行验证（见问题 6）

025 session 归属与多副本正确性

  • turn 租约表：唯一约束即互斥、插入失败抢过期的、CAS 认领；owner=instanceId@epoch；续租 fencing 失败即中止；过期惰性接管 + 不重放
  • 双层锁：进程内快路径 + DB 租约兜底；定时/索引/IM 事件同一套认领原语 + 幂等去重
  • instances 心跳表（落库不落内存）；协调面接口化（JDBC 默认 / Redis 可插拔）
  • 租约配置化 + 指标；分布式误配 fail-fast；IM 渠道多副本定案（已实证）：飞书/钉钉随机投一无需属主、去重下沉 DB 回执表（替换进程内 Map）；企微互踢 → 渠道连接租约属主（持租约副本建连、过期即接管——025 租约模型的直接用例）

026 文件面分布式

  • Agent 工作区 / 知识库源文件走共享卷（其 HA 是企业存储设施职责——与「DB 的 HA 交给 DBA」同一边界哲学）
  • watcher 从 inotify 改为 DB 版本号通知（DB 作变更通知总线、文件作内容载体，仍零新增件）
  • 知识索引任务 DB 原子认领（复用 025 原语）；markdown 记忆档裁决为单机档（误配 fail-fast）

027 容器交付

  • 官方镜像 + Helm Chart + 探针；主密钥接 K8s Secret（022 环境变量档零改动）；共享卷挂载编排
  • OpenTelemetry tracing 导出（021 内生 trace 的导出面）；验收 Demo 四条在此闭环

05差异化立足点

  • 对 Dify / RAGFlow（Postgres+Redis+Celery+向量库多件套）：OryxOS 默认一个共享 DB 就能多副本；Redis 是规模档可选插件而非必答
  • 对 kagent（CNCF，K8s-native）：不绑 K8s——裸机 / VM / K8s 都是一等部署形态，Helm 是兼容而非归顺
  • 对 AgentScope Java 自身：其锁语义（可降级/无 fencing 落地/无续期）与消息层停在「能跑」水平——OryxOS 按企业底座标准把这几块做对

06开放问题（邀请重点拍砖）

Q1 turn 租约的 TTL 策略

参考值：StaffDeck 900s 固定 / AgentScope 90s+心跳续租。OryxOS 单轮含多次 LLM 往返（长的分钟级），倾向「短 TTL（60~90s）+ 心跳续租」——是否认可？

Q0 （已闭环）IM 长连接多副本行为

原"未实证"项已证实：飞书/钉钉随机投一、企微单连接互踢；结论已并入 025 范围（DB 幂等回执 + 企微连接属主租约），无需再评审。

Q2 崩溃轮次的用户体验

不重放 + 告知重发是底线；是否需要在 IM 渠道主动推一条「刚才那轮中断了请重发」（StaffDeck 做了）？

Q3 MySQL 的优先级

建议 v0.4 只做 PostgreSQL（企业开源部署主流 + advisory lock 等能力更全），MySQL 视需求后补——是否接受？

Q4 共享卷的支持矩阵

NFS 语义参差。我们只依赖「读写可见性 + rename 原子性」、不依赖文件锁——文档如何声明支持矩阵？

Q5 Redis 插件的启动时机

接口留缝 v0.4 落；Redis 实现是 v0.4 内做完，还是留待真实规模需求触发（倾向后者，YAGNI）？

Q6 024 的 PG 测试策略

开发/CI 环境镜像受限。候选：宿主机 PG 服务 / 嵌入式 PG 二进制 / 门禁内 SQLite + 发布前 PG 真机清单——需要定一个。
