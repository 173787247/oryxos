验收 Demo（版本完成的定义）——K8s 双副本：
  1. 滚动升级中进行的会话不断线
  2. 定时任务恰好执行一次
  3. 并发多用户 / 同用户连发消息：无丢失、无重复、无报错
  4. 副本 A 创建的 Agent 在副本 B 秒级可见、可对话

01目标与边界

双目标：容错（挂一个副本不断服务、滚动升级用户无感）与承载（用户量上来后加副本就能摊——这是分布式更日常的价值，不只是灾备）。

明确不做：消息队列、K8s Operator、跨请求 Provider 健康记忆、文件全面入库（留 v1.0 租户模型定型后）、智能路由。

02现状盘点：有状态且单点的全量清单

按「状态在哪、多副本下会发生什么」盘点全部已有功能，结论三分：

DB 态——基本就绪，换库即好

会话 / 审计三表 / 记忆(sqlite 档) / 知识 chunk / 调度状态 / 执行历史 / providers / notify / 策略全在 DB。两个关键机制 day one 已按跨进程语义设计：会话乐观锁（saveIfUnchanged 条件更新）与向量层库无关（BLOB + Java 余弦——换 PostgreSQL 零向量迁移，pgvector 从必答降为可选优化）。

内存态——两处要改，其余是可重建缓存

  • sessionLocks 进程锁：跨副本语义要重建（→ 026 核心）
  • IM 长连接（已实证，2026-09-02 官方文档 + SDK 反编译 + 代码核查）：三平台三种语义——飞书集群模式随机投一条（≤50 连接）但有 3s 超时重推且可能落到另一副本；钉钉 Stream 同为随机投一；企微单连接互踢（新连接踢旧连接，多副本不能都建连 → 需租约属主）。存量坑实锤：017 的 MessageDeduplicator 是进程内 Map，多副本下重推去重失效 → 去重下沉 DB 幂等回执表（→ 026）

文件态——第三战场（本次盘点新增）

  • Agent 工作区：共享卷可解，但 WorkspaceWatcher 的 inotify 在共享存储上不可靠——热更新感知要换机制
  • 知识库源文件：共享卷 + 索引任务跨副本认领
  • 记忆 markdown 档：并发追加写丢数据——裁决为单机档
  • 启动期一次性逻辑（迁移/播种）：多副本并发启动安全

瓶颈链（用的人多了，按序炸哪）

① SQLite 单写者锁（几百写 TPS 天花板）　→ 025 解决
② 同 session 跨副本并发（单机排队退化为多机报错）　→ 026 解决
③ LLM Provider 配额（加副本不增配额；023 fallback 缓冲）　→ 运营面，如实声明
④ 计算层（虚拟线程挂 IO 等待，单副本可承数万并发）　→ 最不慌

03参考实现调研：StaffDeck / AgentScope Java

对两个项目做了逐文件调研（八个维度，证据到文件:行号），交叉结论：

核心发现：两家殊途同归于「turn 租约互斥」，都没做粘性路由

StaffDeckAgentScope Java
形态刻意单实例（文件锁拒绝第二进程），但租约模型完整无状态多副本；官方明确「不 sticky-route，只互斥」，sessionAffinity 是死代码
会话归属turn 租约表：唯一约束即互斥，执行期归属、执行完释放同款（TTL 90s、TTL/3 心跳续租），turn 间无归属、每轮从 store 重载
副本挂了租约过期 → 终结该轮 + 保留检查点 + 告知用户重发，不自动重放租约过期 → 释放 + 置 idle，下一条消息任意副本自然接管

采纳口径：绑定的是「正在执行的一轮」（租约 + 续租 fencing 硬互斥），不是「会话永久归属副本」——状态在共享 DB，永久归属换不来正确性收益，却要付路由/转发/再平衡整套复杂度。副本挂 → 租约过期 → 下一条消息落到哪个健康副本哪个接管：零协调者、秒级、零数据丢失。LB 层 IP-hash 粘性可作缓存优化叠加，不承担正确性。

吸收 — StaffDeck 的租约工艺

  • 统一并发原语：「唯一约束即互斥 + 插入失败抢过期的 + 条件 UPDATE rowcount==1」——session turn / 定时任务 / 知识索引 / IM 事件全用同一套
  • 续租带 owner fencing、失败即终止执行——防脑裂核心
  • 双层锁：进程内快路径 + DB 慢路径（OryxOS 的 sessionLocks 恰好已是一半）
  • 不自动重放：崩溃轮次终结为失败、执行历史留痕、告知用户重发、标记「副作用结果未知」
  • 回收多证据交叉验证；IM 事件幂等回执表

吸收 — AgentScope Java 的架构骨架

  • 总路线验证：「无状态副本 + 外置状态 + turn 互斥 + CAS 兜底」——OryxOS 现状与之同构
  • 协调面接口化：JDBC 租约为默认实现（零新增件，同库多副本即可跑），Redis 作为可插拔第二实现（规模档插件）
  • 误配 fail-fast：分布式档 + 单机型组件 → 启动直接拒绝
  • 「权威落库 + seq 游标」事件流分层——记为 v0.5 方案储备

025 可插拔存储

解决什么问题（三个，都能演示出坏行为）：

  • 多副本没有共同事实源——SQLite 是嵌入式单文件库，放 NFS 共享官方明确锁不可靠会坏库；今天起两个副本，连「都看到同一批会话」的前提都不存在。这是 026/027 的物理前提，必须第一刀
  • 单机写并发天花板——SQLite 单写者（WAL 仅读写并行），每轮对话写 5+ 行；几十并发用户即撞写锁（busy_timeout: 5000 是已在吃止痛药的证据）
  • 表结构演进的债在指数化——五个手工 SchemaUpgrade 类是 SQLite ALTER 弱的补偿；两种库后每次加列要手写两套幂等方言，且多副本并发启动会同时跑迁移

怎么解：Flyway 收编（schema.sql 转 baseline、五个升级类转版本化脚本后删除；history 表 + 内建启动锁一并解决并发启动）；db/migration/{sqlite,postgres}/ vendor 双轨（14 处 AUTOINCREMENT 等专有面清理）；SQLite 保持默认零配置档。为什么不是别的：hibernate 自动迁移宪法明令禁止；Liquibase 的 XML 层无收益，Flyway 是宪法预留的口。

026 session 归属与多副本正确性

解决什么问题（六个，每个都是双副本一跑就翻车的具体场景）：

  • ① 同会话并发消息落两副本 → 乐观锁冲突 → 用户随机看到「处理失败」（单机的排队退化为报错）
  • ② 每副本的调度器都到点开火 → 客户收到两封日报
  • ③ 飞书 3s 超时重推落到另一副本 → 进程内去重 Map 失效 → 用户收到两条回答（已实证）
  • ④ 企微单连接互踢 → 两副本循环踢连接、消息丢在换连缝里（已实证）
  • ⑤ 副本挂了，处理中的轮次悬空 → 用户永远等不到回复也没有提示
  • ⑥ 哪些副本活着、谁在处理什么——运维无处可查

怎么解：一条 CAS 认领原语（「唯一约束即互斥 + 插入失败抢过期的 + 条件 UPDATE rowcount==1」）套五个场景——① session_turn_leases turn 租约（owner=instanceId@epoch，心跳续租带 fencing、失败即中止；本副本内保留 sessionLocks 快路径）；② scheduled_tasks 同款 CAS 认领；③ 去重下沉 channel_event_receipts 回执表；④ channel_leases 连接属主（持租约副本才建企微连接，过期即接管；飞书/钉钉随机投一无需属主）；⑤ 回收扫描只认过期租约（绝无 startup 全量抹除）→ 该轮标失败 + 告知重发、不重放；⑥ instances 心跳表。协调面收敛在一个接口后：JDBC 默认（零新增件）、Redis 可插拔（规模档）。为什么不是别的：粘性路由+转发被两个参考项目双双否定（状态在共享 DB，归属换不来正确性只换来路由层）；纯 advisory lock 给不了「有身份有期限」的租约语义（企微属主、崩溃收尾、可观测都需要它）。

026 补充 · 同一 session 的消息到底谁处理？

关键认知：session 不归属副本，归属的只是「正在执行的这一轮」。对话连续性由 DB 会话历史保证（处理方进锁后重读最新快照，day one 设计），不靠任何副本的内存。

消息① → 飞书随机投给副本 A → A 认领 session-X 租约 ✔ → 读历史·跑 ReAct·写回 → 回复① → 释放
消息② → 飞书随机投给副本 B → B 认领租约 ✔ → 读历史（含 A 刚写的①）→ 上下文完整 → 回复②

三个边界：时间重叠（①在 A 处理中、②落到 B）→ B 认领失败短轮询等待，A 释放后 B 接着处理——与单机排队语义等价，只是队伍横跨副本；超时重推跨副本 → 回执表判重丢弃，用户只收一条；A 处理中挂掉 → 租约过期、该轮标失败并提示重发，用户下一条消息落到哪个健康副本谁接管——接管的是下一轮执行权，不是进行中的执行（不重放）。

026 补充 · 消息量大了性能怎么保障？

  • 租约开销账：每轮仅增约 5 次单行小写（去重 1 + 认领 1 + 续租 ~2 + 释放 1），对比该轮既有的 5+ 次写与几十 KB 会话覆写是零头；LLM 往返（秒~分钟级）才是时间大头，DB 毫秒级操作在关键路径占比 <1%。估算：1000 活跃用户 ×1 条/分钟 ≈ 17 msg/s → 含租约约 170 写/s，PG 单实例数千写/s 余量十倍以上
  • 串行只在同 session 内（对话语义必须，与今天单机排队一致）；session 间零竞争、全并行——并发承载靠这个，加副本即加并行度
  • 群聊（消息量最大的场景）天然绕开竞争：017 既有设计群聊问答走无状态独立会话（feishu-group:<uuid>），几十人同时 @bot 是几十个互不相干的会话，零租约竞争
  • 真瓶颈位次：LLM Provider 配额（运营面，023 fallback 分摊）≫ 会话历史整段覆写（既有行为，max_history_turns 控制，PG TOAST 前无忧）≫ 协调面（万级 msg/s 才需换 Redis 实现——接口留缝正为此）
  • 验收锚点：026 的 SC 含压测——双副本 + PG 下「N 并发独立会话 + 单会话连发」两种负载，断言吞吐随副本数线性、租约开销在 p99 不可见

027 文件面分布式

解决什么问题（四个）：① 副本 A 建的 Agent 在 B 的盘上不存在 → B 报「Agent 不存在」；② 挂共享卷后 inotify 在 NFS 上不产生事件 → B 的注册表永远陈旧、改配置不生效；③ 知识索引流水线两副本都捡 → 重复索引/generation 互相覆盖；④ markdown 记忆档并发追加 → 经典丢写。

怎么解：文件本体走共享卷（只依赖「读写可见 + rename 原子」，不依赖文件锁——StaffDeck 教训）；②变更感知换总线——管理台写路径在 DB 记工作区版本号、各副本秒级轮询（DB 作通知总线、文件作内容载体，单机档保留 watcher 零回归）；③索引 CAS 认领 + 超时回退（复用 026 原语，零新机制）；④markdown 档裁决为单机档，分布式档启动 fail-fast 拒绝并指明 DB 记忆后端。为什么不是别的：文件全面入库动「目录=Agent」接口承诺根基 + 单机直改文件的双模式难题，留 v1.0 租户定型时裁决。

028 容器交付

解决什么问题（三个）：① 企业没有标准部署入口（无镜像无 Chart，每客户手工装机）；② 前三刀能力没有验收载体——且滚动升级不断线不是免费的（需要 readiness 就绪门控 + preStop 优雅期让在途轮次收尾）；③ 021 内生 trace 接不进客户已有的 Jaeger/Tempo 观测栈。

怎么解：多阶段 Dockerfile（精简 JRE）+ Helm Chart（Deployment 副本可调、DB 连接与 ORYXOS_MASTER_KEY 走 K8s Secret——022 环境变量档零改动、.oryxos PVC 挂载、liveness/readiness 用既有 actuator、preStop 对接优雅停机与租约释放）；OTel 导出以 021 traceId 为 trace 上下文、span 打在既有审计点位（审计供精确回放、OTel 供跨系统链路，同源不同面）；验收 Demo 四条 + 性能锚点在真 K8s 走查落卷。

因果链收拢：025 给多副本一个能共享、扛得住写并发的事实源；026 用一条租约原语把六种「双副本一跑就翻车」的场景全部收口；027 让文件形态的资产在副本间可见、可感知、不打架；028 把这一切装进企业一条命令部署的载体并闭环验收。

05差异化立足点

  • 对 Dify / RAGFlow（Postgres+Redis+Celery+向量库多件套）：OryxOS 默认一个共享 DB 就能多副本；Redis 是规模档可选插件而非必答
  • 对 kagent（CNCF，K8s-native）：不绑 K8s——裸机 / VM / K8s 都是一等部署形态，Helm 是兼容而非归顺
  • 对 AgentScope Java 自身：其锁语义（可降级/无 fencing 落地/无续期）与消息层停在「能跑」水平——OryxOS 按企业底座标准把这几块做对
