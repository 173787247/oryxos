# Feature Specification: Health 端点暴露版本信息（Health Version Info）

**Feature Branch**: `052-health-version`

**Created**: 2026-10-14

**Status**: Draft

**Input**: User description: "给现有的 GET /api/v1/health 健康检查端点的返回体里，新增版本信息字段：version（当前 OryxOS 版本号，如 0.x.y）和 build（构建标识，如 git short sha / 构建时间）。目的是让运维和客户端一眼看出线上跑的是哪个版本。保持向后兼容：现有字段不动，只做纯增量加字段。不需要鉴权变化，不新增端点。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运维确认线上版本（Priority: P1）

运维/SRE 在排障或发布核验时，访问健康检查端点，就能直接看到当前实例运行的 OryxOS 版本号与构建标识，无需登录机器查看 jar 名或翻日志。

**Why this priority**: 这是本特性的核心价值——"一眼看出线上跑的是哪个版本"。缺了它，排障时无法快速确认版本是否发布成功、是否存在多实例版本不一致。

**Independent Test**: 单独实现本故事即可交付价值——对一个运行中的实例请求健康检查端点，返回体中出现可读的 `version` 和 `build` 字段即验证通过。

**Acceptance Scenarios**:

1. **Given** 一个正常运行的 OryxOS 实例，**When** 请求健康检查端点，**Then** 返回体在原有字段之外，额外包含 `version`（当前发布版本号）和 `build`（构建标识）两个字段。
2. **Given** 实例由某次确定的构建部署，**When** 多次请求健康检查端点，**Then** `version` 与 `build` 的取值在该实例生命周期内保持稳定一致。

---

### User Story 2 - 现有健康检查调用方不受影响（Priority: P1）

已有的监控探针、K8s liveness/readiness 探针、负载均衡健康检查等调用方，在本特性上线后行为不变——它们原本读取的字段（如健康状态）位置与语义都不变。

**Why this priority**: 向后兼容是硬约束。健康检查被大量自动化组件依赖，一旦破坏现有字段会直接引发探针误判、实例被误杀。与 P1 故事同级。

**Independent Test**: 用上线前的调用方契约（原有字段集合）去校验上线后的返回体，所有原字段仍存在且语义不变即通过。

**Acceptance Scenarios**:

1. **Given** 一个只读取原有健康状态字段的调用方，**When** 本特性上线后请求健康检查端点，**Then** 该调用方读取的原字段依旧存在、取值语义不变，调用方无需任何改动。
2. **Given** 健康检查端点当前的鉴权要求，**When** 本特性上线，**Then** 该端点的可访问性与鉴权要求保持不变（不新增鉴权门槛、不放宽现有要求）。

### Edge Cases

- 当版本号/构建标识在当前运行环境中无法确定时（例如从源码直接运行、未经正式构建），返回体仍应给出明确、可读的占位取值（如 `unknown` / `dev`），而不是缺字段、报错或返回 null，以免调用方解析失败。
- 当健康检查端点本身处于非健康状态时，版本信息字段应尽量仍然可读（版本信息与运行是否健康相互独立，不应因不健康而丢失版本标识）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 健康检查端点的返回体 MUST 在保留全部现有字段的前提下，新增 `version` 字段，表示当前实例对应的 OryxOS 发布版本号。
- **FR-002**: 健康检查端点的返回体 MUST 新增 `build` 字段，表示当前实例对应的构建标识（用于区分同一版本号下的不同构建）。
- **FR-003**: 系统 MUST 保证 `version` 与 `build` 在单个实例生命周期内取值稳定（同一次部署多次查询结果一致）。
- **FR-004**: 当版本号或构建标识无法确定时，系统 MUST 以明确的占位取值填充对应字段，而非缺字段、null 或报错。
- **FR-005**: 本特性 MUST 不改变健康检查端点的路径、原有字段的名称与语义、HTTP 状态语义及鉴权要求（纯增量、向后兼容）。
- **FR-006**: 本特性 MUST NOT 新增任何端点，仅在既有健康检查端点上扩展返回体。

### Key Entities *(include if feature involves data)*

- **版本信息（Version Info）**: 描述当前运行实例的身份标识，包含两个属性——`version`（面向人阅读的发布版本号）与 `build`（区分同版本不同构建的标识）。该信息在实例启动时即确定，运行期内只读、不变。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运维在不登录宿主机、不查日志的前提下，仅通过一次健康检查请求即可确认实例版本，确认动作可在 10 秒内完成。
- **SC-002**: 本特性上线后，现有健康检查调用方（监控探针、K8s 探针等）零改动、零告警，原有字段 100% 保持。
- **SC-003**: 对同一部署实例的任意多次查询，`version` 与 `build` 取值 100% 一致。
- **SC-004**: 在无法确定版本/构建的环境中查询，返回体 100% 仍为可解析结构（字段存在且为占位值），调用方解析不报错。

## Assumptions

- 版本号以项目已有的发布版本号为准（与构建产物版本保持同源），`build` 取构建期可获得的唯一标识（如 git short sha 或构建时间），具体取值来源在规划阶段决定，不影响本规格。
- 复用现有的健康检查端点与其返回体结构，不引入新的对外契约形态。
- 版本信息为公开的非敏感信息，向健康检查调用方暴露不构成安全/合规问题（沿用该端点当前的鉴权策略，不单独收紧或放宽）。
- 本特性范围限定为"读取并展示"版本信息，不包含版本比对、升级提示、多实例版本一致性校验等衍生能力（如需，另立特性）。
