## Implementation Strategy

### MVP First（US1 Only）

1. Phase 1 + Phase 2（T001~T015）：表 + 主体 + 决策点 + 强制点就绪
2. Phase 3（T016~T027）：角色解析、路径映射、两扇 Filter 接线、CLI 赋权、E2E
3. **STOP and VALIDATE**: quickstart V2 + V4 走通即可演示（三档 200/403 差异 + Key 上限）
4. US2（拒绝留痕与可见性）、US3（启动校验与零回归锚点）依次叠加，各自 checkpoint 独立验收

### 关键依赖提醒

- T021 是 MVP 的胜负手之一：没有它，矩阵里 EDITOR/ADMIN 的差异不会在真实请求上生效（当前实现只做 `READ_WORKSPACE` 基线判定），US1 的验收场景无法成立——若 maintainer 对路径映射边界（spec.md §Clarifications 第 4 条）尚未裁决，先落「按 contracts §4 全表 + 未登记 fail-closed」的版本，把边界分歧收敛在映射表一处。
- T016~T018 是 MVP 的另一个胜负手：角色不落库时（当前 `default-user-roles=ADMIN`）**所有管理台账号都是 ADMIN**，VIEWER/EDITOR 两档只在单测里存在；落库与「默认档收紧为空 + 无 ADMIN 拒启」必须同批做，缺一就会在「锁死管理台」与「人人 ADMIN」之间二选一（spec.md §Clarifications「待补」条）。
- T001/T002 的 V8 版本号在实现前需再次确认 `db/migration/{sqlite,postgresql}/` 仍无 V8（026 的 V6 撞号重编号是前车之鉴）。
- 安全红线贯穿全部任务：审计只记主体标识与理由，**绝不落 API Key 明文**；`enabled=false` 时任何代码路径都不得产生 403 或审计写入。
