# Feature Specification: 文件面分布式（File Plane Distribution）

**Feature Branch**: `027-file-plane`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "文件面分布式（027-file-plane）：v0.4 分布式底座第三刀。025 给了共同事实源（共享 PG）、026 给了行为正确性（CAS 认领原语），但文件形态的资产（Agent 目录、Skill 库、知识库源文件、markdown 记忆）仍各副本各一份盘——四个双副本一跑就翻车的具体场景：①副本 A 建的 Agent 在 B 的盘上不存在→B 报「Agent 不存在」；②挂共享卷后 inotify 在 NFS 上不产生事件→B 的注册表永远陈旧、管理台改配置不生效；③知识索引流水线两副本都捡→重复索引/generation 互相覆盖；④markdown 记忆档并发追加→经典丢写。解法（出处 docs/DistributedFoundationPlan.html §04，已经维护者评审）：文件本体走共享卷，只依赖「读写可见性 + rename 原子性」、不依赖文件锁；变更感知换总线——管理台写路径在 DB 记工作区版本号、各副本秒级轮询，DB 作通知总线、文件作内容载体，单机档保留既有 watcher 零回归；知识索引 CAS 认领 + 超时回退，复用 026 CoordinationStore 原语零新机制；markdown 记忆后端裁决为单机档专属，分布式档启动 fail-fast 拒绝并指明 DB 记忆后端。零破坏：单机档零配置零行为变化。不做：文件全面入库、事件流分层（v0.5 储备）、Redis 总线。"

> 前置：025-pluggable-storage（共享 PG 事实源）与 026-session-ownership（CAS 认领原语、误配 fail-fast 框架、instances 心跳）已交付。本刀让文件形态的资产在副本间**可见、可感知、不打架**。规划出处：docs/DistributedFoundationPlan.html §04（四场景与裁决已经维护者与评审对齐）。场景④（markdown 记忆并发丢写）的裁决——分布式档拒启 markdown 记忆——已由 026 的启动检查交付，本刀保持回归并把文件面新增的误配组合并入同一框架。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 文件资产多副本一致可见与秒级生效（Priority: P1）

企业双副本部署（共享数据库 + 共享卷承载 `.oryxos/` 工作区）。管理员在管理台（或 CLI/API，请求可能落到任一副本）创建一个新 Agent、修改某 Agent 的配置或指令正文、绑定/解绑 Skill、或新增自定义人格。无论写操作发生在哪个副本：其他副本在**秒级**感知到变更并重载对应注册表——用户下一条消息不管落到哪个副本，看到的都是最新的 Agent 定义；不存在「A 建的 Agent 在 B 上报不存在」「改了配置在另一副本不生效」。

**Why this priority**: 这是文件面「多副本成立与否」的判据——没有它，双副本下管理台形同抽奖：写操作落在哪个副本，就只有那个副本认账。四个翻车场景中的 ①② 由此收口。

**Independent Test**: 双副本连同一共享库与共享工作区目录，经副本 A 的管理 API 创建/修改/删除 Agent 与 Skill 绑定，断言副本 B 在时限内列表与调用结果均反映变更；单机档同样操作走既有 watcher 路径，全量既有测试零回归。

**Acceptance Scenarios**:

1. **Given** 双副本共享工作区，**When** 经副本 A 创建新 Agent，**Then** 副本 B 在秒级时限内的 Agent 列表含该 Agent，且经 B 调用该 Agent 正常应答
2. **Given** 某 Agent 已在两副本可用，**When** 经副本 A 修改其配置（如 provider、指令正文）或 Skill 绑定，**Then** 副本 B 在秒级时限内以新配置处理下一条消息
3. **Given** 经副本 A 删除某 Agent，**When** 副本 B 感知变更后，**Then** B 上该 Agent 不可再被调用，列表同步消失
4. **Given** 单机单副本部署（默认档），**When** 同样的创建/修改/删除操作，**Then** 行为与本特性交付前完全一致（watcher 感知，零配置零变化）
5. **Given** 集群档运行中某副本重启，**When** 重启完成，**Then** 该副本按当前工作区内容重建注册表，与另一副本一致（不依赖错过的「事件」）

---

### User Story 2 - 知识索引流水线多副本恰好执行一次（Priority: P2）

管理员上传知识库文件或触发索引重建。双副本都能看到共享卷上的源文件、都可能被触发——系统必须保证同一次索引构建**只有一个副本实际执行**：不重复消耗解析/向量化成本，产出的索引代次（generation）不互相覆盖；执行副本中途挂掉时，等待窗口过后另一副本可接管重建，知识检索始终返回一致的已提交代次。

**Why this priority**: 场景③ 的收口——重复索引浪费的是真金白银的 embedding 调用，代次互覆则直接损坏检索正确性；依赖 US1 的变更感知与 026 的认领原语先立起来。

**Independent Test**: 双副本下同时触发同一知识库的索引构建，断言解析/向量化恰好执行一份、提交代次唯一且检索一致；kill 执行副本，断言超时窗口后另一副本接管完成。

**Acceptance Scenarios**:

1. **Given** 双副本且同一知识库的索引构建被同时触发，**When** 构建发生，**Then** 恰好一个副本执行完整流水线，另一副本不重复解析/向量化
2. **Given** 执行索引的副本在构建中途被杀，**When** 认领超时窗口过后，**Then** 另一副本可接管重建，最终提交的代次唯一且完整
3. **Given** 构建进行中，**When** 任一副本处理知识检索请求，**Then** 返回的是最近一次**已提交**代次的结果（构建中代次不可见）
4. **Given** 单机档，**When** 同样的构建与检索场景，**Then** 行为与既有零差异（无认领写入）
5. **Given** 副本 A 正在重建某知识库索引，**When** 副本 B 同时经上传接口向同一知识库导入新文档，**Then** 导入不会落在将被淘汰的旧代次上静默丢失——导入与重建经同一认领机制协调（排队或明确提示重建进行中），重建完成后该文档最终可检索

### User Story 3 - 共享卷部署的行为边界清晰可依（Priority: P3）

运维在 NFS / K8s RWX PVC 等共享卷上部署 `.oryxos/` 工作区。产品文档明确声明对卷的**最小依赖**（读写可见性 + rename 原子性）与明确**不依赖**的能力（跨机器文件锁、inotify 事件），并给出主流卷类型的支持矩阵与挂载建议；文件写入路径全部采用「临时文件 + 原子改名」方式落盘，共享卷上不产生半写状态的文件。误配组合（集群档 + 单机型文件后端）沿 026 框架启动即拒并指明替代。

**Why this priority**: NFS 语义参差是文件面分布式最大的现场风险；把依赖面收到最小并如实声明，是「装在企业自己基础设施上」承诺的一部分。属于文档与写入纪律，独立于 US1/US2 交付。

**Independent Test**: 审查全部工作区写路径均为原子改名落盘（含并发写同一文件时不出现混合内容）；文档含支持矩阵；误配组合启动被拒且报错指路。

**Acceptance Scenarios**:

1. **Given** 任一管理写路径（Agent/Skill/人格/知识源文件），**When** 写入过程中进程被杀，**Then** 共享卷上要么是旧完整内容要么是新完整内容，绝无半写文件
2. **Given** 集群档 + markdown 记忆后端（或其他单机型文件后端组合），**When** 启动，**Then** 拒绝启动并明确指出应改用的后端（026 框架回归）
3. **Given** 运维查阅部署文档，**When** 选择共享卷方案，**Then** 能得到「依赖什么/不依赖什么/建议挂载参数」的明确声明

---

### Edge Cases

- 副本 B 的轮询恰好发生在副本 A 写文件与递增版本号之间：B 下一轮轮询必然追上（版本号在文件落盘**之后**递增，读到新版本号即保证能读到新内容）
- 在途轮次与注册表重载并发：正在执行的一轮继续使用其开始时的 Agent 定义快照，重载只影响后续轮次（快照式替换，不热改在途）
- NFS 客户端缓存导致 B 读到旧文件内容：依赖「close-to-open 一致性」这一 NFS 默认保证——A 关闭文件后 B 重新打开必见新内容；文档在支持矩阵中声明该要求（禁用该一致性的挂载参数不受支持）
- 版本号并发递增（两副本同时写不同 Agent）：版本号只增不减、单调递增，任何一次递增都触发全量重载对应域，两次变更都不丢
- 共享卷短暂不可达：读失败的重载保留上一份注册表快照并告警，不清空；恢复后下一轮轮询自愈
- 同名 Agent 在两副本几乎同时创建：后写者的文件内容胜（rename 原子覆盖），注册表最终一致——管理写路径不做跨副本互斥（低频人工操作，冲突概率与代价都低）[见 Assumptions]
- 时钟偏移：变更感知不依赖时间戳比较，版本号为数据库生成的单调序号
- 单机档用户直接在盘上改文件（不经管理台）：watcher 感知，行为不变；集群档绕过管理台直接改共享卷不承诺自动感知——提供手动「刷新工作区」入口（管理台/API 递增版本号触发全副本重载，复用同一总线，见 FR-011），文档声明该逃生舱用法

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有管理写路径（Agent 目录 CRUD、Skill 实体与绑定软连接、人格自定义、知识源文件上传/删除）完成文件变更后，系统 MUST 在共享事实源中递增对应域的工作区版本号（文件先落盘、版本号后递增）
- **FR-002**: 集群档下每个副本 MUST 以秒级周期轮询工作区版本号，检测到变化后重载对应域的注册表；重载采用快照式替换，不影响在途轮次（无内存注册表的域——如按需读盘的人格库——重载为 no-op，共享卷可见性已足够）
- **FR-003**: 集群档下系统 MUST NOT 依赖文件系统事件（inotify）作为变更感知手段；单机档 MUST 保留既有 watcher 行为，零配置零回归
- **FR-004**: 所有工作区文件写入 MUST 采用「同目录临时文件写全 + 原子改名」方式落盘；系统 MUST NOT 依赖跨机器文件锁保证任何正确性
- **FR-005**: 知识索引构建 MUST 经共享事实源的 CAS 认领保证同一次构建恰好一个副本执行（复用既有认领原语，不引入新机制）；认领 MUST 带超时——执行副本失联后窗口过后可被健康副本接管
- **FR-006**: 索引代次提交 MUST 条件化——只有仍持有认领的副本能提交其代次；检索始终读最近已提交代次，构建中代次对检索不可见
- **FR-007**: 误配组合（集群档 + markdown 记忆等单机型文件后端）MUST 启动即拒并指明替代后端（沿 026 fail-fast 框架；既有三组合保持回归）
- **FR-008**: 轮询周期、认领超时等参数 MUST 配置化并有安全默认值；文件面协调事件（重载次数/耗时、索引认领与接管）MUST 挂既有指标口径
- **FR-009**: 部署文档 MUST 声明共享卷支持矩阵：依赖「读写可见性（close-to-open 一致性）+ 同卷 rename 原子性」，不依赖文件锁与 inotify；给出 NFS / K8s RWX PVC 的挂载建议与不支持的配置
- **FR-010**: 单机档（cluster 缺省关闭）MUST 零配置零行为变化：不产生版本号写入、不轮询、watcher 与索引流水线行为与交付前完全一致
- **FR-011**: 集群档 MUST 提供手动「刷新工作区」入口（管理台/API）：递增全部域的工作区版本号，触发所有副本重载——供绕过管理台直接修改共享卷后的运维逃生舱使用（维护者裁决 2026-09-14）

### Key Entities *(include if feature involves data)*

- **工作区版本号（Workspace Version）**: 共享事实源中按域（agents / skills / personas / knowledge）维护的单调递增序号，附带最后更新副本与时间；是「DB 作通知总线、文件作内容载体」的总线载体
- **索引构建认领（Index Build Claim）**: 某知识库一次构建的执行权凭据——持有者、代次标识、认领时限；复用 026 认领原语的存储形态
- **索引代次（Index Generation）**: 一次完整构建产出的索引版本，具备「构建中 / 已提交」状态；检索只见已提交

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 双副本下经任一副本创建/修改/删除 Agent，另一副本在 **3 秒内**列表与调用行为均反映变更（走查 + 自动化断言）
- **SC-002**: 双副本同时触发同一知识库索引构建，解析/向量化恰好执行一份、提交代次恰好一个，两副本检索结果一致
- **SC-003**: 执行索引的副本被强杀，认领超时窗口后另一副本接管并完成构建，最终代次完整可检索
- **SC-004**: 任一工作区写路径在写入中途被杀，共享卷上无半写文件（旧完整或新完整二选一）
- **SC-005**: 集群档 + 单机型文件后端的误配组合启动被拒，报错信息指明替代方案（026 既有三组合回归 + 本刀新增组合）
- **SC-006**: 单机档全量既有测试绿；集群档空闲时文件面新增负载仅为每副本每秒常数次单行读，对共享库负载占比可忽略（<1%）
- **SC-007**: 部署文档含共享卷支持矩阵；按矩阵推荐配置在 NFS 类共享卷上完成 US1/US2 真机走查

## Assumptions

- 共享卷由运维负责供给与挂载（NFS、K8s RWX PVC 等），两副本的工作区根指向同一共享目录；卷的供给与备份不在本刀范围
- 会话、审计、凭证等结构化状态已全部在共享数据库（025/026 交付），本刀只处理文件形态资产；日志仍各副本本地
- 管理写路径是集群档文件变更的正常入口；直接改盘属运维逃生舱，不自动感知，改盘后经手动刷新入口生效（FR-011）
- 管理写操作为低频人工操作：跨副本同名并发创建不做互斥，后写胜 + 最终一致是可接受的裁决
- 轮询默认周期取 1 秒（配置化），「秒级生效」的验收口径以 SC-001 的 3 秒为准（含轮询 + 重载耗时余量）
- 变更感知覆盖 Agent/Skill/人格/知识源四个域；MEMORY.md 记忆文件不在感知范围（集群档已拒 markdown 记忆后端，DB 记忆后端无文件面）
- 不做：文件全面入库（动「一个目录 = 一个 Agent」接口承诺，留 v1.0 租户定型时裁决）、「权威落库 + seq 游标」事件流分层（v0.5 方案储备）、Redis 通知总线（DB 轮询够用，接口不为此预留新缝）
- 与下一阶段规划（wiki《成为企业级 Agent 运行底座》）的边界：本刀的「工作区版本号」是**变更通知序号**，不是资产内容版本化——历史、回滚、变更归属属治理层能力，另行规划；wiki 列出的 Git / 对象存储载体不在本刀（共享卷是 v0.4 裁决），但「DB 作通知总线、文件作内容载体」的解耦设计不排除未来更换载体
- 多租户不在本刀（v0.4 不做租户），但工作区版本号按域分键的形态不得排除未来扩展租户维度（域键 → 租户+域键）
