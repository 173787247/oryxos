## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一条命令在 K8s 上部署多副本 OryxOS（Priority: P1）

企业运维拿到发布物后，在自己的 K8s 集群上用**一条安装命令**部署 OryxOS：副本数可调（默认双副本）、数据库连接与主密钥经集群密文机制注入（不落明文）、工作区挂共享存储（027 支持矩阵姿势）、集群档自动开启且每副本自动获得唯一实例标识。安装完成后健康检查全绿，管理台/API 可用，`GET /api/v1/instances` 显示全部副本存活——025/026/027 的全部能力开箱即得，无需手写任何部署清单。

**Why this priority**: 「企业一条命令部署」是本刀的存在理由——没有标准载体，前三刀的多副本能力每客户都要手工装机，交付成本吞掉底座价值。

**Independent Test**: 本地 K8s 集群（kind/k3d 可接受）上执行安装命令起双副本，断言全部就绪、实例接口双活、管理面在任一副本可用且互相秒级可见（027 行为在 K8s 载体上成立）。

**Acceptance Scenarios**:

1. **Given** 一个可用的 K8s 集群与共享数据库，**When** 运维执行一条安装命令（仅提供数据库连接与主密钥两项密文配置），**Then** 双副本全部就绪、健康检查绿、实例列表双活
2. **Given** 已安装的发布，**When** 运维把副本数从 2 调到 3 并应用，**Then** 新副本加入后实例列表三活，无需其他配置改动
3. **Given** 双副本运行，**When** 经任一副本管理台创建 Agent，**Then** 其余副本秒级可见（027 行为在 PVC 共享卷上成立）
4. **Given** 缺少必填的数据库或主密钥配置，**When** 执行安装，**Then** 安装期即给出明确报错指出缺失项，不部署出带病实例

### User Story 2 - 滚动升级与故障不打断在途对话（Priority: P1）

运维发布新版本触发滚动升级：升级全程持续有用户请求进入——旧副本在收到终止信号后先摘流量、给在途轮次一个优雅收尾窗口（完成或按 026 口径标失败释放租约）再退出；新副本未就绪前不接流量。用户视角：滚动升级期间连续请求**零失败**。某个副本被强杀（模拟节点故障）时，探针在窗口内摘除坏副本，后续请求由健康副本接管，会话历史完整连续（026 语义在 K8s 生命周期下成立）。

**Why this priority**: 「滚动升级不断线不是免费的」——就绪门控与优雅停机若不与平台生命周期正确对接，升级窗口就是每次发布必然出现的用户可见故障；这是验收前三刀正确性的载体场景。

**Independent Test**: 升级期间以固定速率持续打请求，断言零非 2xx/429 外失败；kill 单 pod 后请求由另一副本继续服务、`instances` 窗口后反映死活。

**Acceptance Scenarios**:

1. **Given** 双副本 + 持续请求流，**When** 触发滚动升级到新版本，**Then** 全程请求零失败、升级完成后实例列表为新代副本
2. **Given** 某副本正在处理会话轮次，**When** 该副本收到终止信号，**Then** 在优雅窗口内在途轮次完成（或按既有口径标失败、租约释放），不出现悬空租约阻塞后续消息超过等待窗口
3. **Given** 双副本运行，**When** 强杀一个 pod，**Then** 健康检查在窗口内摘除它，后续请求由存活副本正常服务，被杀副本重建后自动归队
4. **Given** 副本尚未完成启动（迁移/注册表构建中），**When** 平台探测就绪，**Then** 未就绪副本不接入流量（不出现「打到半启动实例」的失败）

### User Story 3 - 内生 trace 接入企业观测栈（Priority: P2）

企业已有分布式追踪平台（Jaeger/Tempo 类，OTLP 协议）。管理员配置一个导出端点后：每轮消息处理以既有 traceId 为链路标识导出 span——LLM 调用、工具调用、Agent 执行各成 span 且父子关系正确，跨副本的同一轮次在追踪平台上呈现为一条完整链路；span 与库内审计记录同源（同 traceId 可互查）。**不配置导出端点时零开销零行为变化**（不引入常驻连接、不产生额外依赖故障面）。

**Why this priority**: 观测栈接入是企业采纳的常见门槛（第③问题），但独立于部署载体可单独交付验证，列 P2。

**Independent Test**: 配置 OTLP 端点后跑一轮带工具调用的对话，在追踪后端断言链路存在、span 层级与耗时合理、traceId 与 `llm_calls`/`tool_invocations` 表一致；不配置时全量既有测试绿且无导出尝试。

**Acceptance Scenarios**:

1. **Given** 配置了 OTLP 导出端点，**When** 用户发起一轮含工具调用的对话，**Then** 追踪平台出现该轮链路：根 span 为该轮处理，LLM 调用与工具调用为子 span，traceId 与审计表一致
2. **Given** 未配置导出端点（默认），**When** 正常使用全部功能，**Then** 行为与本特性交付前完全一致，无任何导出尝试或告警噪音
3. **Given** 导出端点不可达，**When** 正常处理消息，**Then** 主链路零影响（导出失败静默降级 + 低频告警），对话与审计照常

### User Story 4 - 前刀留账在真 K8s 环境兑现（Priority: P3）

以本刀交付的 K8s 载体补齐两笔如实记录的验收留账：**026 吞吐线性性**——独立发压端 + 双副本对比单副本，给出吞吐比值硬数字（修正 026 走查中发压端瓶颈的口径缺陷）；**027 共享卷抽查**——RWX PVC 上复跑 027 quickstart 的可见性走查（SC-007 尾巴）。结果如实落卷（含环境说明与局限）。

**Why this priority**: 债务兑现不阻塞 US1~US3 交付，但属于本刀「闭环验收」定位的一部分；环境受限时按既有口径如实记录。

**Independent Test**: 见验收卷 SC 对照——两笔留账各有独立的复测步骤与数字。

**Acceptance Scenarios**:

1. **Given** K8s 双副本 + 独立发压端 + mock provider 注入固定时延，**When** 分别对单副本与双副本压测同负载，**Then** 得到吞吐对比硬数字并落卷（线性性判定与偏差解释如实记录）
2. **Given** RWX PVC 挂载的共享工作区，**When** 复跑 027 的 A 建 B 见/改盘刷新走查，**Then** 全过并在 027 与本刀验收卷互相补记

### Edge Cases

- 单副本安装（replicas=1）：集群档照常开启（自己抢自己的，026 已验证语义自洽），不因副本数退化配置
- 数据库暂不可达时副本启动：启动失败重启退避由平台机制处理，不得进入「就绪但无库」状态（就绪判定含依赖）
- 优雅窗口内轮次未完成（长 LLM 往返）：窗口到期按既有停机口径处理，租约过期后由 026 惰性回收——不无限等待阻塞升级
- 滚动升级与 027 轮询并发：新旧版本副本短暂共存于同一共享卷/库——前向兼容迁移纪律（V6+ 只增不改）保证共存窗口安全；升级含新迁移时由 Flyway 启动锁串行化
- preStop 与企微等独连渠道：属主副本退出时释放连接租约，新属主在窗口内接管（026 语义，验收含此路径的日志抽查）
- OTel 导出与 SSE 流式（019）并存：导出不改变响应时序（异步批量导出，不在请求路径同步等待）
- 工作区 PVC 为 RWO 误配（单点可写）：多副本调度到不同节点时第二副本挂载失败——部署文档明确要求 RWX 并在 values 校验副本数 >1 时提示存储类要求
- 主密钥轮换/错配：沿 022 既有行为（启动即拒并指路），K8s 下表现为 CrashLoopBackOff + 日志指明原因——文档写明排查入口

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供官方 Helm Chart 作为 K8s 标准部署入口：副本数、镜像版本、资源配额可配置；数据库连接与主密钥 MUST 经 K8s Secret 注入（环境变量档，022 零改动），MUST NOT 在 values 或模板中出现明文凭证
- **FR-002**: Chart MUST 默认开启集群档（cluster.enabled=true）并为每副本自动派生唯一实例标识（Pod 名）；工作区 MUST 以共享卷（RWX PVC）挂载，挂载要求与 027 支持矩阵一致并在文档声明
- **FR-003**: Chart MUST 配置存活与就绪两类探针（复用既有健康端点语义）：未完成启动（含迁移与注册表构建）或依赖不可用的副本 MUST NOT 接入流量
- **FR-004**: 副本终止 MUST 走优雅序列：先摘流量，给在途轮次一个可配置的优雅窗口（默认与既有停机口径一致）完成收尾与租约释放；窗口到期按既有停机行为处理，MUST NOT 无限等待
- **FR-005**: 滚动升级采用逐副本替换策略，全程 MUST 保持服务可用（连续请求零失败为验收口径）；新旧版本短暂共存 MUST 安全（依赖既有前向兼容迁移纪律）
- **FR-006**: 缺失必填配置（数据库连接、主密钥）时 MUST 在安装/启动期给出明确报错与修复指引，不得部署出带病可用实例
- **FR-007**: 系统 MUST 支持可选的 OTLP trace 导出：以既有 traceId 为链路上下文，在既有审计点位（轮次处理、LLM 调用、工具调用）产生 span，父子关系与耗时正确；导出端点、采样与开关 MUST 配置化
- **FR-008**: 未配置导出端点时 MUST 零开销零行为变化（不建连接、不加依赖故障面、无告警噪音）；端点不可达时 MUST 静默降级不影响主链路（低频告警可接受）
- **FR-009**: OTel span 与库内审计记录 MUST 同源同 traceId（跨系统链路与库内精确回放可互查）
- **FR-010**: 既有部署形态（裸机 tar.gz/bin、docker compose）MUST 零变化；Helm 为新增选项，不引入任何「必须上 K8s」的行为分叉。例外：实证缺陷修复不算破坏——`bin/stop.sh` 停机宽限期与 compose `stop_grace_period`/实测口径对齐（10s→40s）属回归既有文档承诺（analyze I1 裁决 2026-09-14）
- **FR-011**: Chart MUST 通过模板校验（lint/template/schema）**与 CI 内 kind 集群安装冒烟（install 双副本就绪 + 实例双活断言）**进入 CI 门禁——CI runner 自带容器运行时，安装冒烟属可自动化面不得留人工尾巴（analyze C1 裁决 2026-09-14）；滚动升级压测与故障接管等交互式走查按验收卷落卷
- **FR-012**: 部署文档 MUST 含：一条命令安装示例、必填/常用 values 说明、RWX 存储要求、升级与回滚操作、故障排查入口（探针失败/CrashLoop/密钥错配）

### Key Entities *(include if feature involves data)*

- **Helm 发布（Release）**: 一次安装的配置快照——副本数、镜像版本、Secret 引用、PVC 声明；升级/回滚以 Release 为单位
- **部署 values**: 用户可配置面——必填（数据库、主密钥 Secret）与可选（副本数、资源、探针参数、优雅窗口、OTLP 端点）
- **Trace 链路**: 一轮消息处理的 span 树（轮次根 span → LLM/工具子 span），traceId 与审计表同源；本刀不新增库表

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在干净的本地 K8s 集群上，从执行安装命令到双副本全部就绪 ≤5 分钟（不含镜像拉取），期间仅需提供数据库与主密钥两项配置
- **SC-002**: 滚动升级期间以稳定速率持续请求（≥1 req/s），非预期失败为 **0**（429 类背压响应按口径另计并说明）
- **SC-003**: 强杀单副本后，后续请求由存活副本服务成功率 100%；被杀副本自动重建归队，实例列表窗口内反映死活
- **SC-004**: 副本终止时在途轮次在优雅窗口内完成或按既有口径标失败，无悬空租约导致的后续消息阻塞超过等待窗口
- **SC-005**: 配置 OTLP 端点后，一轮含工具调用的对话在追踪后端形成完整链路（根 span + LLM/工具子 span），traceId 与审计表记录一致；未配置时全量既有测试绿、零导出尝试
- **SC-006**: 027 的 A 建 B 见走查在 RWX PVC 上复跑通过（≤3s 口径不变）；026 吞吐线性性以独立发压得到双/单副本吞吐比硬数字落卷（目标 ≥1.6×，未达时如实记录瓶颈分析）
- **SC-007**: Chart lint 与本地集群安装冒烟进 CI 可重复执行；裸机与 compose 全量既有验收零回归

## Assumptions

- 验收环境用本地 K8s（kind/k3d）+ 本地 RWX 存储（如 NFS provisioner 或 kind 共享 hostPath 满足读写可见 + rename 原子），如实记录环境与真云差异；共享 PostgreSQL 由集群外或集群内附带 chart 提供，二选一在文档写明（数据库本体的 HA 不在本刀范围）
- 镜像沿用既有 GHCR 发布物与版本策略；本刀不改镜像构建（如需微调 entrypoint 以配合探针/preStop 属允许的最小增量）
- OTel 导出只做 trace（不做 metrics/logs 导出——metrics 已有 Prometheus 端点、logs 已 stdout 交采集器）；采样默认全采（企业内网流量规模），可配置
- 「零失败」口径：客户端重试关闭、请求超时设为优雅窗口以上；因滚动摘流产生的连接层瞬断由就绪门控避免，不依赖客户端重试兜底
- 026 吞吐复测使用 mock provider 注入固定时延（模拟真实 LLM 往返），独立发压端与服务副本不同机（或至少不同资源组），修正 026 的发压端瓶颈口径
- 不做：Operator/CRD、HPA 启用（模板留注释）、服务网格、marketplace 上架、日志采集栈、数据库 HA 编排
