# Feature Specification: 审计 Trace 串联与脱敏

**Feature Branch**: `021-audit-trace`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "审计 Trace 串联与脱敏（021-audit-trace）：一次消息处理的全链路可回放，v0.3 治理面第二刀（roadmap：trace ID 串联一次 ReAct 全链路，敏感字段脱敏；验收 Demo 后半段「管理台按 trace ID 查到完整链路与成本」）。要点：每次消息处理（会话消息/无状态调用/定时触发/飞书入站）生成唯一 trace ID，贯穿本轮全部审计记录——llm_calls 与 tool_invocations 各自加 trace_id 列（手工 schema 升级），同一轮的多次 LLM 调用与工具调用按时间序可完整回放「思考→调工具→再思考」链路；trace ID 回传调用方（REST 响应头/响应体、SSE 事件、执行历史记录），用户报障时可凭 trace ID 精准定位；审计查询 API 支持按 trace_id 查询单轮全链路（LLM 调用+工具调用合并时间线，含成本合计与总耗时）；管理台审计面新增按 trace ID 查询入口与时间线视图（每步的类型/名称/耗时/成败/token 或参数摘要）；敏感字段脱敏：审计查询 API 返回的工具参数/结果与 LLM 相关内容对已知敏感形态（API key、Authorization 头、URL 凭证段、password 类字段）做脱敏，脱敏在查询展示层做、落库保持原文（排障需要原始数据，展示不泄密）；结构化日志同一 trace ID 贯穿（日志与审计可互查）；默认开启零配置，旧审计数据 trace_id 为空不影响查询；分布式 tracing（OpenTelemetry）留 v0.4 不做。"

## Clarifications

### Session 2026-09-01

- Q: 审计中的敏感内容，落库时保留原文还是直接脱敏？ → A: 展示层脱敏、落库原文——API/管理台一律掩码，库中原文供深度排障（库访问=运维特权，018 门禁 + 内网边界）；凭证本不该进工具参数（宪法 VI 走环境变量），脱敏是对意外出现的展示防线。
- Q: 一个 trace ID 覆盖的范围？ → A: 一次消息处理——一轮 ReAct 的全部 LLM/工具调用共享同一 ID；会话维度靠既有 session_id，单步粒度即审计行自身，trace 补中间缺的报障自然单位。
- 事实性修正（非决策）：`llm_calls` 表不存 prompt/completion 内容（仅模型名/token/耗时/成本），脱敏的实际作用面为 `tool_invocations` 的参数、结果与错误信息——spec 各处口径以此为准。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 凭 trace ID 回放一次处理的全链路 (Priority: P1)

业务用户反馈"Agent 昨天下午那次回答不对/特别慢"。管理员拿到该次调用的 trace ID（调用方响应里带回、或从审计列表按时间定位），在审计查询里输入它——得到这一轮处理的完整时间线：第 1 步 LLM 思考（模型、token、耗时）、第 2 步调了什么工具（名称、成败、耗时）、第 3 步 LLM 收尾……直到最终响应；时间线自带本轮的成本合计与总耗时。「思考→调工具→再思考」的每一步都有据可查，排障从"翻日志猜"变成"按 ID 查"。

**Why this priority**: 这是 trace 串联的本体，也是 v0.3 验收 Demo 的后半段——审计数据 016 起已可查，但按会话查回来的是一大串记录，无法回答"某一次处理到底发生了什么"；trace ID 把审计粒度从"会话"精确到"单轮"，是排障与追责的最小可用单元。

**Independent Test**: 触发一次会多轮调工具的消息处理 → 从审计列表拿到该轮 trace ID → 按 trace ID 查询：返回本轮全部 LLM 调用与工具调用的合并时间线（时间序正确、类型/名称/成败/耗时齐全）、成本合计与总耗时；换一个 trace ID 查另一轮互不混串。

**Acceptance Scenarios**:

1. **Given** 一次触发了工具调用的消息处理完成，**When** 按其 trace ID 查询审计，**Then** 返回该轮全部 LLM 调用与工具调用的合并时间线，按发生时间排序，每步含类型（LLM/工具）、名称（模型名/工具名）、成败、耗时，LLM 步含 token 数。
2. **Given** 同一会话先后发生两轮处理，**When** 分别按各自 trace ID 查询，**Then** 两轮记录完全分离、互不混串；按会话查询仍可见全部记录（既有口径不变）。
3. **Given** 一轮处理的时间线，**When** 查看汇总，**Then** 含该轮 LLM 成本合计（已配定价时）、总 token、总耗时与步数。
4. **Given** 处理中途失败（LLM 报错/工具失败），**When** 按 trace ID 查询，**Then** 失败步骤同样在时间线中（失败原因可见），链路完整到失败点。
5. **Given** 升级前的历史审计数据（无 trace ID），**When** 按会话/时间查询，**Then** 照常返回（trace 字段为空），不影响任何既有查询。

### User Story 2 - trace ID 回传调用方，报障可精准定位 (Priority: P2)

业务系统调用 REST 接口后，响应里带着本次处理的 trace ID；流式调用在事件里带；定时任务与飞书触发的执行在执行历史里能看到。用户报障时只要提供 trace ID（或截图里带着它），管理员直接按 ID 查询，不再需要"大概几点、哪个会话"的模糊定位。结构化日志里同一 trace ID 贯穿本轮全部日志行——审计查到可疑步骤后可以精确翻到对应日志上下文。

**Why this priority**: trace 的价值一半在"查得到"，另一半在"拿得到"——ID 不回传给调用方，报障时还是要靠时间猜。依赖 US1 的 ID 生成与落库先就位。

**Independent Test**: REST 非流式调用响应中可取到 trace ID；SSE 流式调用的事件中可取到；定时/手动触发的执行历史记录展示 trace ID；用拿到的 ID 查询审计能命中本轮；grep 日志文件该 ID 能命中本轮的日志行。

**Acceptance Scenarios**:

1. **Given** REST 非流式消息调用，**When** 响应返回，**Then** 调用方可从响应中获得本轮 trace ID（既有响应字段不变，纯增量）。
2. **Given** SSE 流式调用，**When** 事件流开始后，**Then** 调用方可从事件中获得 trace ID（遵循 019「事件类型只增不改」的兼容承诺）。
3. **Given** 定时任务或管理台手动触发的执行，**When** 查看执行历史，**Then** 每条执行记录可见其 trace ID，点查可进入该轮时间线。
4. **Given** 一轮处理产生的结构化日志，**When** 以 trace ID 检索日志，**Then** 本轮的关键日志行（LLM 调用、工具执行、错误）均携带该 ID，日志与审计可互查。

---

### User Story 3 - 管理台时间线视图与敏感信息脱敏 (Priority: P3)

管理员在管理台审计面输入 trace ID，看到该轮的可视化时间线：每步的类型图标、名称、耗时、成败状态，LLM 步显示 token 与成本、工具步显示参数摘要与结果摘要。摘要中的敏感内容——API key、Authorization 凭证、URL 里的账密段、password 类字段值——显示为掩码（如 `sk-****`），管理员能看懂链路但看不到明文凭证；数据库中保留原文供深度排障（直连库属运维特权操作）。

**Why this priority**: 可视化与脱敏是查询能力之上的体验与安全增强：时间线让非专家也能读懂链路；脱敏让审计面可以放心开给更大范围的管理角色。依赖 US1 的查询 API 先成立。

**Independent Test**: 管理台按 trace ID 查到时间线视图（步骤序、类型、耗时、成败、摘要齐全）；构造含 API key/password 的工具调用后，审计查询 API 与管理台展示中的对应内容为掩码，数据库原文完整；不含敏感形态的内容原样展示。

**Acceptance Scenarios**:

1. **Given** 管理台审计面，**When** 输入有效 trace ID，**Then** 展示该轮时间线：步骤按序、类型/名称/耗时/成败可见，LLM 步含 token 与成本，工具步含参数与结果摘要；无效 ID 给出明确"未找到"提示。
2. **Given** 某工具调用参数含 `Authorization: Bearer xxx` 或 `"password":"..."` 或 URL 账密段，**When** 通过审计查询 API 或管理台查看，**Then** 敏感值显示为掩码；同一记录在数据库中保持原文。
3. **Given** 内容不含任何已知敏感形态，**When** 查看摘要，**Then** 原样展示（脱敏不误伤正常内容）。
4. **Given** 016 既有的审计列表页，**When** 本 feature 上线，**Then** 列表新增 trace 维度入口（列表行可跳转该轮时间线），既有列表功能不变。

---

### Edge Cases

- **trace ID 的边界 = 一次消息处理**：一轮 ReAct 的全部 LLM 调用与工具调用共享同一 ID；同一会话的不同消息各有各的 ID；SSE 与非流式同口径。
- **审计写入失败的既有语义不变**：trace 字段只是随行落库的新列，各表既有的 fail-open/fail-closed 口径不因 trace 改变。
- **并发处理互不串号**：同一时刻多轮处理（不同会话/定时任务并发）各自持有独立 trace ID，虚拟线程并发下不得互相污染。
- **策略拒绝/沙箱拒绝的调用**（020 的 blocked_by 记录）：同样携带 trace ID，时间线里可见"这一步被拦"。
- **脱敏是展示层行为**：落库原文；导出/API/管理台一律走脱敏；脱敏规则按已知形态匹配（API key 常见前缀、Authorization 头、URL userinfo 段、password/secret/token 类字段名），不做全文启发式（避免误伤）。作用面为 `tool_invocations` 的参数/结果/错误信息——`llm_calls` 不存对话内容，无脱敏对象（Clarifications 事实性修正）。
- **脱敏对 020 参数摘要的一致性**：策略页/审计页展示的工具参数摘要走同一套脱敏规则（单一实现，不各写一份）。
- **无审计记录的 trace**（如校验失败在 LLM 调用前）：按 ID 查询返回空时间线 + 明确提示，不报错。
- **日志中的 trace ID**：仅在本轮处理的执行路径日志中携带；与审计 ID 完全一致（同一个值，不是两套 ID）。
- **旧数据兼容**：trace 列为空的历史记录在按会话/时间查询中照常出现；按 trace 查询自然查不到它们（如实为空）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每次消息处理开始时系统 MUST 生成全局唯一 trace ID，覆盖全部触发源：REST 会话消息、无状态调用、管理台会话/触发、定时任务、飞书入站；一轮 ReAct 的全部 LLM 调用与工具调用 MUST 共享同一 ID。
- **FR-002**: `llm_calls` 与 `tool_invocations` MUST 各自新增 trace 标识列（可空，手工 schema 升级，旧行为空），本轮每条审计记录写入当前 trace ID；写入语义（fail-open/fail-closed）与既有口径一致。
- **FR-003**: 并发处理 MUST 互不串号：同一时刻的多轮处理各自持有独立 trace ID（虚拟线程并发下的隔离正确性）。
- **FR-004**: 审计查询 MUST 支持按 trace ID 查询单轮全链路：LLM 调用与工具调用合并为按时间排序的时间线，每步含类型、名称、成败、耗时，LLM 步含 token 与成本；附本轮汇总（成本合计、总 token、总耗时、步数）；未命中返回空时间线与明确提示。
- **FR-005**: trace ID MUST 回传调用方：REST 非流式响应可获取（既有字段不变，纯增量）；SSE 流式事件可获取（遵循 019 事件类型只增不改）；执行历史记录展示 trace ID。
- **FR-006**: 本轮处理路径的结构化日志 MUST 携带同一 trace ID（与审计同值），关键节点（LLM 调用、工具执行、失败）均可按 ID 检索；处理结束后 MUST 清理线程上下文，不得污染后续请求。
- **FR-007**: 审计查询 API 与管理台展示 MUST 对已知敏感形态脱敏：API key 常见形态、`Authorization` 凭证、URL 中的账密段、`password`/`secret`/`token`/`api_key` 类字段值——显示为部分掩码；落库 MUST 保持原文；不含敏感形态的内容 MUST 原样展示（不误伤）。
- **FR-008**: 脱敏 MUST 为单一共享实现：审计时间线、016 既有审计列表、020 策略页参数摘要等全部展示面走同一套规则。
- **FR-009**: 管理台审计面 MUST 提供 trace ID 查询入口与时间线视图（步骤序/类型/名称/耗时/成败/摘要，LLM 步含 token 与成本）；016 既有审计列表 MUST 增加 trace 维度（行内可见 ID 并可跳转时间线），既有功能不变。
- **FR-010**: 全部能力 MUST 默认开启零配置；升级前历史数据（trace 为空）MUST 不影响任何既有查询；本 feature MUST NOT 改变既有响应字段与审计表既有列的语义（回归零破坏）。
- **FR-011**: 不做分布式 tracing（OpenTelemetry/跨进程传播，留 v0.4）；不做日志文件的查询 API（日志检索靠既有日志设施 + trace ID grep）。

### Key Entities

- **Trace（单轮处理轨迹）**: 逻辑实体，不单独建表——由 `llm_calls` 与 `tool_invocations` 中共享同一 trace ID 的记录集合构成。属性（查询时派生）：trace ID、触发源、起止时间、步骤列表（时间序）、成本合计、总 token、总耗时、终态（成功/失败）。
- **脱敏规则（RedactionRule）**: 已知敏感形态的匹配与掩码策略集合（API key 形态/Authorization/URL 账密/敏感字段名），代码内置、全展示面共享；不落库、不可由外部输入扩展（避免注入面）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 回归零破坏：既有全量测试 100% 通过；升级前历史审计数据在既有查询中表现与升级前一致。
- **SC-002**: 串联完整率 100%：任一轮处理的全部 LLM 调用与工具调用（含失败/被策略拦截的）都携带同一 trace ID，按 ID 查询时间线步数与实际发生数一致。
- **SC-003**: 并发隔离 100%：并发多轮处理的审计记录无串号（压测样本中跨 trace 混入为 0）。
- **SC-004**: 回传可达率 100%：REST/SSE/执行历史三个通道都能拿到 trace ID，且用它查询审计必命中本轮。
- **SC-005**: 排障路径缩短：从"用户报障"到"看到该轮完整时间线"只需一步查询（输入 trace ID），无需按时间/会话人工筛选。
- **SC-006**: 脱敏有效且不误伤：含已知敏感形态的样本 100% 掩码展示、库中原文完整；不含敏感形态的样本 100% 原样展示。
- **SC-007**: 日志互查：凭 trace ID 检索日志可命中该轮全部关键节点日志行（LLM/工具/失败），与审计时间线步骤可对应。
- **SC-008**: v0.3 验收 Demo 后半段可完整演示：触发调用 → 拿到 trace ID → 管理台按 ID 查到完整链路与成本。

## Assumptions

- **trace ID 形态取通用短标识**（如 UUID 或等价随机标识），不编码业务含义；对外形态在契约文档固化后不再变更（接口即承诺）。
- **边界=一次消息处理**：SSE/非流式/定时/飞书同口径；不做「跨消息的任务级 trace」（多轮对话的串联靠会话维度，已有）。
- **脱敏规则内置不可配置**：形态清单随版本演进（新增形态走代码变更），不开放运行时配置——避免规则本身成为注入/绕过面；落库原文的前提是数据库访问本身属运维特权（018 门禁 + 内网部署边界）。
- **执行历史的 trace 展示**只覆盖有执行记录的触发源（定时/手动触发的 `agent_executions`）；REST 直接调用不产生执行记录，其 trace 从响应获取。
- **日志检索不建 API**：结构化日志已含 trace 字段，检索靠部署方现有日志设施（grep/ELK 等）。
- **依赖**：016 审计查询与看板（时间线是其纵深视图）、019 SSE 事件协议（新增事件或字段遵循只增不改）、020 的 blocked_by 记录（时间线中可见被拦步骤）、成本计算沿用 016 定价口径。
