# Feature Specification: session 归属与多副本正确性（Session Ownership）

**Feature Branch**: `026-session-ownership`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "session 归属与多副本正确性（026-session-ownership）：v0.4 分布式底座第二刀、技术核心。025 已给多副本共同事实源（PG 部署选项），但行为正确性未保障——六个双副本一跑就翻车的具体场景：①同会话并发消息落两副本→乐观锁冲突→用户随机看到「处理失败」；②每副本调度器都到点开火→客户收到两封日报；③飞书 3s 超时重推可落到另一副本→进程内去重 Map 失效→用户收到两条回答（已实证）；④企微单连接互踢→两副本循环踢连接、消息丢在换连缝里（已实证）；⑤副本挂了处理中的轮次悬空→用户永远等不到回复也没有提示；⑥哪些副本活着、谁在处理什么运维无处可查。解法是一条 CAS 认领原语套五个场景：turn 租约（绑定「正在执行的一轮」非会话永久归属，owner=instanceId@epoch，心跳续租带 fencing、失败即中止，双层锁保留进程内快路径，跨副本后到者短轮询等待）；调度任务同款 CAS 认领；去重下沉幂等回执表；渠道连接租约属主（企微）；过期惰性回收不重放、绝无 startup 全量抹除；instances 心跳表。协调面接口化：JDBC 默认、Redis 留缝不实现。租约参数配置化；指标挂 023 MetricsRecorder；分布式误配 fail-fast。性能口径：每轮约 5 次单行小写、session 间全并行、群聊无状态绕开竞争；验收含性能锚点（双副本+PG 压测两种负载，吞吐随副本线性、租约开销 p99 不可见）与正确性验收（同会话并发无丢失无重复无报错、定时恰好一次、跨副本去重、kill 后下条消息健康副本接管）。零破坏：单机 SQLite 档零配置零行为变化；ReActLoop/AgentService 契约面尽量零改动。不做：粘性路由/转发、消息队列、崩溃重放、Redis 实现、跨请求 Provider 健康记忆、IM 平台侧连接管理。"

> 前置：025-pluggable-storage（共享数据库部署选项）已交付——本刀在共同事实源之上补齐多副本的**行为正确性**。规划出处：docs/DistributedFoundationPlan.html §04（六场景与裁决已经维护者与评审对齐）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同一会话的消息在多副本下有序且恰好处理一次（Priority: P1）

企业把系统部署为双副本（共享数据库）。终端用户在 IM 里连续发多条消息，平台把消息随机投给任一副本；用户偶尔因网络重发、平台也可能超时重推同一条消息到另一个副本。无论消息落在哪个副本：同一会话内的消息**按序逐条**处理（后到的等待前一条完成，与单机排队体验一致）、每条消息**恰好回答一次**（重推/重发被识别丢弃）、不同会话之间完全并行互不等待。

**Why this priority**: 这是「多副本」成立与否的判据——没有它，双副本对用户的直接感受是随机报错和重复回答，比单副本更差。六个翻车场景中的 ①③ 由此收口。

**Independent Test**: 双副本连同一共享库，经**渠道入站路径**（模拟 IM 平台投递入站事件，复用 017 渠道契约测试手法）对同一会话并发投递多条消息 + 把同一事件重推到两个副本，断言回答条数恰好等于消息条数、会话历史有序完整、全程无处理失败报错；另起 N 个独立会话并发投递，断言互不阻塞。真机抽查：飞书实际 @bot 连发提问，逐条恰好一答。

**Acceptance Scenarios**:

1. **Given** 双副本运行且同一会话的两条消息几乎同时分别落到两个副本，**When** 处理发生，**Then** 两条消息按到达序先后完成、各回答一次、无失败报错（后到者等待而非冲突）
2. **Given** IM 平台把同一条消息（同一事件标识）超时重推到另一个副本，**When** 第二个副本经渠道入站路径收到它，**Then** 识别为重复并丢弃，用户在 IM 里只收到一条回答（去重判定在共享存储，替换单机内存去重）
3. **Given** 用户在 IM 私聊 @bot 连续提问三条，消息被平台分散投到两个副本，**When** 处理发生，**Then** 用户按提问顺序收到三条回答，体验与单机排队一致
4. **Given** N 个互不相关的会话并发发消息到两个副本，**When** 处理发生，**Then** 各会话独立并行完成，无跨会话等待
5. **Given** 单副本单机部署（默认档），**When** 同样的并发消息场景，**Then** 行为与本特性交付前完全一致（零配置零变化）

### User Story 2 - 定时任务在多副本下恰好执行一次（Priority: P1）

管理员配置了 Agent 的定时任务（如每日日报）。双副本部署下每个副本的调度器都会到点触发——系统必须保证同一次到点**只有一个副本实际执行**：客户收到恰好一封日报，执行历史里恰好一条记录。执行副本中途挂掉时，该次执行按既有失败口径记录，不会被另一副本重复补发。

**Why this priority**: 场景② 是对外可见的最尴尬故障（客户收到两封一样的日报）；调度是既有能力，多副本下不修就是回归。

**Independent Test**: 双副本下注册一个短周期任务，跑若干个周期，断言每个周期的执行记录恰好一条、通知恰好一次。

**Acceptance Scenarios**:

1. **Given** 双副本且同一定时任务到点，**When** 两个副本的调度器同时触发，**Then** 恰好一个副本执行，执行历史恰好一条
2. **Given** 执行副本在任务进行中被杀，**When** 该周期结束，**Then** 不产生第二次执行（不重放），下一周期由任一健康副本正常执行

---

### User Story 3 - 副本故障的自动接管与运维可见性（Priority: P2）

副本 A 在处理某会话的消息中途崩溃。用户视角：这一条消息不会永远悬空——等待窗口过后该轮被标记失败；用户重发（或发下一条）时，消息落到哪个健康副本哪个正常处理，会话历史完整连续。运维视角：管理台/接口能看到当前有哪些副本存活（最近心跳时间）、哪些会话轮次正被谁处理；崩溃副本的痕迹在窗口过后自动回收。独连型 IM 渠道（企微）由某一副本持有连接，该副本挂掉后另一副本在窗口内自动接管连接，消息收发恢复。

**Why this priority**: 场景⑤⑥④ 的收口——容错是双副本的核心卖点之一，但依赖 US1 的认领机制先立起来。

**Independent Test**: 双副本处理中 kill 掉执行副本，断言该轮在窗口后标失败、用户下一条消息由健康副本处理成功、会话历史无损；查询接口列出存活副本；企微型连接在属主被杀后由另一副本接管。

**Acceptance Scenarios**:

1. **Given** 副本 A 正在处理某会话消息，**When** A 被强杀，**Then** 等待窗口过后该轮标记失败（有明确的失败记录），**不自动重放**该消息
2. **Given** A 已死、用户再发一条消息落到副本 B，**When** B 处理，**Then** 正常认领并完成，会话历史含 A 崩溃前已落库的完整上下文
3. **Given** 双副本运行，**When** 运维查询实例状态，**Then** 能看到每个副本的标识与最近心跳时间；已死副本在窗口后不再显示为存活
4. **Given** 独连型渠道（企微）连接由 A 持有，**When** A 被杀，**Then** B 在接管窗口内建立连接，后续消息正常收发（两副本不互踢）

---

### Edge Cases

- 执行副本假死（进程活着但停顿，如长 GC）后苏醒：它对本轮的续约已失效，苏醒后必须立即中止本轮执行且不得写回结果（防脑裂——两个副本同时认为自己持有同一轮）
- 副本快速重启（同一实例标识再次上线）：不得误继承重启前的轮次持有权（持有身份含代次信息，旧代次的持有不被新进程认领）
- 等待前序消息的后到副本长时间等不到（前序执行超长）：等待有上限，超限按既有超时口径反馈用户，不无限挂起
- 时钟漂移：副本间时钟差在常规 NTP 水平（秒内）时不影响正确性；判定以数据库时间为准而非各副本本地时钟
- 单副本部署但配了共享数据库：租约机制照常工作（自己抢自己的），行为正确只是无竞争；不因单副本而绕过
- 分布式误配：多副本部署 + 仅单机可用的组件（本地文件记忆档、本地嵌入式库）→ 启动拒绝并指明正确配置，不带病运行
- 群聊问答（无状态独立会话）：天然无同会话竞争，不因本特性引入额外等待

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 保证同一会话在任一时刻至多一个副本在执行其消息处理（互斥以「正在执行的一轮」为粒度，不是会话到副本的永久归属）；同一会话的后到消息 MUST 等待前序完成后按序处理，等待有上限、超限明确反馈
- **FR-002**: 不同会话之间的处理 MUST 完全并行，不因互斥机制产生跨会话等待
- **FR-003**: 执行权持有 MUST 有期限并周期性续期；续期失败（持有权已被回收或身份失效）时执行方 MUST 立即中止本轮且不写回结果
- **FR-004**: 副本崩溃后其持有的轮次 MUST 在期限过后可被识别与回收：该轮标记失败留痕，**不自动重放**；回收 MUST 只针对已过期的持有，任何情况下不得全量清除他人持有
- **FR-005**: 定时任务的每次到点 MUST 恰好被一个副本执行，执行历史恰好一条；执行中崩溃按失败记录，不补发
- **FR-006**: 入站消息去重 MUST 跨副本生效（判重依据落共享存储）：平台重推/用户重发的同一事件恰好处理一次；现有单机内存去重行为在单副本下保持一致
- **FR-007**: 独连型渠道（企微）的连接 MUST 由持有渠道执行权的唯一副本建立；持有副本失效后其他副本 MUST 在接管窗口内接管连接；多副本 MUST NOT 同时建连互踢
- **FR-008**: 每个副本 MUST 周期性上报心跳（落共享存储），运维可查询存活副本清单与最近心跳；持有关系可查询（谁在处理什么）
- **FR-009**: 协调能力 MUST 收敛在统一接口之后，默认实现基于既有共享数据库（零新增运维组件）；接口预留其他实现的接入缝，本刀不交付第二实现
- **FR-010**: 期限、续期间隔、等待轮询间隔、接管窗口等参数 MUST 配置化并有安全默认值；关键协调事件（认领、回收、续期失败）MUST 产出监控指标（挂既有指标体系）与结构化日志
- **FR-011**: 多副本部署与仅单机组件的组合 MUST 启动即拒绝并指明修正方向（如本地文件记忆档、本地嵌入式库 + 多副本）；单机默认档 MUST 零配置零行为变化
- **FR-012**: 上述协调数据 MUST 全部落共享存储（新增表走 025 迁移体系，两种库同语义）；对处理链路的既有契约（会话历史、审计口径、REST/SSE）零改动

### Key Entities

- **轮次持有（turn lease）**: 会话标识 → 持有者（实例标识+代次）+ 到期时间；一轮执行的互斥载体，执行完释放，过期可被回收
- **调度认领（schedule claim）**: 定时任务的某次到点 → 执行副本；恰好一次的互斥载体
- **事件回执（event receipt）**: 渠道事件标识 → 首次处理记录；跨副本判重依据
- **渠道执行权（channel lease）**: 独连型渠道 → 持连副本 + 到期时间；连接唯一性的载体
- **实例心跳（instance heartbeat）**: 副本标识 → 最近心跳时间、启动时间；存活判定与运维可见性载体

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 双副本下经渠道入站路径对同一会话投递 20 条消息（含模拟平台重推）：回答恰好 20 条、会话历史有序完整、零处理失败报错；IM 真机抽查连发提问逐条恰好一答
- **SC-002**: 双副本下短周期定时任务连续 10 个周期：执行记录恰好 10 条、通知恰好 10 次
- **SC-003**: 执行副本被强杀后：该轮在接管窗口内标记失败留痕；用户下一条消息由健康副本正常处理，会话上下文完整
- **SC-004**: 平台重推同一事件到不同副本 100 次演练：重复回答 0 次
- **SC-005**: 独连型渠道属主被杀后，另一副本在接管窗口内恢复消息收发；连续运行期间零互踢循环
- **SC-006**: 运维查询能列出全部存活副本与心跳时间；杀掉一个副本后其在窗口过后不再显示存活
- **SC-007**: 性能锚点（双副本 + 共享库压测）：「N 并发独立会话」负载下吞吐相对单副本近似线性（≥1.8×）；「单会话连发」负载下端到端延迟与单机排队相当；协调开销在整轮耗时的 p99 中不可见（<1%）
- **SC-008**: 单机默认档全量回归零变化：零新增必填配置，既有测试全绿
- **SC-009**: 误配组合（多副本 + 单机组件）启动即拒绝且报错指明修正方向，演练全部命中

## Assumptions

- 多副本的部署形态与滚动升级编排归 027/028（容器交付）；本刀在两个裸进程 + 共享库的形态下验收多副本正确性
- 「多副本部署」的判定信号在 plan 阶段定稿（如显式配置实例标识/副本模式开关），缺省单机档不需要任何新配置
- 崩溃轮次不自动重放是产品裁决（副作用未知，重放可能造成重复外呼/重复写）；用户以重发消息恢复
- 平台侧投递语义沿用已实证结论（飞书/钉钉随机投一、企微单连接互踢）；平台自身的投递保证不在本刀控制范围
- 群聊问答沿用既有无状态独立会话设计，不纳入同会话互斥语义
- 压测的性能锚点在共享库（PG）档执行；单机 SQLite 档不承诺多副本（025 已定口径）
- Redis 等第二协调实现、粘性路由、消息队列、崩溃自动重放明确不做（评审稿裁决）
