# Feature Specification: IM 入站渠道抽象与飞书双向接入

**Feature Branch**: `016-feishu-im-channel`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "IM 入站渠道抽象与飞书双向接入：企业用户在飞书里 @Agent 或私聊提问，OryxOS 路由到对应 Agent 跑 ReAct 循环并把回答发回飞书；作为第一个入站 IM Channel，沉淀可复用的入站渠道抽象（后续企微/钉钉接入只加适配器）；复用现有 Notify 凭证体系与沙箱域名白名单（*.feishu.cn）；会话与审计与现有 CLI/REST 渠道同一套底座（roadmap v0.2「IM 入站」条目，为 v0.3 HITL 审批卡片打底）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 飞书私聊问答闭环（Priority: P1）

企业员工在飞书里找到 Agent 机器人，像跟同事聊天一样发一句「服务器磁盘告警了怎么处理？」，片刻后在同一个对话里收到 Agent 检索知识库/记忆后给出的回答；接着追问「第二步的命令具体怎么写？」，Agent 基于刚才的上下文继续回答——多轮对话连续，无需重复背景。

**Why this priority**: 这是 IM 入站的最小完整价值闭环——「企业 Agent 的实际入口」从 REST/控制台变成员工每天打开的聊天工具。没有它，本特性不成立。

**Independent Test**: 配好一个飞书应用与 Agent 的绑定后，在飞书私聊发问并收到正确回答、追问得到承接上下文的回答，即可独立验收。

**Acceptance Scenarios**:

1. **Given** 飞书应用已与 Agent `ops-agent` 绑定且服务在线，**When** 员工私聊发送「服务器磁盘告警了怎么处理？」，**Then** 员工在同一私聊会话里收到该 Agent 经完整推理（可含知识检索、记忆调用）后的回答。
2. **Given** 员工刚在私聊里问过磁盘告警问题，**When** 追问「第二步的命令具体怎么写？」，**Then** 回答承接上一轮上下文（能指出是哪条命令），不要求员工重述背景。
3. **Given** Agent 处理某问题失败（如模型服务不可用），**When** 员工发问，**Then** 员工在飞书里收到一条可读的失败说明（不是永久沉默，也不暴露内部堆栈）。

---

### User Story 2 - 群聊 @ 触发（Priority: P2）

运维群里有人 @Agent 问「昨晚的发布为什么回滚了？」，Agent 只在被 @ 时响应，把回答发回该群；群里其他闲聊消息 Agent 完全不读、不响应、不留痕。

**Why this priority**: 群聊是企业协作的主场景，但涉及「何时该响应」的边界（隐私与噪音）；在私聊闭环之上叠加，独立可测。

**Independent Test**: 把机器人拉进测试群，验证 @ 消息被响应、非 @ 消息零响应即可独立验收。

**Acceptance Scenarios**:

1. **Given** 机器人已在群内，**When** 成员发送「@运维小欧 昨晚的发布为什么回滚了？」，**Then** Agent 在该群回复答案，且提问文本中的 @ 片段不进入 Agent 的输入。
2. **Given** 机器人已在群内，**When** 成员发送不含 @ 机器人的任意消息，**Then** 系统不处理、不回复、不产生任何会话与审计记录。
3. **Given** 同一群里多名成员先后 @ 提问，**When** Agent 分别处理，**Then** 每条提问都得到回复，回复与提问的对应关系清晰（如引用原消息）。

---

### User Story 3 - 管理员配置接入（Priority: P2）

管理员在配置中登记飞书应用凭证（走环境变量，不落明文）与「飞书应用 ↔ Agent」的绑定关系，启动或变更后接入即生效；凭证缺失、绑定的 Agent 不存在等配置错误在启动/变更时就得到点名的可读报错，而不是运行时静默失败。

**Why this priority**: 没有可靠的配置与报错，前两个故事无法在真实企业环境落地；但它本身不产生终端用户价值，排 P2。

**Independent Test**: 分别用正确配置、缺凭证、绑定不存在的 Agent 三种输入启动，验证生效与两类可读报错。

**Acceptance Scenarios**:

1. **Given** 凭证与绑定配置齐全，**When** 服务启动，**Then** 飞书接入自动上线，运行信息中可见渠道状态。
2. **Given** 绑定指向不存在的 Agent，**When** 服务启动或配置变更，**Then** 得到点名该绑定的可读报错，接入不带病上线。
3. **Given** 凭证未配置，**When** 服务启动，**Then** 飞书渠道明确停用并给出提示，其余功能（CLI/REST/管理台）不受影响。

---

### User Story 4 - 可复用的入站渠道抽象（Priority: P3）

平台开发者接入第二个 IM（企微/钉钉）时，只需新增一个渠道适配器实现既定契约：消息如何进来、路由到哪个 Agent、回复如何送回、会话与审计如何标识——这些语义由底座统一承担，核心模块零修改。

**Why this priority**: 这是本特性沉淀的架构资产（对齐「新增 Channel 只加模块不改 core」的设计原则），价值在后续版本兑现。

**Independent Test**: 用一个测试桩渠道实现同一契约，跑通与飞书档相同的契约测试集，验证核心模块无改动。

**Acceptance Scenarios**:

1. **Given** 入站渠道契约与其行为测试集已建立，**When** 用测试桩实现该契约，**Then** 桩渠道跑通「收消息 → 路由 → 回复 → 会话 → 审计」全链路且核心模块无 diff。

---

### Edge Cases

- **事件真伪**：伪造的回调/事件（签名或校验凭据不符）必须 100% 拒绝且留下拒绝痕迹；合法事件不误杀。
- **重复推送**：飞书对未及时确认的事件会重试推送——同一事件重复到达时，Agent 只处理一次，用户只收到一条回答。
- **处理耗时与平台时限**：平台要求秒级确认收到事件，而 ReAct 推理可能数十秒——接收确认与回答发送必须解耦；超过配置阈值仍未完成时，先行告知「处理中」。
- **非文本消息**：图片、语音、文件等入站消息，回复「当前仅支持文本提问」的说明，不静默丢弃、不报错。
- **超长回答**：超过平台单条消息上限的回答按上限分段发送，内容不丢失。
- **绑定的 Agent 被停用/删除**：期间的提问收到可读的「Agent 不可用」回复；审计留痕。
- **服务重启窗口**：重启期间平台侧的事件依赖平台重试机制送达；已被确认但未完成处理的消息允许丢失，但必须在日志/审计中可见（不承诺跨重启的处理队列）。

## Requirements *(mandatory)*

### Functional Requirements

**A. 入站接入**

- **FR-001**: 系统 MUST 接收飞书私聊文本消息事件，并路由到该飞书应用绑定的 Agent 执行完整推理循环。
- **FR-002**: 群聊消息 MUST 仅在 @ 机器人时触发处理；@ 片段 MUST 从 Agent 输入中剥离；非 @ 消息 MUST 完全忽略（不处理、不落任何记录）。
- **FR-003**: 系统 MUST 校验入站事件的真实性（平台签名/校验凭据），未通过校验的事件 MUST 100% 拒绝并留下可查的拒绝痕迹。
- **FR-004**: 系统 MUST 对入站事件去重：同一事件标识重复到达时只处理一次，用户只收到一条回答。
- **FR-005**: 系统接收飞书事件的连接方式为 [NEEDS CLARIFICATION: 长连接模式（服务端主动连飞书，免公网回调地址，适合内网部署）还是公网 Webhook 回调（需要可被飞书访问的 HTTPS 地址），或两者都支持？这决定企业部署的网络前提]。

**B. 会话与回复**

- **FR-006**: 私聊会话 MUST 按「渠道 + 飞书用户 + Agent」维持多轮连续，与现有渠道的会话语义同构（同一套会话底座与历史窗口规则）。
- **FR-007**: 回答 MUST 送回消息来源处：私聊回私聊、群聊回原群（并与提问可对应）。
- **FR-008**: 事件接收确认与回答发送 MUST 解耦：收到即确认，推理完成后再发送回答；处理失败 MUST 以可读消息回复用户，不静默。
- **FR-009**: 入站仅支持文本消息；非文本消息 MUST 收到能力说明回复；超长回答 MUST 按平台上限分段发送不丢内容。

**C. 渠道抽象与配置**

- **FR-010**: 系统 MUST 沉淀入站 IM 渠道契约（消息进入、Agent 路由、回复送出、会话标识、审计标识），新增 IM 渠道 MUST 只需新增适配器、核心模块零修改；契约行为 MUST 由参数化测试集钉死（飞书档 + 测试桩档）。
- **FR-011**: 飞书应用与 Agent 的对应关系为 [NEEDS CLARIFICATION: 一个飞书应用固定绑定一个 Agent（多 Agent 需建多个飞书应用，映射简单清晰），还是单个飞书应用内按 @ 的机器人名/指令前缀路由到多个 Agent（员工侧入口统一，路由规则复杂）？]。
- **FR-012**: 飞书凭证 MUST 经环境变量注入或既有凭证注册体系管理，MUST NOT 明文写入配置文件。
- **FR-013**: 渠道启停与绑定变更 MUST 无需重启进程即可生效；配置错误（凭证缺失、Agent 不存在）MUST 在启动或变更时点名可读报错，渠道不带病上线且不影响其余功能。

**D. 审计与可观测**

- **FR-014**: 每次 IM 触发 MUST 与现有渠道同构地落会话与审计记录（会话、模型调用、工具调用、Agent 执行历史），渠道标识可区分可查询；运行信息 MUST 呈现渠道在线状态。

### Key Entities

- **入站渠道（Inbound Channel）**: 一种消息来源的接入形态（飞书为首个实现）；具备身份（渠道类型 + 应用标识）、在线状态、凭证引用。
- **渠道绑定（Channel Binding）**: 飞书应用与 Agent 的对应关系（形态取决于 FR-011 的裁决）；配置驱动、可变更、变更即生效。
- **IM 会话标识**: 私聊 =「渠道 + 用户 + Agent」；群聊 = 「渠道 + 群 + Agent」（群内共享上下文，见 Assumptions）；与既有会话底座同构。
- **入站事件**: 平台推送的一次消息投递，具备全局事件标识（去重依据）、消息类型、来源（私聊/群 + 用户）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 员工私聊提问到收到回答，除模型推理耗时外的渠道端到端开销 ≤ 2 秒（P95）。
- **SC-002**: 群内非 @ 消息 0 响应、0 留痕；@ 消息 100% 得到响应。
- **SC-003**: 伪造/签名不符的事件 100% 被拒绝且有拒绝留痕；合法事件 0 误杀。
- **SC-004**: 平台重复推送同一事件时，用户收到且仅收到 1 条回答（去重有效率 100%）。
- **SC-005**: 多轮私聊对话中，追问能得到承接上文的回答（人工评审通过率 ≥ 90%，软指标）。
- **SC-006**: 每次 IM 触发均可在审计中按渠道标识查到完整链路（会话 + 模型调用 + 工具调用），字段与 CLI/REST 渠道同构。
- **SC-007**: 以测试桩模拟第二个 IM 渠道接入，核心模块零修改、渠道契约测试集全绿。
- **SC-008**: 三类配置错误（缺凭证 / Agent 不存在 / 绑定格式非法）100% 在启动或变更时点名可读报错，无一带病上线。

## Assumptions

- **仅文本**：入站仅处理文本消息；图片/语音/文件/富文本卡片入站不在本期范围（回复能力说明）。
- **回复形态**：回答以文本（或平台等价的基础格式）整条/分段发送；流式逐字更新不在本期（SSE 属 REST 渠道的独立特性）；HITL 审批卡片属 v0.3。
- **群聊上下文**：群聊会话按「群 + Agent」共享上下文（同群成员的 @ 提问共享同一会话历史），与真实群聊心智一致。
- **应用形态**：飞书侧为企业自建应用（内部应用）；可见范围与使用权限由飞书管理员在飞书侧控制，OryxOS 不另建用户白名单。
- **单实例**：本期按单实例部署语义交付；多副本下的事件抢占/去重属 v0.4 分布式底座。
- **渠道范围**：本期仅实现飞书适配器；企微/钉钉只由渠道契约与测试桩证明可扩展性，不实现。
- **既有资产复用**：`*.feishu.cn` 已在沙箱域名白名单；出站通知（Notify）体系继续独立存在，本特性的「回复」走渠道自身的会话语义而非 Notify。
