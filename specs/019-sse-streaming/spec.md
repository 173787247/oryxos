# Feature Specification: SSE 流式响应

**Feature Branch**: `019-sse-streaming`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "SSE 流式响应（019-sse-streaming）：为会话消息端点加流式返回能力，补齐 v0.2「补齐公式」最后一角（roadmap：text/event-stream，保持同步模型不变——虚拟线程内逐 token 写出，不引入 WebFlux）。要点：POST /api/v1/sessions/{id}/messages 在客户端声明 Accept: text/event-stream 时改为 SSE 流式返回——LLM 生成的 token 逐段推送（打字机体验），ReAct 过程中的工具调用有进度事件（开始/结束），最终有完成事件（含完整回复与会话元数据）、失败有错误事件；不带该 Accept 的调用保持现状 JSON 一次性返回，回归零破坏；宪法七不动摇：不引入 WebFlux/Reactor 编程模型进核心循环，ReActLoop 保持同步；审计口径不变（llm_calls/tool_invocations 照写）；018 的 API Key/session 认证门禁对流式端点同样生效；管理台聊天页跟进打字机效果可作低优先级故事。"

## Clarifications

### Session 2026-08-27

- Q: 客户端中途断开连接，服务端怎么处理本轮处理？ → A: 继续完成并落库——停止推送但本轮照常跑完，回复入会话历史、审计照写；断开后仍消耗 token 的代价明示于契约（不做「断开即中止」，避免向核心循环注入取消语义）。
- Q: 本期流式范围只做会话消息端点，还是一并覆盖 invoke / CLI？ → A: 全部——`/api/v1/sessions/{id}/messages` 与 `/api/v1/agents/{name}/invoke` 均按 Accept 分流支持 SSE；CLI `oryxos chat` 同期改为打字机式逐段输出（进程内消费同一套流式能力，不经 HTTP）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 调用方看到打字机式的流式回复 (Priority: P1)

业务系统（或用 curl 调试的工程师）向会话发一条消息时，在请求上声明接受事件流。Agent 开始生成回复后，文字一段一段实时到达——调用方不再对着空白等待十几秒，而是像看人打字一样看着回复逐渐成形；全部生成完毕后收到一个明确的完成信号，携带完整回复与会话元数据。不声明接受事件流的调用方，得到与今天完全一致的一次性 JSON 响应。

**Why this priority**: 这是本 feature 的核心价值——长回复场景下「毫无动静地等十几秒」是最伤体验的环节，流式输出把感知等待压缩到秒级；同一端点按客户端声明分流，是对既有调用方零破坏的前提。此故事独立成立即是 MVP。

**Independent Test**: 对同一会话发同样的消息各调一次：带 `Accept: text/event-stream` → 响应为事件流，token 事件逐段到达，最后一个完成事件包含完整回复；不带 → 一次性 JSON，与 018 交付时的响应逐字段一致。把 token 事件按序拼接，与完成事件里的完整回复一致。对 `/api/v1/agents/{name}/invoke` 重复同样的双路验证。

**Acceptance Scenarios**:

1. **Given** 一个已存在的会话，**When** 带 `Accept: text/event-stream` 发消息，**Then** 响应 `Content-Type` 为 `text/event-stream`，回复内容以多个 token 事件逐段推送，最后收到一个完成事件（含完整回复文本与会话元数据），连接正常关闭。
2. **Given** 同一会话，**When** 不带该 Accept（或 `Accept: application/json`）发消息，**Then** 行为与现状完全一致：阻塞至生成完毕，返回一次性 JSON 统一信封（回归零破坏）。
3. **Given** 流式调用完成，**When** 将全部 token 事件按序拼接，**Then** 与完成事件中的完整回复文本一致；会话历史里落库的回复也与之一致。
4. **Given** 流式调用完成，**When** 查询审计表，**Then** `llm_calls` 与 `tool_invocations` 的写入与非流式调用口径完全一致（流式不改变审计）。
5. **Given** Provider 不支持流式输出（或流式获取失败），**When** 带 Accept 发消息，**Then** 降级为把整段回复作为单个 token 事件推送 + 完成事件，调用方无需感知差异。
6. **Given** 无状态调用端点 `/api/v1/agents/{name}/invoke`，**When** 带 / 不带 `Accept: text/event-stream` 各调一次，**Then** 分流行为与会话消息端点一致（事件协议相同，完成事件的元数据取该端点现有响应口径）。

### User Story 2 - 过程可见与异常有终 (Priority: P2)

Agent 处理一条消息往往要经历多轮「思考 → 调工具 → 再思考」。调用方在事件流里能看到工具调用的开始与结束（工具名、成败），明白 Agent 此刻在干什么而非卡死；工具执行的静默期内连接有心跳保活，不被中间代理掐断。任何一步失败，调用方收到明确的错误事件后连接关闭——事件流永远有终结信号，不会不明不白地断掉。

**Why this priority**: 工具调用可能耗时数十秒（HTTP 请求、Shell 命令），没有过程事件的流式只解决了「LLM 生成期」的等待，解决不了「工具执行期」的黑盒；错误有终是调用方实现可靠客户端的前提。

**Independent Test**: 用会触发工具调用的消息发起流式请求 → 事件流中可见工具开始/结束事件（含工具名）夹在 token 事件之间；用会失败的场景（如 Provider 故障）发起 → 收到错误事件且连接关闭；用长耗时工具场景观察 → 静默期内有周期性心跳。

**Acceptance Scenarios**:

1. **Given** 一条会触发工具调用的消息，**When** 流式发起，**Then** 事件流中出现工具开始事件（含工具名）与工具结束事件（含成败），且与 token 事件的先后顺序反映真实执行顺序。
2. **Given** 处理过程中某步失败（如 Provider 调用异常），**When** 流式进行中，**Then** 调用方收到错误事件（含可读错误信息、不泄露敏感堆栈）后连接关闭；每次流式调用恰好收到一个终结事件（完成或错误，二选一）。
3. **Given** 工具执行静默超过心跳间隔，**When** 流式进行中，**Then** 连接上有心跳信号（不构成业务事件），代理/网关不因空闲断连。
4. **Given** 调用方中途断开连接，**When** 服务端检测到写出失败，**Then** 停止推送但本轮处理照常完成：回复落入会话历史、审计照写（数据一致性不受客户端断开影响）。

### User Story 3 - 自有消费面打字机体验（管理台 + CLI） (Priority: P3)

管理员在管理台的会话聊天页发消息后，Agent 的回复以打字机效果逐段浮现，工具调用过程有可视提示；工程师在终端用 `oryxos chat` 对话时，回复同样逐段打印而非静默等待后整段吐出。体验与主流 AI 对话产品一致。

**Why this priority**: 管理台与 CLI 是流式能力的两个自有消费方，也是最直观的演示面；但它们依赖 US1/US2 的流式能力先就位，且不影响 REST 调用方的价值成立，故排最后。

**Independent Test**: 浏览器登录管理台 → 打开会话聊天页发消息 → 回复逐段浮现（而非一次性出现），工具调用期间有状态提示；断网重进后历史消息完整。终端 `oryxos chat` 发消息 → 回复逐段打印，工具调用期间有单行状态提示，最终完整回复与会话历史一致。

**Acceptance Scenarios**:

1. **Given** 管理台聊天页，**When** 发送消息，**Then** 回复以打字机效果逐段渲染，完成后与刷新页面看到的历史记录一致。
2. **Given** Agent 处理中调用了工具，**When** 打字机进行中，**Then** 页面出现工具调用中的可视提示（工具名），结束后提示消失或标记完成。
3. **Given** 流式过程出错，**When** 错误事件到达，**Then** 页面显示可读的错误提示，输入框恢复可用（不卡死）。
4. **Given** 终端 `oryxos chat` 会话，**When** 发送消息，**Then** 回复逐段打印（打字机效果），工具调用期间有状态提示，处理失败时打印可读错误并回到输入提示符。

### Edge Cases

- 流开始前就能判定的失败（会话不存在、认证未过、请求体非法）：MUST 以普通 JSON 错误响应返回（404/401/400），不进入事件流——调用方按状态码处理，与现状一致。
- 018 认证门禁：无凭据/无效凭据的流式请求与非流式同样被拒（401 JSON）；带有效 API Key 或管理台 session 均可流式调用。
- 已推送部分 token 后发生失败：HTTP 状态已是 200 且不可更改，错误只能以错误事件表达——终结事件语义因此必须严格（恰好一个 done 或 error）。
- 多轮 ReAct（一条消息触发多次 LLM 调用）：多轮的 token 事件连续推送，调用方无需感知轮次边界；完成事件只在整条消息处理完毕后发出一次。
- Provider 流式中断（网络抖动、上游截断）：降级或错误二选一——已收到的部分不足以构成完整回复时发错误事件，绝不把残缺回复当完成。
- 客户端断开后本轮继续执行：消耗的 token 照常计费与审计；不做「断开即中止」（保证会话历史与审计一致性，也避免中断语义侵入核心循环）。
- 同一会话并发消息：维持现状语义（本 feature 不改变会话并发规则），流式与否不影响。
- 心跳不是业务事件：调用方的事件解析器应忽略注释行心跳；契约文档必须写明。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `POST /api/v1/sessions/{id}/messages` 与 `POST /api/v1/agents/{name}/invoke` MUST 按请求 `Accept` 头分流：包含 `text/event-stream` 时以 SSE 事件流响应；否则维持现状一次性 JSON（含响应体结构、状态码、审计写入），回归零破坏。管理台聊天页实际调用的 `POST /api/v1/agents/{name}/session/messages` MUST 同规则分流（FR-013 的载体端点）。三端点共用同一事件协议，`done` 事件的元数据分别取各自现有响应的口径。
- **FR-002**: 流式响应 MUST 采用标准 SSE 线格式（`Content-Type: text/event-stream`，UTF-8，`data:` 行携带 JSON 负载，事件间空行分隔），主流 SSE 客户端（浏览器 EventSource、curl、常见 HTTP 库）无需私有解析逻辑即可消费。
- **FR-003**: 事件类型 MUST 覆盖：`token`（回复文本增量）、`tool_start`（工具名）、`tool_end`（工具名、成败）、`done`（完整回复文本 + 会话元数据）、`error`（可读错误信息）。每次流式调用 MUST 恰好以一个 `done` 或一个 `error` 终结，此后连接关闭。
- **FR-004**: 全部 `token` 事件按序拼接 MUST 等于 `done` 事件中的完整回复文本，且与落库的会话历史一致。
- **FR-005**: LLM 生成期间 MUST 逐段推送 `token` 事件（打字机粒度），不得攒到生成完毕后一次性下发；多轮 ReAct 的多次 LLM 生成连续推送。
- **FR-006**: Provider 不支持流式或流式获取失败但已有完整结果时，MUST 降级为单个 `token` 事件 + `done`（调用方协议不变）；结果残缺时 MUST 发 `error`，不得把残缺内容当 `done`。
- **FR-007**: 事件流静默期 MUST 周期性发送 SSE 注释行心跳（默认 15 秒，可配置），防中间代理断连；心跳 MUST NOT 构成业务事件。
- **FR-008**: 客户端中途断开时，服务端 MUST 停止推送并照常完成本轮处理：回复落入会话历史、`llm_calls`/`tool_invocations` 照写；MUST NOT 因断开产生残缺的会话状态。
- **FR-009**: 流开始前可判定的失败（会话不存在、认证失败、请求非法）MUST 以普通 JSON 错误响应返回对应状态码，不得以 200 + 错误事件表达。
- **FR-010**: 018 认证门禁 MUST 对流式请求同等生效：无凭据/无效凭据 401；有效 API Key 或管理台 session 均可发起流式调用。
- **FR-011**: 流式路径 MUST NOT 改变核心循环的执行模型：ReActLoop 保持同步阻塞（宪法七），不引入 WebFlux/Reactor 编程模型进入核心循环；流式仅是响应写出方式的变化。
- **FR-012**: 审计口径 MUST 与非流式完全一致：每次 LLM 调用写 `llm_calls`（含 token 计数）、每次工具调用写 `tool_invocations`；流式不新增、不省略审计字段。
- **FR-013**: 管理台会话聊天页 MUST 消费事件流实现打字机渲染与工具调用提示；错误事件呈现可读提示且界面可恢复；完成后的展示与刷新后的历史一致。
- **FR-014**: 契约文档 MUST 完整描述事件类型、负载字段、终结语义与心跳约定，作为对外承诺（原则五：接口即承诺）。
- **FR-015**: CLI `oryxos chat` MUST 以打字机方式逐段输出回复（进程内消费同一套流式能力，不经 HTTP），工具调用期间有状态提示；流式能力不可用时回落为现状整段输出，不得报错。

### Key Entities

- **流事件（StreamEvent）**: 一次流式调用中服务端推送的最小单元。类型：`token` / `tool_start` / `tool_end` / `done` / `error`；负载按类型携带文本增量、工具名与成败、完整回复与会话元数据、或错误信息。事件只存在于传输过程，不落库（落库的仍是会话历史与审计记录）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 不带流式声明的调用，响应与本 feature 之前逐字段一致；既有全量测试 100% 通过（回归零破坏）。
- **SC-002**: 长回复场景（生成耗时 ≥ 5 秒），调用方从发出请求到看到首段内容的时间不超过完整生成时间的 30%；用户不再经历「全程空白等待」。
- **SC-003**: 事件序列完整性 100%：每次流式调用恰好一个终结事件；token 拼接与完整回复一致率 100%。
- **SC-004**: 客户端中途断开的调用，会话历史与审计记录完整率 100%（与未断开对照无差异）。
- **SC-005**: 认证门禁对流式路径 100% 生效（无凭据 401，有效凭据放行），018 的全部认证测试在流式场景复验通过。
- **SC-006**: 管理台聊天页打字机效果可用：回复逐段渲染、工具调用有提示、错误可恢复；刷新后历史一致率 100%。
- **SC-007**: 流式与非流式对同一消息的审计写入（记录条数、字段口径）一致率 100%。
- **SC-008**: `oryxos chat` 回复逐段打印（长回复不再整段静默后一次吐出）；无状态调用端点的流式/非流式双路行为与会话消息端点一致（同一验收口径复验通过）。

## Assumptions

- **范围全覆盖（Clarifications 裁决）**：REST 两端点（会话消息 + 无状态调用）均支持 SSE 分流；CLI `oryxos chat` 打字机走进程内流式（直接消费引擎的流式能力，不经 HTTP），三个消费面共享同一套底层能力。
- **断开语义取「继续完成」**：客户端断开后本轮照常执行完毕并落库。理由：保证会话历史与审计一致性；「断开即中止」需要向核心循环注入取消语义，违背「流式不侵入核心循环」的边界。代价（断开后仍消耗 token）明示于契约文档。
- **心跳间隔默认 15 秒**：低于常见代理/网关 30~60 秒的空闲超时，可配置。
- **事件负载用 JSON**：与项目统一响应风格一致；`done` 事件的会话元数据沿用现有非流式响应的数据结构口径。
- **并发规则不变**：同一会话的并发消息处理维持现状语义，本 feature 不引入新的并发控制。
- **依赖**：复用 018 的认证 filter（`/api/v1/*` 模式天然覆盖本端点）；复用现有统一错误信封（流开始前的失败路径）。
