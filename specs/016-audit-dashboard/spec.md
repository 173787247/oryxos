# Feature Specification: 审计查询接口与报表看板（Audit Query & Dashboard）

**Feature Branch**: `016-audit-dashboard`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "业务人员要查看报表。方向：审计查询接口与看板。挂在两张审计表之上（数据 Day One 就在）。"

---

## 1. 背景与目标

### 为什么做

OryxOS 从第一天起就把每次 LLM 调用（`llm_calls`）和工具调用（`tool_invocations`）落库审计（宪法 V），
数据一直在积累，但业务人员**无法查看这些数据的报表**——既没有聚合查询接口，也没有看板页面。
业务人员想知道：Agent 调用了多少次模型、花了多少成本、成功率如何、平均耗时多少、按哪个
Agent / 模型 / 工具分布——这些答案今天都埋在 SQLite 里，只能靠人工翻库。

### 这个特性是什么（一句话）

在两张既有审计表之上，加一层**只读的审计查询接口 + 报表看板**，让业务人员自助查看调用量、成本、
成功率、耗时的汇总与明细，不改变任何现有审计写入链路。

### 做成了长什么样（三个画面）

1. 业务人员打开「报表」页，一眼看到选定时间窗内 LLM 调用次数、总成本、成功率、平均耗时的 KPI 卡片；
2. 业务人员按 Agent / 模型 / 工具看分布，知道哪个 Agent 最活跃、哪个模型 / 工具用得最多；
3. 业务人员点进明细，看到具体某次调用的 provider、模型、token、耗时、成败。

---

## 2. 术语表

| 术语 | 定义 |
|------|------|
| **审计表** | `llm_calls`（LLM 调用）与 `tool_invocations`（工具调用）两张 Day One 落库的审计记录 |
| **成本（金额）** | 一次 LLM 调用消耗的 token 按**具体模型**单价折算出的金额；**写时定格**——调用时算好落库，历史成本不随单价事后变动 |
| **模型定价** | 针对具体模型（provider + model）的输入/输出 token 单价；同一 provider 下不同模型单价不同 |
| **微元** | 成本的存储单位：1 元 = 1,000,000 微元；整数存储，避免浮点累加误差 |
| **未计量** | 因未配置单价或调用失败而无法折算成本的状态，区别于「零成本」 |
| **Agent 维度** | 按「哪个 Agent（profile）」聚合报表；业务人员最关心的归集口径 |
| **时间窗** | 报表的统计区间：近 7 天 / 近 30 天 / 全部 |

**需求用语约定**：MUST = 必须满足；MUST NOT = 必须禁止。FR/US/SC 编号为稳定标识符。

## 3. 范围

### 本期交付

| 范围项 | 说明 |
|--------|------|
| LLM 调用聚合查询 | 次数、总 token、总成本、成功率、平均耗时；可按时间窗 / Agent / 模型 / provider 过滤与分组 |
| 工具调用聚合查询 | 次数、成功率、平均耗时；可按时间窗 / Agent / 工具名过滤与分组 |
| 成本计算与落库 | 为具体模型（provider+model）配置输入/输出 token 单价；LLM 调用时按用量算成本并写时定格落库 |
| 明细下钻查询 | 查看具体某次 LLM 调用 / 工具调用的记录 |
| 报表看板页 | KPI 汇总卡片 + 分布图表 + 明细下钻表格 + 时间窗切换 |

### 明确不做（及去向）

| 不做的事 | 原因 | 去向 |
|----------|------|------|
| 改变现有审计写入链路 | 数据 Day One 已在，只补查询与成本列 | — |
| 审计记录的删除 / 修改 | 只读查询，审计 append-only 可追溯 | 有合规诉求再立项 |
| 成本预测 / 预算告警 / 配额限制 | 超出「看报表」范围 | 后续按需 |
| 引入第三方图表库 | 项目约束：不为漂亮引大型 UI 库盖过 token | 手写 SVG/CSS |
| 工具调用成本折算 | 工具无统一计价模型 | 工具只看次数/成功率/耗时 |
| 分布式 / 多租户隔离 | 单实例核心阶段 | 路线图方向 A |
| 首 token 响应时间（TTFT） | 需流式 API、违反宪法 VII，属扩展阶段 | 扩展阶段再评估 |
| agent 执行链路可观测（langfuse 式 trace） | 需 `llm_call_id` 关联 + trace 树可视化，范围远超成本看板 | 另立独立特性 |

## Clarifications

### Session 2026-08-21

- Q: provider 的 token 单价怎么配置？ → A: 管理台配置，业务人员自助调价、无需重启。
- Q: 单价按什么粒度设置？ → A: 按具体模型名称（provider + model）——同一 provider 下不同模型价格不同，需针对每个模型单独设置（独立 `llm_pricing` 表 + 模型定价 CRUD）。
- Q: 报表响应时间指标用什么？ → A: 仅总耗时（`duration_ms` 的平均值），不做首 token 时间（TTFT，需流式 API、违反宪法 VII，属扩展阶段）。
- Q: LLM 调用失败（拿不到 usage）时成本怎么处理？ → A: 记「未计量」（cost=null）——失败时 `model.call()` 抛异常、无 ChatResponse、usage 为空，精确按 token 算不了，宁可标未计量也不伪装精确；报表标注「含未计量调用」。
- Q: agent 执行链路可观测（类似 langfuse/langsmith）怎么做？ → A: 另立独立特性（需 `llm_call_id` 关联 + trace 树可视化 + 评估），本期 016 只做成本看板。

## 4. User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务人员查看 LLM 调用汇总报表（Priority: P1）

业务人员打开「报表」页，看到选定时间窗内 LLM 调用的 KPI 汇总：总调用次数、总成本、成功率、平均耗时，
以及按模型 / provider 的分布。

**Why this priority**: 这是业务人员最直接的问题「模型花了多少、用得多不多」，也是本特性的核心价值。

**Independent Test**: 预置若干条 `llm_calls` 记录，调聚合查询接口，断言次数/成本/成功率/耗时正确；看板页正确渲染 KPI 卡片。

**Acceptance Scenarios**:

1. **Given** 时间窗内有 10 次 LLM 调用（8 成功 2 失败），**When** 查询汇总，**Then** 次数=10、成功率=80%、平均耗时正确。
2. **Given** 配置了单价的 provider 有 N 次调用，**When** 查询总成本，**Then** 总成本 = Σ(每次调用按当时单价算出的成本)。
3. **Given** 调用跨多个模型，**When** 按模型分组，**Then** 每个模型的次数 / 成本正确归集。

---

### User Story 2 - 业务人员查看工具调用汇总报表（Priority: P1）

业务人员看到工具调用的汇总：调用次数、成功率、平均耗时，以及按工具名的分布。

**Why this priority**: 工具调用是 Agent 真实动作，业务人员要知道 Agent 在干什么、干得顺不顺。

**Independent Test**: 预置 `tool_invocations` 记录，调聚合接口断言次数/成功率/耗时正确。

**Acceptance Scenarios**:

1. **Given** 时间窗内有若干工具调用（含失败），**When** 查询汇总，**Then** 次数、成功率、平均耗时正确。
2. **Given** 跨多个工具，**When** 按工具名分组，**Then** 每个工具的调用量正确归集。

---

### User Story 3 - 成本计算与写时定格落库（Priority: P1）

为具体模型配置输入 / 输出 token 单价后，每次 LLM 调用按用量算出成本并落库；历史成本不随单价事后变动。

**Why this priority**: 「要算成本」是本特性的关键诉求，且写时定格是成本可信的前提。

**Independent Test**: 配置单价后触发 LLM 调用，断言 `llm_calls` 落库了正确成本；改价后历史记录成本不变。

**Acceptance Scenarios**:

1. **Given** 模型单价为输入 1 元/百万 token、输出 2 元/百万 token，**When** 一次调用消耗 1000 输入 + 2000 输出 token，**Then** 成本 = 1000×1 + 2000×2 = 5000 微元（=0.005 元）。
2. **Given** 某次调用已落库成本，**When** 之后修改模型单价，**Then** 该历史记录的成本不变。
3. **Given** 未配置单价的 provider 或调用失败，**When** 落库，**Then** 成本记为「未计量」，不误记为零。

---

### User Story 4 - 按 Agent 下钻（Priority: P2）

业务人员按「哪个 Agent」查看各自的调用量和成本。

**Why this priority**: 业务人员按 Agent 归集是核心口径，但依赖成本落库时冗余 Agent 归属，故列 P2。

**Independent Test**: 预置多个 Agent 的调用记录，按 Agent 聚合断言归集正确（含无状态 invoke 的调用）。

**Acceptance Scenarios**:

1. **Given** 两个 Agent 各有若干 LLM 调用，**When** 按 Agent 聚合，**Then** 各自调用量与成本正确归集。
2. **Given** 一次无状态调用（不落 sessions 表），**When** 聚合，**Then** 该调用仍能归到发起它的 Agent（不丢失、不成孤儿）。

---

### User Story 5 - 明细下钻（Priority: P2）

业务人员从汇总点进明细，查看具体某次调用的记录。

**Why this priority**: 汇总回答「多少」，明细回答「是哪次」，是看板闭环的最后一环。

**Independent Test**: 调明细查询接口，断言返回具体记录字段正确。

**Acceptance Scenarios**:

1. **Given** 某次 LLM 调用，**When** 查明细，**Then** 返回 provider、模型、token、耗时、成败、成本、时间、所属 Agent。
2. **Given** 某次工具调用，**When** 查明细，**Then** 返回工具名、耗时、成败、时间、所属 Agent。

---

### Edge Cases

- **空数据**：时间窗内无任何调用，聚合返回零值而非报错；看板显示空态。
- **成本未计量**：未定价 / 失败调用的成本为「未计量」，聚合时被忽略（不当作 0 计入总额），看板明确标注「含未计量调用」。
- **存量数据**：迁移后历史行新列（成本、Agent 归属）为 null，看板显示「未计量 / 未归属」，不崩。
- **时间窗边界**：`from`/`to` 为闭区间或半开区间须定义一致；`from > to` 返回空或明确报错。
- **单价为 0 或非法**：单价为 0 视为「免费」；负值 / 非法值在配置时拒绝。
- **超大时间窗（全部）**：万级调用聚合在可接受时间内完成（Java 内存聚合 + 时间窗索引）。

## 5. Requirements *(mandatory)*

### Functional Requirements

> 分组：A 查询接口 → B 成本计算 → C Agent 归属 → D 看板。

**A. 查询接口**

- **FR-001**: 系统 MUST 提供 LLM 调用聚合查询接口，返回选定时间窗内的调用次数、总 token（输入/输出/合计）、总成本、成功率、平均耗时；MUST 支持按时间窗过滤，按模型 / provider / Agent 分组。
- **FR-002**: 系统 MUST 提供工具调用聚合查询接口，返回选定时间窗内的调用次数、成功率、平均耗时；MUST 支持按时间窗过滤，按工具名 / Agent 分组。
- **FR-003**: 系统 MUST 提供 LLM 调用与工具调用的明细查询接口，可下钻查看单条记录（含时间、Agent、provider/模型/工具名、token/耗时、成败、成本）。
- **FR-004**: 聚合查询 MUST 为只读，MUST NOT 提供对审计记录的任何删除 / 修改路径。

**B. 成本计算（写时定格）**

- **FR-005**: 系统 MUST 允许通过管理台为**具体模型（provider + model）**配置输入 / 输出 token 单价（元/百万 token），配置后即时生效、无需重启。
- **FR-006**: 每次 LLM 调用 MUST 在落库时按「当时单价 × 用量」计算成本并写时定格；MUST 采用微元整数（1 元 = 1,000,000 微元），计算全程无浮点累加误差。
- **FR-007**: 未配置单价或调用失败的成本 MUST 记为「未计量」，MUST NOT 误记为零；聚合总额 MUST 忽略未计量项，看板明确标注。
- **FR-008**: 修改模型单价 MUST NOT 影响已落库的历史成本。

**C. Agent 归属**

- **FR-009**: LLM 调用与工具调用记录 MUST 冗余其所属 Agent（profile）标识，使按 Agent 聚合无需依赖会话表关联；无状态调用的审计记录 MUST 同样能归属到发起它的 Agent（不成孤儿）。

**D. 报表看板**

- **FR-010**: 看板页 MUST 展示 KPI 汇总卡片（LLM 调用次数、总成本、成功率、平均耗时；工具调用次数、成功率、平均耗时）。
- **FR-011**: 看板页 MUST 展示分布图表（按模型 / provider / 工具名 / Agent），图表 MUST 手写实现，MUST NOT 引入第三方图表库。
- **FR-012**: 看板页 MUST 展示明细下钻表格，可从汇总点进单条记录。
- **FR-013**: 看板 MUST 支持时间窗切换（近 7 天 / 近 30 天 / 全部）。

### Key Entities

- **LLM 调用记录（llm_calls）**: 既有审计实体，本次新增「成本（微元，可空=未计量）」与「所属 Agent（profile）」两个属性；其余字段（provider、model、token、success、耗时、时间）不变。
- **工具调用记录（tool_invocations）**: 既有审计实体，本次新增「所属 Agent（profile）」属性；其余字段（工具名、耗时、success、时间）不变。
- **模型定价（llm_pricing）**: 每个具体模型（provider + model）的输入 / 输出 token 单价（元/百万 token），可配置、可修改，仅影响之后的新调用。

## 6. Success Criteria *(mandatory)*

- **SC-001**: 成本换算正确：`1 元/百万 token × 1000 token == 1000 微元`，含舍入边界与 null 分支（CI 断言）。
- **SC-002**: 聚合查询对预置数据返回正确的次数、成功率、平均耗时、总成本（CI 断言）。
- **SC-003**: 写时定格生效：修改单价后，历史记录成本不变（CI 断言）。
- **SC-004**: 按 Agent 聚合归集正确，无状态调用能归属到 Agent（CI 断言）。
- **SC-005**: 存量数据迁移后启动不崩，历史行成本 / Agent 归属显示「未计量 / 未归属」（迁移测试）。
- **SC-006**: 看板页在选定时间窗内正确展示 KPI 卡片、分布图表与明细下钻，时间窗切换生效（人工验收）。

## 7. Assumptions

- **规模假设**：单实例审计数据量级（万级调用），Java 内存聚合 + 时间窗索引足够，无需 SQL GROUP BY。
- **成本单位**：微元整数；单价「元/百万 token」恰好等于「微元/token」，故成本 = round(token × 单价)。
- **币种**：成本单位与配置单价一致（国内 provider 即人民币），系统不做汇率换算。
- **时间窗档位**：近 7 天 / 近 30 天 / 全部三档；接口层支持任意 `from`/`to`。
- **图表示现**：手写 SVG/CSS，遵守「不为漂亮引大型 UI 库」的项目约束。
- **宪法遵从**：同步执行 + 虚拟线程；审计写入链路不变；无新凭证；schema 变更走手工 DDL（SQLite `ALTER TABLE` 弱）。
- **模块落位**：成本与 Agent 归属的契约放 `oryxos-core`（依赖倒置），持久化与迁移放 `oryxos-storage`，成本计算放 `oryxos-provider`，查询接口与看板放 `oryxos-web`（详见 plan）。

## 8. 依赖与风险

| 类型 | 事项 | 影响 | 缓解 |
|------|------|------|------|
| 迁移风险 | `providers`/`llm_calls`/`tool_invocations` 加列（SQLite ALTER 弱） | 存量库启动崩溃 | 手工 DDL + 专门升级器（沿用 `ScheduleSchemaUpgrade` 模式）；新列可空 |
| 成本口径 | 无状态调用（`invoke-exec:`）不落 sessions 表 | 若走 join 会丢行 | 写入时冗余 Agent 归属（FR-009），不 join |
| 数据正确性 | 成本「未计量」与「零」混淆 | 报表失真 | 未计量记 null，聚合忽略并标注 |
| 存量成本 | 历史调用无成本数据 | 历史报表成本缺失 | 历史行标「未计量」，仅新调用可计量 |
