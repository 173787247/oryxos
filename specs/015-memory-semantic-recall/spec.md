## 1. 背景与目标

### 为什么做

Agent 的长期记忆目前只能「按字面找回」：`recall_memory` 在归档区做简单关键词匹配（且 markdown 与
sqlite 两档的大小写行为不一致）。用户上周说「发布流程在灰度环节踩了雷」，这周问「上次那个部署的坑
后来怎么处理的」——没有共同关键词，记忆找不回来。这是核心阶段的刻意克制（记忆行为契约四），
路线图方向 B 约定：知识检索基建就位后升级。

同时，记忆的可插拔接口（`LongTermMemoryStore` 三档）还停留在上一代水平：没有能力声明、没有跨档
行为契约测试，外部记忆服务档（mem0）是未经实测的骨架。014 在知识域验证了成熟的插件范式（契约
必选项 + 能力逐项声明 + 桩验三同），本特性把记忆后端对齐到同一范式——**知识与记忆共用一套插件
哲学，底座心智模型只剩一个**；并以设计约束的形式为分布式部署（路线图方向 A）预留：记忆状态全部
外置、索引可重建，分布式时不需要重做记忆。

### 这个特性是什么（一句话）

让 `recall_memory` 从「字面匹配」升级为「语义 + 关键词 + 时间新近的三路融合检索」，同时把记忆
后端升级为带能力声明的插件契约（本地档内置检索、外部服务档整体接管）——未配置向量化的部署行为
与今天一致，零配置、零破坏；本期同时把 mem0 档真实跑通（外部记忆服务路线的首个落地档），将来接百炼或走分布式，都不再动记忆的需求层。

### 做成了长什么样（三个画面）

1. 用户问 Agent「我上次说的那个部署问题后来怎么解决的」，记忆里写的是「发布流程在灰度环节踩雷，
   回滚后改为分批放量」——措辞完全不同，语义召回命中；且同等相关时，上周的记忆排在三年前的前面；
2. 管理员什么都不用配：已为知识库配了向量化的部署，记忆检索自动同享；没配的，一切照旧；
3. 企业已有 mem0 这类记忆服务：切换后端档之后，`save_memory`/`recall_memory` 两个工具、
   审计、分区语义完全不变——本期在自托管 mem0 OSS 上真实跑通这条路（换脑不换脸），百炼等
   其他服务将来照同一契约挂入。

## 2. 术语表

| 术语             | 定义                                                                        |
| -------------- | ------------------------------------------------------------------------- |
| **核心区 / 归档区**  | 长期记忆两分区（既有）：核心区全量注入每轮 prompt、永不截断；归档区注入截断、检索找回。**检索（含本特性）只作用于归档区**。         |
| **记忆条目**       | `save_memory` 写入的一条记录（既有）。一条记忆 = 一个向量，不切分。                                 |
| **三路召回 / 融合**  | 语义（向量）、关键词、时间新近三路并行取候选，按名次融合排序（RRF，与知识检索同款机制、多一路时间维度）。                    |
| **降级**         | 向量化不可用/未配置时，检索退回「关键词 + 时间新近」两路（即修正大小写后的现状行为增强版）。                           |
| **记忆向量索引**     | 归档区条目的向量副本，派生数据——可从记忆本体全量重建，与本体同库存储，不是第二份记忆。                              |
| **检索能力三态**     | 记忆后端对检索方式的声明：KEYWORD（仅关键词）/ HYBRID_BUILTIN（条目交底座内置流水线）/ DELEGATED（后端自带语义，整体接管）。分区语义（core/archival）不在声明之列——它是必选能力，映射不了的后端装配期即拒绝。 |

**需求用语约定**：MUST = 必须满足；MUST NOT = 必须禁止。FR/US/SC 编号为稳定标识符。

| 分布式实现本身            | 本期只留约束不做实现                                 | 路线图方向 A（v0.4）    |

## Clarifications

### Session 2026-08-19

- Q: embedding 配置键归属？ → A: 新增全局 `embedding.provider/model` 段，`knowledge.embedding.*` 作兼容别名。
- Q: sqlite 档 memory_entries 无 Agent 维度的既有缺口？ → A: 随本特性补 `agent_name` 列修复（手工 DDL）；存量行归全局占位。
- Q: 降级可观测性？ → A: 仅工具结果与审计埋点标注，管理台状态条不做。

### Session 2026-08-20（多轮讨论收敛）

- Q: 检索双路还是三路？ → A: 三路——语义 + 关键词 + **时间新近**。时间性是记忆区别于知识的本质维度（业界 relevance×recency 共识）；RRF 按名次融合天然多路，加一路零调参。
- Q: 关键词大小写两档不一致？ → A: 借本特性统一为不区分大小写；SC-002 兼容措辞相应放宽。
- Q: 记忆后端契约是否随本特性对齐 014 范式？ → A: 对齐——检索能力三态声明 + 分区语义校验 + 参数化契约测试 + 外部桩验三同；真实外部服务联调独立成 016。
- Q: 记忆路线定位？ → A: 本地语义为默认档（append-only 可审计、数据不出域），外部记忆服务为可选 DELEGATED 档——业界两条路线（文件式/记忆服务）各占一档，不二选。
- Q: 分布式怎么进 spec？ → A: 作为设计约束条款（FR 组 E），不作为交付。
- Q: 真实 mem0 联调是否并入本期？ → A: **并入**——「mem0 也跑通」为 015 的验收目标之一（维护者拍板 2026-08-20）；契约桩仍保留（CI 无 docker 也能跑），真实联调打 integration 标签按需执行；百炼等其他服务仍为后续。
- Q: 记忆条目的管理面编辑/删除？ → A: **暂不做**（维护者拍板「先放着，貌似也没必要」）；同时拍板 Agent 侧永不提供删除记忆工具（prompt 注入可诱导抹除 + 与 append-only 可审计主张冲突）——将来若有合规诉求，遗忘走管理面、人拍板留审计。
- Q: 记忆配置（backend/embedding/权重）要不要管理台化？ → A: 不做——维持 yml + 重启；切档属重大部署决策，权重调优等埋点数据。
- Q（R3）: 三路融合权重？ → A: 缺省等权，但权重留为配置系数（加权 RRF），后续手动可调、无需改码（维护者拍板）。
- Q（R4）: 关键词大小写统一？ → A: 确认统一为不区分大小写——FR-002 定案，SC-002 的兼容例外措辞维持（维护者拍板）。
- Q（R2）: 外部档不支持分区时装配期拒绝还是降维？ → A: **装配期拒绝，删除降维分支**。调研依据：mem0 经「infer:false 原文模式 + metadata 过滤」可完整映射两区（core 原文常驻、archival 交提炼），百炼有等价维度——「映射不了」是假想场景；降维会静默破坏契约二，fail-fast 符合「不静默失败」原则（research D8）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 终端用户：按意思找回记忆，近事优先（Priority: P1）

用户用不同措辞提起旧事，Agent 语义召回命中；精确代号靠关键词路保底；同等相关时最近的记忆排在
更前（「上次」的直觉）。用户感知只是「这个 Agent 记性变好了」。

**Independent Test**: 手工写入归档记忆（语义相近措辞不同 / 含精确代号 / 内容相似但时间不同三类），
经 `recall_memory` 验证三路召回与融合排序。

**Acceptance Scenarios**:

1. **Given** 归档区有「发布流程在灰度环节踩雷，回滚后改为分批放量」，**When** 检索「上次部署出的问题怎么解决的」，**Then** 该条目被召回（语义路，无共同关键词）。
2. **Given** 归档区有含工单号「OPS-4721」的条目，**When** 检索「ops-4721」，**Then** 该条目被召回（关键词路，统一不区分大小写）。
3. **Given** 两条与查询相关性相当、写入时间相差数月的条目，**When** 检索，**Then** 较新条目排序在前（时间新近路生效）。
4. **Given** 检索与任何记忆无关的内容，**Then** 返回「没有找到相关记忆」，不编造。
5. **Given** 任意一次 `recall_memory` 调用，**Then** 照旧入工具审计，埋点含查询原文、命中明细、降级标记、耗时。
6. **Given** 两个 Agent 各有记忆，**When** 任一 Agent 检索，**Then** 只命中自己的，绝不跨 Agent。

### User Story 2 - Agent 作者/管理员：零配置升级、完全向后兼容（Priority: P1）

已有部署升级后：配了向量化（与知识库同一份全局配置）的，记忆检索自动变聪明、存量记忆自动补索引；
没配的，`recall_memory` 行为与升级前一致（唯一例外：关键词大小写统一修正）——不报错、不变慢、
无迁移动作。

**Acceptance Scenarios**:

1. **Given** 未配置向量化的部署，**When** 升级后调用 `recall_memory`，**Then** 除大小写统一修正外，结果与升级前一致（CI 断言）。
2. **Given** 已配置向量化、存量 N 条归档记忆的工作区，**When** 服务启动，**Then** 30 秒内存量条目全部可被语义检索（对账补索引）。
3. **Given** 向量化模型/维度变更，**When** 服务启动，**Then** 记忆索引自动重建，不混比新旧向量（记忆量小，无需手动重建入口）。
4. **Given** 向量化服务故障期间，**When** Agent 调 `save_memory`，**Then** 记忆 100% 落库成功（标记待索引，恢复后对账补齐）；同期 `recall_memory` 自动降级两路（关键词 + 时间）并标注。
5. **Given** `knowledge.embedding.*` 旧键配置的存量部署，**When** 升级，**Then** 配置继续生效（兼容别名），知识与记忆共享同一份向量化配置。

### User Story 5 - 平台管理员：真实 mem0 跑通（Priority: P2）

在自托管 mem0 OSS（docker，数据不出域）上把 DELEGATED 档真实跑通：按 research D8 的映射方案

4. **Given** 契约参数化测试套件，**When** 挂入 mem0 档执行，**Then** 全档行为不变量逐项通过（与本地档同一套断言）。

### Edge Cases

- **一致性取舍与知识相反**：知识导入可显式失败（源文件在，可重试）；记忆写入是对话副作用，丢了不可恢复 → 条目落库永远优先，索引异步补齐；关键词路天然覆盖未索引条目——追齐窗口零召回损失。
- **降级中途发生**：单次检索中向量化超时/报错 → 该次退回两路（关键词 + 时间）并标注，对话不中断。
- **超长条目**：截断后向量化，召回返回完整原文。
- **空归档区**：返回「没有找到相关记忆」（现状不变）。
- **后端档切换**：markdown/sqlite 间切换后按当前档条目重建索引；DELEGATED 档不产生本地索引。
- **多副本对账**（分布式就绪）：两个实例同时对账 MUST 收敛到一致状态，不产生重复索引或互相覆盖。

## Requirements *(mandatory)*

### Functional Requirements

> 分组：A 检索升级 → B 写入与索引 → C 后端契约 → D 兼容与作用域 → E 分布式就绪约束。

**A. 检索升级**

- **FR-001**: `recall_memory` MUST 升级为三路召回（语义 + 关键词 + 时间新近）+ 加权名次融合：三路权重 MUST 为配置系数、缺省等权（1:1:1），改配置即可手动调整、无需改码；范围仍限归档区；工具名、参数、返回形态 MUST 不变（完全向后兼容）。
- **FR-002**: 关键词路 MUST 跨后端档统一为不区分大小写（修正 markdown/sqlite 现状不一致）。
- **FR-003**: 向量化不可用/未配置时 MUST 自动降级为「关键词 + 时间新近」两路并在结果中标注；恢复后自动回到三路，无需干预。
- **FR-004**: mock provider MUST 提供确定性向量使全链路可在 CI 稳定断言（复用 014 mock）。

**B. 写入与索引**

- **FR-005**: `save_memory` MUST 先落记忆本体再异步向量化；**仅归档（archival）条目入向量索引，core 条目 MUST NOT 入索引**（核心区不参与检索，契约四）；向量化失败 MUST NOT 使写入失败或丢条目（标记待索引，随对账补齐）。
- **FR-006**: 记忆向量索引 MUST 为派生数据：与记忆本体同库存储、可随时全量重建；删除索引 MUST NOT 影响本体与核心区注入。
- **FR-007**: 服务启动 MUST 对账归档条目与索引（补缺失、清孤儿）；向量模型/维度不一致 MUST 自动重建，MUST NOT 混比新旧向量；对账 MUST 幂等。
- **FR-008**: `save_memory` 的分区参数说明 MUST 讲清两区语义与取舍依据（core = 少量常驻事实，每轮在场；archival = 一般值得记的事件，检索找回；不确定填 archival）；工具名与参数结构不变（仅文案增强）。

**C. 后端契约（对齐 014 插件范式）**

- **FR-009**: 记忆后端 MUST 以带能力声明的契约挂载：检索能力三态（KEYWORD / HYBRID_BUILTIN / DELEGATED）；**分区语义（core/archival）为记忆后端的必选能力**——无法完整映射分区的后端 MUST 在装配期被可读拒绝，MUST NOT 提供降维路径或以运行时异常暴露（Clarify-R2，调研依据 research D8）。
- **FR-010**: 全档 MUST 共守行为不变量：核心区永不截断、scope 显式、写入落库优先、per-Agent 作用域、审计埋点统一形态、降级可读；同一套参数化契约测试覆盖本地各档与外部桩。
- **FR-011**: DELEGATED 档 MUST 整体接管检索（底座不叠加本地向量索引），且与本地档保持三同（同工具、同审计、同分区语义）；分区映射方式由适配器实现（mem0 类服务经「原文模式 + 元数据过滤」映射，见 research D8），映射保真度由参数化契约测试钉死。
- **FR-012**: 记忆行为契约修订 MUST 同步文档：契约四由「只做简单关键词」修订为「三路可降级，降级态即统一后的关键词行为」；契约一/二/三不变。
- **FR-017**: mem0 档 MUST 按映射方案（research D8）真实跑通：core = 原文模式（不经提炼）+ 元数据分区，archival = 交 mem0 提炼；检索与注入取数 MUST 按分区过滤且过滤有效性经实测验证（含已知 filter 版本问题）；同时修复现有适配器缺陷（检索未按分区过滤、写入未区分原文/提炼模式）。
- **FR-018**: mem0 联调环境 MUST 以 docker compose 清单交付、可复现；真实联调集成测试 MUST 打 integration 标签（CI 默认排除，本地/夜间按需执行）——契约桩测试仍常驻 CI，保证无外部依赖也能验证契约面。

**D. 兼容与作用域**

- **FR-013**: 未配置向量化的部署 MUST 保持升级前行为（除 FR-002 大小写修正外逐项一致）；配置缺失静默处于降级态，不告警刷屏，审计埋点可查。
- **FR-014**: 索引与检索 MUST 按当前 Agent 圈定作用域；sqlite 档 `memory_entries` MUST 补齐 `agent_name` 列（手工 DDL；存量行归全局占位并给可读迁移说明），修复后与 markdown 档 per-Agent 语义一致。
- **FR-015**: 向量化配置 MUST 升格为全局 `embedding.provider/model` 段（知识与记忆共用），`knowledge.embedding.*` MUST 作为兼容别名继续生效。

**E. 分布式就绪约束（设计约束，本期不做分布式实现）**

- **FR-016**: 记忆本体与向量索引 MUST 全部外置于共享存储（sqlite 档同库随 DB 走）；MUST NOT 引入任何实例内不可外置的记忆状态；对账 MUST 幂等（多副本同时执行收敛一致）；markdown 档 MUST 在文档中显式定位为单机档，分布式部署推荐 sqlite（共享 DB）或 DELEGATED 档。

### Key Entities

- **记忆向量索引条目**: 归档条目的向量副本；属性：条目标识、所属 Agent、向量、向量模型标识与维度、写入时间（时间新近路依据）、索引状态。派生数据，可全量重建。
- **记忆后端能力声明**: 检索能力三态；分区语义为必选能力，装配期校验（无法映射即可读拒绝），运行时按声明路由。

## Success Criteria *(mandatory)*

- **SC-001**: 语义找回：10 组「措辞不同、语义相近」记忆-查询对，语义路召回 ≥ 8（真实向量化模型人工评审，软指标不阻塞）。
- **SC-002**: 向后兼容：未配置向量化的部署，除大小写修正外，`recall_memory` 升级前后对同一输入返回一致（CI 断言）。
- **SC-003**: 精确匹配不回退：含精确代号查询召回不劣于升级前（关键词路保底，CI 断言）。
- **SC-004**: 时间新近生效：相关性相当、时间不同的条目，较新者排前（确定性构造，CI 断言）。
- **SC-005**: mock 全链路确定可重复（CI 断言）。
- **SC-006**: 存量补索引：启动 30 秒内全部存量归档条目可语义检索。
- **SC-007**: 写入零丢失：向量化故障期间 `save_memory` 100% 落库成功。
- **SC-008**: 万条归档规模单次检索 1 秒内。
- **SC-009**: 外部桩三同逐项核验通过：同工具/同审计/同分区语义；无法映射分区的后端 100% 在装配期被可读拒绝。
- **SC-010**: 后端档切换（markdown ↔ sqlite ↔ 桩 ↔ mem0）不改上层任何行为契约（参数化契约测试全档全绿；mem0 档打 integration 标签）。
- **SC-011**: 真实 mem0 跑通：两区映射保真（core 原文逐字注入 / archival 提炼后语义可命中）、分区过滤实测有效、停机时检索与写入均可读呈现——US5 四场景逐项通过。

## Assumptions

- **规模假设**：单 Agent 归档记忆万条以内；超出与知识同承接路径（可插拔存储换档）。
- **条目不切分**：一条记忆 = 一个向量；超长截断向量化、召回返回完整原文。
- **融合权重**：三路缺省等权（1:1:1），权重为配置系数（加权 RRF：Σ wᵣ/(K+rankᵣ)）；具体配置键名在 plan 定，等权缺省下行为与无权重版完全一致。
- **配置缺失语义**：`embedding.*` 未配置时静默降级态，审计埋点可查。
- **返回上限**：已配置向量化时融合结果截断至可配置 top-k（缺省 20，键名在 plan 定）；未配置模式不截断（保 SC-002 字节级兼容）。
- **宪法遵从**：同步执行 + 虚拟线程；审计照旧；无新凭证；schema 变更手工 DDL。
