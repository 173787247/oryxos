# Research: 可插拔存储（Pluggable Storage）

**Feature**: 025-pluggable-storage | **Date**: 2026-09-03

两路摸底已完成：存量存储面逐文件盘点（18 张表 / 5 个升级类 / 全部 SQLite 专有面精确到行号）与 PG 测试路径环境实证（实际下载依赖、实际起停嵌入式 PG、实际跑通两库 Flyway 迁移）。以下裁决全部有实证依据。

## R1 迁移语义：统一幂等序列，不做 baseline 分叉

**Decision**: `baseline-on-migrate=true` + `baseline-version=0`——存量库与新库走**完全相同**的迁移序列 V1~V5：V1 = 现 schema.sql 原样平移（`CREATE TABLE IF NOT EXISTS` 保留），V2~V5 = 四个结构升级类的幂等逻辑平移为 Flyway **Java migration**（列存在性检查照旧）。V6 起的新迁移才写非幂等的干净 SQL（history 表保证恰好一次）。

**Rationale**: 存量库状态多样（可能停留在任意旧版本、缺任意后加列），现状靠「IF NOT EXISTS + 幂等补列」任意状态收敛——这个语义直接平移进 Flyway 最小惊讶，且存量/新库无路径分叉（分叉 = 测试面翻倍）。`baseline-version=0` 使存量库 baseline 后仍执行全部 V1+，幂等性自保安全。

**Alternatives considered**: ① V1 = 完整最终结构 + 存量库 baseline 到 V1——存量库实际缺列时结构与 history 脱节，需要额外收敛器，被否；② 纯 .sql 化四个升级类——SQLite 无 `ADD COLUMN IF NOT EXISTS`、Schedule 升级含 UUID 生成与 Java Map 键映射（`ScheduleSchemaUpgrade.java:249-316`），纯 SQL 不可表达，被否。

## R2 升级类处置：四个结构类退役进 Flyway，SecretMigration 保留为启动 Bean

**Decision**:
- `AuditSchemaUpgrade` / `MemorySchemaUpgrade` / `ScheduleSchemaUpgrade` / `NotifyChannelSchemaMigration` → 逻辑平移为 V2~V5 Java migration（`io.oryxos.storage.migration` 包，经 Spring Boot 的 `JavaMigration` bean 自动收集，仅 SQLite url 下注册——PG 无存量库不需要），原类删除；`llm_pricing` 双份 DDL（schema.sql:169 与 AuditSchemaUpgrade.java:106）在平移时去重。
- `SecretMigration`（022）**不进 Flyway**：它是数据 + 安全逻辑（主密钥守卫拒启 + AES 加密回写），依赖 cipher/Jackson，保留为启动 Bean，`@DependsOn` 锚点从 `dataSourceScriptDatabaseInitializer` 改为 Flyway 初始化 Bean。
- `spring.sql.init.mode` 关闭，schema.sql 移入 `db/migration/sqlite/V1__baseline.sql`——现状 5 处散落副作用（含 1 个跑在 refresh 之后的 CommandLineRunner 时序泥潭，`SecretMigration.java:98-107` 为此打的容错补丁一并拆除）收敛为单一 Flyway 序列。

**Rationale**: 盘点确认 4 个结构类幂等依据全是 `PRAGMA table_info`（仅 SQLite 语义），平移为 SQLite-only Java migration 不需要跨方言化；SecretMigration 的密钥守卫必须能拒启且逻辑不属于 schema 演进。

## R3 vendor 双轨：`{vendor}` 占位符 + sqlite/postgresql 双目录

**Decision**: `spring.flyway.locations=classpath:db/migration/{vendor}`。**已实证**（反编译 spring-boot-autoconfigure 3.5.16 `FlywayAutoConfiguration$LocationResolver`）：占位符按 `DatabaseDriver.getId()` 展开，SQLite = `sqlite`、PG = `postgresql`。PG 目录只有 `V1__baseline.sql`（完整最终结构一步到位，无存量历史故无 V2~V5），SQLite 目录 V1 + Java V2~V5。

**PG baseline 转写规则**（盘点定位的全部专有面）：14 处 `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`；7 处 `BOOLEAN NOT NULL DEFAULT 1/0` → `DEFAULT TRUE/FALSE`；2 处 `BLOB` → `BYTEA`；`REAL`（llm_pricing 价格两列）→ `DOUBLE PRECISION`；其余（TEXT/VARCHAR/TIMESTAMP/UNIQUE/索引）可原样。实体侧零改动：14 个实体全部 `GenerationType.IDENTITY` 两库通用，`@Query` 原生 SQL 0 处、JPQL 2 处均无方言依赖（`MemoryEntryRepository` 的 LOWER 双压是既有跨方言防御）——这是本刀最大的有利条件。

## R4 Flyway 依赖：SQLite 内置于 core，PG 加一个插件模块

**Decision**: 新增 `org.flywaydb:flyway-core` + `org.flywaydb:flyway-database-postgresql`（版本均由 Boot 3.5.16 BOM 管到 **11.7.2**）+ `org.postgresql:postgresql`（42.7.11，BOM 管）。三者都打进 fat jar（PG 是部署选项，即开即用不换包）。

**Rationale（实证）**: `flyway-database-sqlite` **不存在**（Maven Central search `numFound: 0`，dependency:get 实测失败）；SQLite 支持内置在 flyway-core 11.7.2（jar 内含 `SQLiteDatabaseType` 并经 ServiceLoader 注册，离线模式实跑 SQLite 迁移成功铁证）。PG 支持 Flyway 10+ 拆分为独立插件，必须显式加。阿里云镜像三个构件均实测可达（但极慢——CI 必须缓存 ~/.m2）。

## R5 PG 测试路径：zonky 嵌入式 PG（本环境唯一可行，已端到端实证）

**Decision**: `io.zonky.test:embedded-postgres:2.0.7`（test scope）作为「同套业务测试两库全绿」的执行载体，本地与 CI 门禁同构。

**Rationale（实证，2026-09-03）**: 宿主机无 PG（psql/pg_ctl 不存在、5432 无监听）；docker 命令缺失（WSL integration 未开）→ 宿主机 PG 与 testcontainers 两条路**本机均不可用**。zonky 实测：依赖可下（linux-amd64 二进制 14.5MB 已入 ~/.m2）、启动 1658ms / 停止 140ms / 随机端口、JDBC + `flyway-database-postgresql` 迁移全链路 2s 内跑通（PG 14.10 on WSL2）；同套机制对 SQLite 离线迁移 306ms 同绿。**spec 假设的「plan 阶段先行验证」已完成**。

**Alternatives considered**: 宿主机 PG（不可用）；testcontainers（jar 可下但 docker 缺失，可作 CI 侧「真 PG 16 官方镜像」可选 job，不作为开发者本地必经路径）。注：zonky 2.0.7 默认二进制 PG **14.10**；如需对齐 PG 16 可引 `embedded-postgres-binaries-bom` 覆盖（构件存在未单独实测）——本刀先用默认 14，版本对齐留部署文档声明「支持 PG 14+」。

## R6 配置面：vendor 自动适配，SQLite 专属项不再锁死

**Decision**: 主 application.yml 保留 SQLite 默认（url/driver/WAL/busy_timeout 现状不动，零配置零变化）；新增一个 `EnvironmentPostProcessor`（storage 模块）按 `spring.datasource.url` 前缀做 vendor 适配：`jdbc:postgresql:` 时清除 SQLite 专属默认（`journal_mode`/`busy_timeout` 两个 hikari data-source-properties、`database-platform=SQLiteDialect`）、driver 交给 Boot 按 url 自动推导。配置模板补 PG 示例段（url + username + `${ORYXOS_DB_PASSWORD}` 环境变量占位）。

**Rationale**: 盘点确认 `driver-class-name`/`database-platform` 锁死在 jar 内 yml 且模板未暴露；SQLite 的 hikari `data-source-properties` 若原样合并给 PG 驱动是未定义行为——必须按 vendor 条件化，且不能要求用户手工「反配」这三项（易错面）。用户视角：配一个 PG url + 凭证即可，库类型自动识别（FR-006）。

**Alternatives considered**: Spring profile（`application-postgres.yml` + 手动激活）——多一个用户必须知道的开关，违背「按 url 自动选择」的 spec 要求，被否。

## R7 CLI 轻命令与测试基建的 SQLite 硬编码收口

**Decision**:
- 3 个裸连 SQLite 的 CLI 轻命令（`KnowledgeCommand:38-40`、`SessionListCommand:29-31`、`StatusCommand:19`）：改为从外部配置（`config/application.yml` 合并链）解析 datasource url 后 `DriverManager` 直连——其 SQL 本身已是标准语法两库通用；`Files.exists(oryxos.db)` 的文件检查仅在 sqlite url 时执行，PG url 时改为连接探测。
- storage 8 个 `@DataJpaTest` 类的五行四件套重复配置抽成共享测试基座（`@SqliteJpaTest` 组合注解 + PG 侧对应物），业务用例抽象基类共享、两 vendor 子类各自实跑（可单独执行、失败可归因）；boot E2E 选代表性场景双库化 + 新增一个 PG 全链路 smoke E2E，其余 E2E 保持 SQLite（全量 ×2 执行时间不可接受）。
- `SqliteDataSourceConfigTest`（断言 PRAGMA）保持 SQLite-only；升级类单测随类退役改写为对应 Java migration 的测试（存量库 fixture 手法保留）。

## R8 宪法与文档同步

**Decision**: 宪法 §技术栈「持久化：SQLite + Spring Data JPA」随本特性 PR 修订为「SQLite（默认）/ PostgreSQL（部署选项）+ Spring Data JPA，表结构由 Flyway 管理」（PATCH 级措辞澄清——原则 VIII 本就写明「手工建表脚本**或 Flyway**」，Flyway 是宪法预留的口）；同步 CLAUDE.md（技术栈表、SQLite 迁移注意改为 Flyway 口径）、`docs/TechnicalSolution.md`、`config/application.yml.example`、`docs/CliGuide.md`、docker-compose 注释（「SQLite ⇒ 只能单副本”补 PG 选项说明）。

## R9 不做的（边界重申）

MySQL、pgvector（向量 BYTEA + Java 余弦已实证库无关，`VectorCodec` float32 小端序两库同字节）、SQLite→PG 存量搬迁工具、分布式行为改造（调度抢锁/租约归 026）、Hibernate `ddl-auto=validate`（收益有限且 SQLite community 方言 validate 误报风险，维持 `none`，本刀不动）、连接池参数调优面板。
