# Feature Specification: 可插拔存储（Pluggable Storage）

**Feature Branch**: `025-pluggable-storage`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "可插拔存储（024-pluggable-storage）：v0.4 分布式底座第一刀——多副本的物理前提。解决三个问题：①多副本没有共同事实源（SQLite 单文件放 NFS 会坏库，两副本连"看到同一批会话"都不成立）；②单机写并发天花板（SQLite 单写者，每轮对话写 5+ 行，几十并发用户即撞写锁，busy_timeout=5000 是止痛药证据）；③表结构演进债指数化（四个手工 SchemaUpgrade 类是 SQLite ALTER 弱的补偿，两种库后每次加列要手写两套幂等方言，且多副本并发启动会同时跑迁移）。要点：引入 Flyway 接管全部表结构迁移——现 schema.sql 收编为 baseline 迁移脚本，既有手工 SchemaUpgrade 类（Audit/Memory/Schedule/NotifyChannel 等）的补列逻辑转为版本化迁移脚本后退役删除；Flyway history 表 + 内建启动锁天然解决多副本并发启动只跑一次迁移。新增 PostgreSQL 支持：迁移脚本按 vendor 双轨目录（sqlite/postgres 各一套，14 处 AUTOINCREMENT、TIMESTAMP 语义、hikari 连接参数等专有面清理），方言/驱动按 datasource url 自动选择；SQLite 仍是默认零配置档（单机五分钟上手是产品资产，不配任何东西行为与现状完全一致——PG 是部署选项不是升级）。向量层（BLOB float32[] + Java 余弦）与 022 密文列天然库无关，换库零数据语义变化。功能面回归零破坏：同一套业务测试在两种库上全绿（PG 测试路径受环境镜像限制，测试策略在 plan 阶段先行验证：候选宿主机 PG 服务/嵌入式 PG 二进制/门禁内 SQLite+发布前 PG 真机清单）。SQLite→PG 的存量数据搬迁工具不在本刀（部署形态选择在初始安装时做出；跨库搬迁留后续按需）。不做：MySQL（评审建议 v0.4 只做 PG——企业开源部署主流且 advisory lock 等能力更全，MySQL 视需求后补）、pgvector（向量层可选优化留缝不实现）、分布式行为改造（调度抢锁/租约归 025→现编号 026 session 归属特性）。"

> 编号说明：v0.4 规划文档中本刀原编号 024；因 `024-container-sandbox`（issue #334）先行占号，按避让惯例顺延为 025。规划四刀实际编号：025 存储 / 026 归属 / 027 文件面 / 028 交付。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 企业管理员用共享数据库部署（Priority: P1）

企业管理员要把 OryxOS 部署成可横向扩展的形态：在部署配置里指向一个企业已有的共享数据库（连接地址 + 账号凭证），启动后系统的全部持久化数据（会话、审计、记忆、知识、调度、渠道/Provider/通知注册表、策略）都落在这个共享库里。多个副本连同一个库时，任何副本上产生的数据在其他副本立即可见——多副本有了共同事实源。

**Why this priority**: 这是 v0.4 分布式底座的物理前提——没有共享事实源，后续的 session 归属（026）、文件面（027）全部无从谈起；同时共享库的写并发能力解除了单机嵌入式库的写锁天花板（几十并发用户即撞锁）。

**Independent Test**: 配置指向共享数据库启动系统，完整跑一轮对话（含工具调用、记忆写入），从数据库侧直接验证会话/审计/记忆等数据落在共享库中；再起第二个进程连同一个库，验证能看到第一个进程产生的会话与审计数据。

**Acceptance Scenarios**:

1. **Given** 一个可用的共享数据库与连接配置，**When** 启动 OryxOS 并完成一轮含工具调用的对话，**Then** 会话、审计（LLM 调用/工具调用/执行历史）、记忆等数据全部写入共享库，功能行为与单机档完全一致
2. **Given** 副本 A 已在共享库上产生会话数据，**When** 副本 B 连同一个库启动并查询会话列表，**Then** 副本 B 能看到副本 A 产生的全部会话
3. **Given** 连接配置指向不可达的数据库或凭证错误，**When** 启动系统，**Then** 启动失败并给出指明配置项的清晰报错（不静默降级回单机档）

---

### User Story 2 - 单机用户零配置无感升级（Priority: P1）

既有单机用户升级到新版本后什么都不用做：不加任何配置，系统仍用本地嵌入式数据库，已有数据（会话历史、记忆、审计、注册的 Provider/渠道）原样可用，全部功能行为与升级前一致。首次启动时系统把既有表结构无损接管进新的迁移管理体系，用户无感知。

**Why this priority**: 「单机五分钟上手」是产品资产——共享数据库是部署选项不是升级门槛；同时存量用户的数据库里已经有真实数据，接管必须无损，这是零破坏承诺的核心场景。

**Independent Test**: 用旧版本产生带数据的工作区（会话+记忆+注册表），换新版本零配置启动，验证数据完好、对话/记忆/审计功能正常、无新增必填配置。

**Acceptance Scenarios**:

1. **Given** 旧版本产生的带数据工作区，**When** 新版本零配置启动，**Then** 启动成功，既有会话/记忆/注册表数据完好可查，新对话正常读写
2. **Given** 全新空工作区，**When** 新版本零配置启动，**Then** 与现状一致自动建库建表，功能完整可用
3. **Given** 已被新版本接管过的工作区，**When** 再次重启，**Then** 不重复执行接管动作，启动时间无明显变化

---

### User Story 3 - 维护者一次定义表结构变更，两种库自动生效（Priority: P2）

项目维护者要给某张表加一列：在版本化迁移目录里为受支持的每种数据库各写一个迁移脚本（同一版本号），提交后所有部署形态（单机嵌入式库、共享库）在下次启动时自动应用变更且只应用一次；多个副本同时启动时迁移也只执行一次，其余副本等待后继续。旧的手工建表/补列代码全部退役，表结构的唯一真相源是版本化迁移目录。

**Why this priority**: 表结构演进债随库种数指数化——没有统一迁移体系，两种库时代的每次加列都是两套手写幂等方言 + 并发启动竞态。这是维护性投资，排在两个部署场景之后。

**Independent Test**: 加一个测试性迁移脚本，分别在两种库上从旧结构启动，验证变更自动应用且重启不重复应用；两进程同时启动验证迁移只跑一次。

**Acceptance Scenarios**:

1. **Given** 新增一个版本化迁移脚本，**When** 各部署形态重启，**Then** 表结构变更自动生效且迁移历史有记录
2. **Given** 多个副本指向同一共享库同时启动，**When** 存在未应用的迁移，**Then** 迁移恰好执行一次，其余副本等待完成后正常启动
3. **Given** 某迁移脚本执行失败，**When** 启动系统，**Then** 启动失败并报出失败的迁移版本与原因（不带病运行）

---

### Edge Cases

- 存量工作区表结构与预期不一致：历史版本差异由幂等迁移序列自动收敛；调度面结构无法识别（非本产品所建或被手工改动）时拒绝启动并报出差异；其余表的任意手工改动不做完整结构校验（属结构 validate 范畴，本刀明确不做），以运行时报错兜底
- 共享库是空库但账号缺建表权限：启动报错须指明是权限问题而非连接问题
- 迁移执行到一半进程被杀：下次启动能否从失败点恢复或明确报出需人工介入的状态
- 两种库对同一业务数据的语义差异（时间戳精度、布尔表示、大小写排序）不得引起功能面行为差异
- 副本 A 用新版本（已迁移到 V(n+1)）、副本 B 还是旧版本连同一库：旧版本副本不因新增列而崩溃（本刀只要求加列类前向兼容变更）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持通过部署配置指向外部共享数据库，所有持久化数据（会话、三张审计表、记忆、知识索引、调度状态与执行历史、Provider/渠道/通知注册表、工具策略）统一落在所配置的库中——不存在部分数据仍留在本地库的混合形态
- **FR-002**: 未提供任何数据库配置时，系统 MUST 保持现状：使用工作区内的本地嵌入式数据库，零新增必填配置，功能行为与本特性交付前完全一致
- **FR-003**: 系统 MUST 用统一的版本化迁移体系管理全部表结构：建表与结构变更以带版本号的迁移脚本表达，应用历史落库可查，同一迁移不重复执行
- **FR-004**: 系统 MUST 无损接管存量单机数据库：首次以新版本启动时将既有表结构标记为基线，既有数据完好，后续增量迁移正常应用；接管前后功能行为一致
- **FR-005**: 多个副本指向同一共享库并发启动时，未应用的迁移 MUST 恰好执行一次；其余副本等待迁移完成后继续启动，不产生重复执行或表结构冲突
- **FR-006**: 每种受支持的数据库 MUST 有独立的迁移脚本目录；系统按所连接的数据库种类自动选择对应目录与连接方言，无需用户显式声明库类型
- **FR-007**: 既有手工建表/补列逻辑（启动期 schema 升级类）MUST 全部收编为版本化迁移脚本后退役删除，表结构唯一真相源是迁移目录
- **FR-008**: 数据库连接凭证 MUST 遵循既有敏感配置纪律：支持从环境变量注入，不要求明文写入配置文件；连接失败/凭证错误/权限不足时启动报错并指明问题类别
- **FR-009**: 语义向量数据与加密凭证数据 MUST 在两种库上保持同一读写语义（字节级载荷不因库而变），检索与解密行为一致
- **FR-010**: 全部业务功能（对话、工具调用、记忆存取、知识检索、调度、通知、审计查询、管理台）MUST 在两种库上行为一致——同一套业务测试在两种库上全绿
- **FR-011**: 迁移脚本执行失败时系统 MUST 拒绝继续启动，报错包含失败的迁移版本与数据库反馈的原因

### Key Entities

- **迁移脚本（versioned migration）**: 一次表结构变更的最小单元——版本号 + 描述 + 目标库种；同一版本号在每种受支持库各有一份实现；有序、只增不改
- **迁移历史（migration history）**: 落库的已应用迁移清单——版本、校验和、执行时间与结果；既是幂等依据也是并发启动的互斥载体
- **基线（baseline）**: 存量数据库被接管时的起始结构快照标记——之前的结构视为已应用，之后按增量迁移演进
- **数据源配置（datasource config）**: 部署时声明的数据库指向——连接地址、凭证（环境变量注入）、连接池参数；缺省即本地嵌入式库

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单机用户零配置升级后，既有数据完好、全部功能可用——存量工作区回归走查零异常，无任何新增必填配置项
- **SC-002**: 配置共享数据库后，一轮完整对话产生的全部持久化数据可在数据库侧直接查得，与单机档同一口径
- **SC-003**: 两个进程连同一共享库，其一产生的会话/审计数据另一个立即可查——共同事实源成立
- **SC-004**: 多副本并发启动含未应用迁移的场景，迁移历史表中每个版本恰好一条成功记录
- **SC-005**: 存储层全套数据访问用例（8 类）以同一套用例在两种库上全部通过，另有覆盖对话/审计/记忆/重启恢复的共享库全链路端到端用例；零跳过零豁免
- **SC-006**: 既有手工 schema 升级类全部删除，仓库内表结构定义只存在于迁移目录一处
- **SC-007**: 共享库部署档在并发写入场景（多用户同时对话）不再出现单机档的写锁等待报错——数十并发会话写入零锁冲突
- **SC-008**: 迁移失败/连接失败/权限不足三类故障各自的启动报错能让部署者不看源码定位到配置或环境问题

## Assumptions

- 共享数据库由企业自备（自建或托管），OryxOS 不负责数据库本身的部署、备份与高可用
- 本刀交付后受支持的库为两种：本地嵌入式库（默认档）与一种企业级共享库（部署选项）；其他库种（如 MySQL）视需求后补，本刀不做
- SQLite→共享库的存量数据搬迁工具不在本刀范围——部署形态选择在初始安装时做出，跨库搬迁留后续按需
- 向量检索的可选优化（数据库原生向量类型）不在本刀范围，向量层保持库无关实现
- 分布式行为改造（调度跨副本抢锁、session 租约、去重下沉）归 026 session 归属特性，本刀只提供物理前提
- 滚动升级期间的新旧版本共存只要求「加列类前向兼容」；破坏性结构变更的滚升策略随 028 容器交付特性定义
- 测试环境对企业级共享库的可用性在 plan 阶段先行验证并定档（宿主机服务/嵌入式二进制/发布前真机清单三选一或组合）
