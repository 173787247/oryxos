# Feature Specification: 密钥加密存储

**Feature Branch**: `022-secret-encryption`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "密钥加密存储（022-secret-encryption）：v0.3 治理面收尾第一刀——落库凭证从明文变密文，「数据库泄露不再等于凭证泄露；管理台不再能抄 key」。范围：providers.api_key 与 notify_channels.config 内敏感字段（SMTP password 等）写库前 AES-GCM 加密、读取时解密，密文带版本前缀；定义 SecretCipher 接口做一层隔离，本版本落地「本地主密钥」实现，KMS/Vault 留升级缝。主密钥两档：本地试用零配置——首启自动生成落 .oryxos/master.key（0600）静默可用；生产用环境变量 ORYXOS_MASTER_KEY 覆盖。存量明文启动幂等迁移；已有密文但密钥缺失/不匹配时清晰报错拒启并指路恢复；全新库零配置可用。管理台凭证字段只写不回显（掩码 + 留空/掩码原样=保持原值）。不做：审计表内容加密、密钥轮换 UI、真实 KMS 对接、AGENT.md ${ENV} 路径。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 数据库泄露不再等于凭证泄露 (Priority: P1)

企业管理员在管理台录入了多个 LLM Provider 的 API key 和通知渠道的邮箱密码。数据库文件在备份外传、误拷贝、运维交接等场景中单独流出时，拿到文件的人无法从中读出任何第三方凭证的明文；而系统自身的功能（LLM 调用、通知发送、管理台编辑）与加密前完全一致。已在运行的老系统升级到本版本后，库里已有的明文凭证在一次启动内自动完成加密，管理员无需任何手工操作。

**Why this priority**: 这是本特性的存在理由——当前凭证明文落库是自认的"核心阶段让步"，是 v0.3 治理面的最后一笔安全欠账；且 v0.4 共享数据库（多实例共读）之前必须还清，否则风险随架构升级放大。

**Independent Test**: 录入凭证后直接打开数据库文件查询凭证字段——只能看到带标记的密文；重启后 LLM 调用与通知发送照常工作；用升级前的明文库启动一次，全部凭证变为密文且功能不变。

**Acceptance Scenarios**:

1. **Given** 管理台已录入 Provider API key 与含邮箱密码的通知渠道, **When** 直接查询数据库文件中对应字段, **Then** 只能看到带版本标记的密文，任何位置不出现明文
2. **Given** 凭证已加密落库, **When** 触发一次使用该 Provider 的对话与一次邮件通知, **Then** 两者行为与加密前一致（凭证在使用时正确还原）
3. **Given** 升级前的库中存有 N 条明文凭证, **When** 新版本首次启动, **Then** 全部明文自动转为密文、日志记录迁移条数，重复启动不重复迁移
4. **Given** 配置文件中以环境变量形式声明的 Provider 首次播种入库, **When** 播种完成, **Then** 落库值同样为密文

---

### User Story 2 - 主密钥两档配置与故障自明 (Priority: P2)

本地试用者下载即跑：不配置任何东西，系统首次启动自动生成密钥文件放在工作区内（仅属主可读），全程无感。生产部署者按部署文档设置一条环境变量作为主密钥（与现有凭证注入方式同构），环境变量存在时优先于密钥文件。当库中已有密文而主密钥丢失或不匹配时，系统启动即失败并明确说明原因与两条恢复路径（找回原密钥 / 清除并重新录入凭证），绝不静默降级或带病运行。

**Why this priority**: 加密的可用性边界就在密钥管理——配置负担设计不好，安全特性会变成部署劝退项；故障不自明，会变成"系统坏了"的误报工单。

**Independent Test**: 全新环境不配任何变量启动即可用；删除密钥文件后再启动，得到含恢复指引的明确报错而非隐晦异常；设置环境变量后重启，以环境变量为准。

**Acceptance Scenarios**:

1. **Given** 全新工作区且未设置主密钥环境变量, **When** 首次启动, **Then** 系统自动生成密钥文件（仅属主可读）并正常提供全部功能，无需用户理解任何密钥概念
2. **Given** 已设置主密钥环境变量, **When** 启动, **Then** 以环境变量为准；工作区密钥文件不再被读取
3. **Given** 库中已有密文凭证, **When** 主密钥缺失或与加密时不一致地启动, **Then** 启动失败，报错说明「已有 N 条加密凭证无法解密」及两条恢复路径，不静默清空、不明文回退
4. **Given** 密钥文件由系统自动生成, **When** 检查版本控制忽略规则, **Then** 密钥文件在忽略清单内，不会被提交

---

### User Story 3 - 管理台与 API 不再回显凭证明文 (Priority: P3)

管理员打开管理台的通知渠道页或调用其查询接口时，SMTP 密码等敏感配置项只显示掩码，不再返回明文（Provider API key 已有同款掩码机制，本故事将其补齐到通知渠道并统一口径）。编辑渠道时，敏感项留空或原样提交掩码值即表示"保持原值"，只有输入新值才会更新——与 Provider 编辑、API Key「创建时看一次」的既有交互范式一致。

**Why this priority**: 堵住"任何能打开管理台的人都能抄走全部凭证"的回显面；排在 P3 是因为 Provider 侧机制已存在，本故事是补缺口与统一，而非从零建。

**Independent Test**: 查询通知渠道列表/详情接口，响应中敏感项均为掩码；编辑时不动敏感项保存，原凭证仍可正常发通知；输入新值保存后按新值生效。

**Acceptance Scenarios**:

1. **Given** 已存在含邮箱密码的通知渠道, **When** 查询渠道列表或详情, **Then** 密码项显示为掩码，响应任何字段不含明文
2. **Given** 编辑通知渠道时密码项保持掩码原样或留空, **When** 保存, **Then** 原密码保持不变，通知发送照常
3. **Given** 编辑时密码项输入了新值, **When** 保存, **Then** 后续通知使用新密码
4. **Given** 任一携带凭证的管理接口, **When** 遍历其全部查询响应, **Then** 无一处返回凭证明文

---

### Edge Cases

- 迁移中断（加密到一半进程被杀）：再次启动从断点幂等续跑，已密文行跳过、明文行补齐
- 密文行被手工改坏（截断/篡改）：使用该凭证时单条清晰报错并定位到条目，不影响其他凭证与系统整体
- 环境变量与密钥文件同时存在且不一致：环境变量优先；若因此解不开既有密文，按"密钥不匹配"报错处理，不自动尝试另一档
- 主密钥值格式非法（长度/编码不对）：启动即报错说明格式要求，不降级明文
- 通知渠道 config 中敏感项名录之外的普通项（host/port/from）：保持明文可读，不过度加密影响排障
- 空值/空串凭证：不加密、不产生密文标记，保持现状语义

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在 Provider API key 落库前加密、使用时解密，加密后所有既有功能行为不变（LLM 调用、连通性测试、管理台编辑）
- **FR-002**: 系统 MUST 对通知渠道配置中的敏感项（密码类字段的既定名录）落库前加密、使用时解密；名录外的普通配置项保持原样
- **FR-003**: 密文 MUST 携带可识别的版本标记，与明文可区分，为未来算法或密钥体系升级留出识别依据
- **FR-004**: 主密钥来源 MUST 支持两档且环境变量优先：设置了主密钥环境变量则以其为准；未设置则使用工作区密钥文件，文件不存在时首次启动自动生成（仅属主可读权限）
- **FR-005**: 系统 MUST 在启动时将存量明文凭证幂等迁移为密文，记录迁移条数日志；重复启动与迁移中断续跑均不产生重复或破坏
- **FR-006**: 当库中已有密文而主密钥缺失、格式非法或不匹配时，系统 MUST 启动失败并输出含恢复路径（找回原密钥 / 清除重录凭证）的明确报错；MUST NOT 静默降级为明文或清空数据。全新库零配置 MUST 可正常启动使用
- **FR-007**: 加解密 MUST 收敛在单一可替换的机制边界内，为对接外部密钥管理服务（KMS/Vault 类）预留升级位，替换实现不影响调用方
- **FR-008**: 管理台与查询接口 MUST 不回显任何凭证明文：敏感项以掩码呈现；编辑时掩码原样提交或留空 MUST 视为"保持原值"（沿用 Provider 既有的确定性掩码与未修改判定机制，推广到通知渠道）
- **FR-009**: 主密钥 MUST NOT 出现在日志、错误信息、接口响应中；自动生成的密钥文件 MUST 在版本控制忽略清单内
- **FR-010**: 单条凭证解密失败 MUST 只影响该凭证的使用（清晰报错并定位条目），不得导致系统整体不可用或影响其他凭证
- **FR-011**: 本特性 MUST NOT 包含：审计表内容加密（021 已裁决展示层脱敏+落库原文）、密钥轮换界面、真实 KMS/Vault 对接、AGENT.md 中环境变量引用路径的改动（本就不落库）

### Key Entities

- **落库凭证**: 需要加密保护的第三方秘密——Provider API key、通知渠道配置中的密码类项；特征是"可再生"（服务商处可重新签发），丢失密钥的恢复路径因此成立
- **主密钥**: 加解密落库凭证的唯一钥匙，来源两档（环境变量 / 工作区密钥文件）；心智模型为"保险柜钥匙"——与保险柜（数据库）分开存放
- **密文标记**: 密文的版本化前缀形态，承担明文/密文判别与未来升级识别

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单独获得数据库文件的人无法从中读出任何第三方凭证明文（凭证字段 100% 为密文或空）
- **SC-002**: 存量系统升级后一次启动内完成全部明文凭证加密，LLM 调用与通知发送行为与升级前一致（回归零破坏）
- **SC-003**: 全新部署在不配置、不理解任何密钥概念的前提下开箱即用（零新增必配项）
- **SC-004**: 密钥缺失/不匹配/非法的每一种故障场景都在启动阶段被拦截并给出含恢复路径的报错（故障自明率 100%，无静默降级）
- **SC-005**: 管理台全部页面与查询接口响应中凭证明文出现次数为 0（含通知渠道配置——当前的回显缺口被堵上）
- **SC-006**: 加密引入的启动与单次调用开销无用户可感知影响（启动增时不超过 1 秒）
- **SC-007**: 部署文档如实陈述威胁边界：防数据库文件单独外流；密钥文件档与库同目录时不防整机沦陷，生产应使用环境变量档

## Assumptions

- 单实例单主密钥：本版本不考虑多实例共享密钥的分发问题（v0.4 分布式底座再议，环境变量档天然兼容 K8s Secret 分发）
- `web_users.password_hash`（bcrypt）与 `api_keys.key_hash`（单向哈希）已是不可逆形态，不在加密范围
- MCP server 凭证走 `mcp_servers.yaml` 的环境变量引用、不落库，不在范围
- 通知渠道敏感项名录以密码类字段为准（如 password/token 类），具体清单在设计阶段结合现有渠道类型定稿
- Provider 掩码回显与"未修改"判定机制已存在且工作正常，本特性沿用其口径而非另造一套
